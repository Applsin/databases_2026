## Q1. Уникальные рейсы и сортировка

### DISTINCT vs GROUP BY — есть ли разница?

```sql
SELECT DISTINCT flight_no FROM flights ORDER BY flight_no;
SELECT flight_no FROM flights GROUP BY flight_no ORDER BY flight_no;
```

Проверил `EXPLAIN` на обоих — планы **идентичны**:

```
Sort
  Sort Key: flight_no
  ->  HashAggregate
        Group Key: flight_no
        ->  Seq Scan on flights
```

Postgres строит `DISTINCT` через тот же `HashAggregate`/`Group Key`, что и
`GROUP BY` без агрегатных функций — планировщик распознаёт, что задача
одна и та же ("схлопнуть повторяющиеся значения одной колонки"), и выбирает
одинаковую стратегию выполнения. По итоговому набору данных они тоже дают
идентичный результат — оба возвращают ровно уникальные значения `flight_no`.

**Может ли результат когда-либо различаться?** По итоговому набору данных —
нет, для одной колонки без дополнительных условий это всегда одно и то же
множество значений. Разница может появиться только концептуально, если
запрос усложняется: `GROUP BY` позволяет добавить агрегатные функции
(`COUNT`, `SUM` и т.п.) в `SELECT`, а `DISTINCT` — нет (для этого пришлось
бы обернуть в подзапрос). Но сам по себе список уникальных `flight_no`
будет одинаковым.

### Почему ORDER BY flight_no достаточно без ASC

`ASC` — направление сортировки по умолчанию в SQL-стандарте и в Postgres,
поэтому `ORDER BY flight_no` эквивалентно `ORDER BY flight_no ASC`. Указывать
его явно нужно только для убывающего порядка (`DESC`) или когда хочется
явно зафиксировать намерение для читаемости кода.

### Сортировка 'PG0001' и 'pg0001'

Проверил на реальных данных:

```sql
SELECT DISTINCT flight_no FROM flights ORDER BY flight_no;
```
```
 flight_no
-----------
 PG0001
 PG0002
 PG0003
 PG0004
 PG0005
 pg0001
```

Все варианты в верхнем регистре оказались **раньше** `pg0001` (нижний
регистр). Проверил коллацию базы:

```sql
SELECT datcollate FROM pg_database WHERE datname = current_database();
-- C.UTF-8
```

При коллации `C` (или `C.UTF-8`) Postgres сортирует строки побайтово, по
кодам символов (ASCII/Unicode code point). Заглавные латинские буквы имеют
меньшие коды (65–90), чем строчные (97–122), поэтому весь блок `'P...'`
оказывается раньше `'p...'` — а не рядом друг с другом по алфавиту, как
могло бы показаться интуитивно. При другой коллации (например,
`en_US.UTF-8` или ICU-коллации) сортировка может быть "языковой" — тогда
регистр часто учитывается только как второстепенный признак, и `'PG0001'`
и `'pg0001'` могли бы оказаться рядом. То есть **результат сортировки
зависит от коллации базы**, а не является универсальной константой SQL.

## Q2. Аэропорты и выручка за билеты

### Двойной ли счёт, если пассажир купил 2 билета на один рейс?

Запрос:

```sql
SELECT f.flight_id, f.flight_no,
       COALESCE(SUM(tf.amount), 0) AS revenue,
       COUNT(DISTINCT t.passenger_id) AS unique_passengers
FROM flights f
LEFT JOIN ticket_flights tf ON tf.flight_id = f.flight_id
LEFT JOIN tickets t ON t.ticket_no = tf.ticket_no
GROUP BY f.flight_id, f.flight_no
ORDER BY f.flight_id;
```

Проверил на данных, где пассажир `P001` купил **3** билета на рейс `PG0001`
(`0001`, `0002`, `0005`), а `P002` — 1 билет (`0003`):

```
 flight_id | flight_no | revenue  | tickets_sold(COUNT(*)) | unique_passengers
-----------+-----------+----------+-------------------------+--------------------
         1 | PG0001    | 30300.00 |                       4 |                  2
```

Если бы я использовал `COUNT(*)` (или `COUNT(tf.ticket_no)`) для подсчёта
"пассажиров", получилось бы **4** — по одному на каждый билет, хотя реальных
людей на рейсе только **2**. Это и есть двойной счёт: один и тот же
пассажир (`passenger_id`), купивший несколько билетов на один рейс, был бы
посчитан несколько раз. Правильная метрика — `COUNT(DISTINCT t.passenger_id)`,
а не `COUNT(*)`. Выручку (`SUM(amount)`) двойной счёт не искажает — это
сумма денег со всех проданных билетов, и здесь каждый билет действительно
должен учитываться отдельно (два билета = два реальных платежа).

### Рейс без единого проданного билета

Проверил на `PG0002` (рейс существует, но в `ticket_flights` для него
пусто):

```
 flight_id | flight_no | revenue | unique_passengers
-----------+-----------+---------+--------------------
         3 | PG0002    |       0 |                  0
```

Рейс попал в результат с выручкой `0`, потому что я использовал
`LEFT JOIN` от `flights` к `ticket_flights` (не наоборот). `INNER JOIN`
здесь не подошёл бы: он вернул бы только те рейсы, у которых **есть** хотя
бы одна совпадающая строка в `ticket_flights`, и рейс без единого
проданного билета просто исчез бы из результата — а по условию задачи он
должен появиться с нулевой выручкой. `LEFT JOIN` сохраняет все строки
левой таблицы (`flights`) независимо от того, нашлось ли совпадение
справа, подставляя `NULL` вместо отсутствующих значений — поэтому я обернул
`SUM` в `COALESCE(..., 0)`, иначе `SUM` по всем `NULL` дал бы `NULL`, а не
`0`.

## Q3. Отменённые рейсы и города

### Город без единого рейса в таблице flights

В тестовых данных есть аэропорт `GHO` ("Город без рейсов"), который вообще
не упоминается в `flights`. Запрос через `NOT EXISTS`:

```sql
SELECT city FROM airports a
WHERE NOT EXISTS (
    SELECT 1 FROM flights f
    WHERE f.departure_airport = a.airport_code
      AND f.status = 'Cancelled'
);
```

Результат:

```
       city
------------------
 Санкт-Петербург
 Казань
 Сочи
 Город без рейсов
```

Такой город **должен** попасть в результат — по формулировке задания нужны
"города, из которых ни один рейс не был отправлен со статусом Cancelled".
Город, из которого вообще никогда не было рейсов, формально удовлетворяет
этому условию (среди его рейсов, коих 0 штук, действительно нет ни одного
отменённого) — и `NOT EXISTS` корректно включает его, потому что подзапрос
для него просто не находит ни одной подходящей строки в принципе, а не
из-за проблем с `NULL`.

### Ловушка NOT IN + NULL

Формулировка вопроса: `city NOT IN (SELECT departure_airport ... WHERE status = 'Cancelled')`
может вернуть **пустой результат**, если подзапрос вернёт хотя бы один
`NULL`. Проверил это искусственно, добавив `NULL` в список подзапроса:

```sql
SELECT city FROM airports a
WHERE a.airport_code NOT IN (
    SELECT departure_airport FROM flights WHERE status = 'Cancelled'
    UNION
    SELECT NULL
);
```

Результат — **0 строк**, хотя без добавленного `NULL` запрос корректно
возвращал 4 города.

**Почему так происходит:** `NOT IN` в SQL — это синтаксический сахар для
цепочки сравнений через `AND`:
`x NOT IN (a, b, NULL)` ⟺ `x <> a AND x <> b AND x <> NULL`.
Любое сравнение с `NULL` (`x <> NULL`) даёт не `FALSE`, а **`NULL`** (в
трёхзначной логике SQL: `TRUE`/`FALSE`/`UNKNOWN`). А `TRUE AND ... AND NULL`
в итоге тоже даёт `NULL`, а не `TRUE` — то есть `WHERE` отбрасывает такую
строку, как будто условие не выполнено, хотя по смыслу должно было
выполниться. Из-за этого **вообще все** строки, для которых в списке
подзапроса встретился `NULL`, исчезают из результата — отсюда пустая
выборка.

`NOT EXISTS` этой проблемы лишён, потому что он не сравнивает значения
между собой напрямую — он просто проверяет "нашлась ли хотя бы одна
подходящая строка" (`TRUE`/`FALSE`, без промежуточного `UNKNOWN` из-за
`NULL` где-то в списке). Практически это подтвердилось: с той же
искусственной строкой `NULL` в данных `NOT EXISTS` всё равно вернул
правильные 4 города.

**В моей текущей схеме** `departure_airport` объявлен `NOT NULL`, поэтому
классический вариант ловушки (когда в реальных данных `departure_airport`
оказывается `NULL`) физически невозможен — но опасность в другом: если
подзапрос выбирает **любую** колонку, которая теоретически может быть
`NULL` (например, если бы условие было не по `departure_airport`, а по
какому-то необязательному полю), ловушка сработала бы совершенно так же.
Поэтому `NOT EXISTS` — безопасный выбор по умолчанию для таких запросов,
даже если сейчас конкретная колонка защищена `NOT NULL`.

## Q4. Места на борту и дубликаты

### Уникальные пассажиры рейса: DISTINCT или GROUP BY?

```sql
SELECT DISTINCT t.passenger_id, t.passenger_name
FROM boardings b JOIN tickets t ON t.ticket_no = b.ticket_no
WHERE b.flight_id = 1;
```
против
```sql
SELECT t.passenger_id, t.passenger_name
FROM boardings b JOIN tickets t ON t.ticket_no = b.ticket_no
WHERE b.flight_id = 1
GROUP BY t.passenger_id, t.passenger_name;
```

`EXPLAIN` на обоих дал **практически идентичную стоимость** (`cost=28.55..28.58`
у обоих), различие только в имени узла плана: `Unique` (для `DISTINCT`) и
`Group` (для `GROUP BY`) — оба строятся через `Sort` + схлопывание соседних
одинаковых строк. То есть здесь, как и в Q1, разницы в производительности
нет — это, по сути, два синтаксиса для одной и той же операции.
`GROUP BY` эффективнее использовать, только если дополнительно нужны
агрегаты (например, посчитать, сколько посадочных талонов оформлено на
пассажира) — тогда `DISTINCT` не подойдёт в принципе.

### Сданный билет, но есть посадочный талон

В тестовых данных билет `0004` (пассажир Сидоров) специально **не** добавлен
в `ticket_flights` (билет "сдан"), но при этом есть строка в `boardings`.
Проверил:

```sql
SELECT t.ticket_no, t.passenger_name, tf.ticket_no IS NOT NULL AS has_valid_ticket
FROM boardings b
JOIN tickets t ON t.ticket_no = b.ticket_no
LEFT JOIN ticket_flights tf ON tf.ticket_no = b.ticket_no AND tf.flight_id = b.flight_id
WHERE b.flight_id = 1;
```

```
 ticket_no | passenger_name | has_valid_ticket
-----------+----------------+------------------
 0004      | Сидоров Сидор  | f
```

**Да, этот пассажир окажется в списке**, если строить список пассажиров
через `JOIN tickets ↔ boardings` (как в вопросе Q4.1) — потому что запись
о посадке (`boardings`) физически существует, и сама таблица `tickets` тоже
не удаляет билет при возврате (его статус меняется, но строка остаётся).
Это реальная аномалия данных: посадочный талон выдан пассажиру, у которого
уже нет действующего билета на этот рейс. Если бы список пассажиров строился
не через `boardings`, а через `ticket_flights` (`INNER JOIN` с ним), такой
пассажир **не** попал бы в выборку — что и демонстрирует колонка
`has_valid_ticket = false` в моём запросе: у него есть посадочный талон, но
нет действующего билета. Какую из двух версий считать "правильной" —
зависит от бизнес-смысла отчёта (кто реально прошёл на борт vs у кого
действующий билет), но сам факт расхождения между `boardings` и
`ticket_flights` нужно уметь замечать.

## Q5. DDL и блокировки на живой таблице

### ALTER TABLE ... ADD COLUMN во время долгого SELECT

Смоделировал сценарий буквально: открыл в фоне транзакцию
`BEGIN; SELECT count(*) FROM flights;`, не коммитил её 8 секунд, и во время
её работы запустил `ALTER TABLE flights ADD COLUMN weather_data JSONB;`.

Проверил активные блокировки прямо во время работы фоновой транзакции:

```
 pid |      mode        | granted | relation
-----+------------------+---------+----------
 241 | AccessShareLock   | t       | flights
```

`SELECT` берёт `AccessShareLock` — это самая слабая блокировка, она
разрешена одновременно с любым количеством других `AccessShareLock`, но
**конфликтует** с `AccessExclusiveLock`, который обязателен для `ALTER TABLE
ADD COLUMN` (структурное изменение таблицы требует эксклюзивного доступа —
чтобы никто параллельно не читал/писал по старой структуре, пока меняется
метаданные и, возможно, физический формат строк).

Замерил реальное время выполнения `ALTER TABLE`, запущенного параллельно:
**3.79 секунды** — то есть команда не завершилась мгновенно, а буквально
"зависла" в очереди на получение `AccessExclusiveLock`, ожидая, пока
фоновая транзакция (держащая `AccessShareLock`) не завершится (`COMMIT`
происходит автоматически при закрытии сессии). Как только `SELECT`-сессия
закрылась, `ALTER TABLE` тут же получила лок и выполнилась.

**Итог:** `ALTER TABLE ... ADD COLUMN` (без явного значения по умолчанию,
до PG11 включая случаи с non-const default) требует `AccessExclusiveLock`
на всю таблицу, и будет ждать, пока не закроются вообще все транзакции,
удерживающие любую блокировку на этой таблице — включая безобидный на вид
`SELECT` в открытой, но незакоммиченной транзакции.

### ADD COLUMN ... DEFAULT false — почему мгновенно (PG11+)

Выполнил:

```sql
ALTER TABLE flights ADD COLUMN is_delayed BOOLEAN DEFAULT false;
```

Проверил, как Postgres на самом деле хранит значение по умолчанию:

```sql
SELECT attname, atthasmissing, attmissingval
FROM pg_attribute
WHERE attrelid = 'flights'::regclass AND attname = 'is_delayed';
```
```
  attname   | atthasmissing | attmissingval
------------+---------------+---------------
 is_delayed | t             | {f}
```

С PostgreSQL 11 добавление колонки с **константным** значением по
умолчанию — это чисто операция над системным каталогом (`pg_attribute`):
Postgres записывает флаг `atthasmissing = true` и само значение
(`attmissingval`), но **не переписывает** ни одной уже существующей строки
таблицы. Для старых строк, у которых физически нет значения в этом столбце,
при чтении Postgres просто подставляет `attmissingval` "на лету". Новые
строки, вставленные после `ALTER`, уже физически хранят `is_delayed`
как обычную колонку. Именно поэтому операция занимает миллисекунды
независимо от размера таблицы — раньше (до PG11) пришлось бы переписать
**все** строки таблицы, удерживая `AccessExclusiveLock` всё это время,
что на таблице с миллионами строк могло занимать минуты и блокировать всю
работу с таблицей.

**Что произойдёт при изменении DEFAULT на true после этого:**
`ALTER TABLE flights ALTER COLUMN is_delayed SET DEFAULT true;` меняет
значение по умолчанию **только для будущих `INSERT`**, которые не укажут
это поле явно — на уже существующие строки (включая те, что используют
"missing value" оптимизацию выше со значением `false`) это не влияет:
у них уже "зафиксировано" старое значение `false`, либо явно, либо через
`attmissingval`. Параллельные `INSERT`, которые выполняются прямо в момент
`ALTER ... SET DEFAULT`, либо успеют захватить старое значение default,
либо новое — это также определяется блокировкой (`SET DEFAULT` тоже берёт
`AccessExclusiveLock`, хоть и на короткое время, так как меняет только
метаданные), так что "разрыва" в middle of insert не будет — каждая
конкретная `INSERT`-команда увидит консистентное значение default.

### CREATE INDEX без CONCURRENTLY блокирует запись

```sql
CREATE INDEX idx_flights_status ON flights(status);
```

Обычный `CREATE INDEX` берёт `ShareLock` на таблицу на всё время
построения индекса. `ShareLock` не конфликтует с другим `ShareLock`
(поэтому параллельные `SELECT` продолжают работать), но конфликтует с
блокировками, которые берут `INSERT`/`UPDATE`/`DELETE`
(`RowExclusiveLock`) — поэтому все попытки изменить данные в таблице
"подвисают" в очереди до завершения построения индекса. Чем больше
таблица, тем дольше строится индекс — и тем дольше блокировка на запись.

Чтобы избежать этого, используется:

```sql
CREATE INDEX CONCURRENTLY idx_flights_status ON flights(status);
```

`CONCURRENTLY` строит индекс в два прохода, не блокируя `INSERT`/`UPDATE`/
`DELETE` вообще (берёт более слабую блокировку). **Компромисс:** строится
заметно медленнее обычного `CREATE INDEX` (обычно в 2-3 раза дольше), не
может выполняться внутри транзакционного блока (`BEGIN...COMMIT`) вместе с
другими командами, и если процесс построения будет прерван (например,
конфликт с параллельным изменением данных), может остаться "битый"
невалидный индекс (`INVALID` в `pg_index`), который придётся вручную
удалить и попробовать снова — обычный `CREATE INDEX` в этом смысле проще
и надёжнее, поэтому `CONCURRENTLY` применяют осознанно, именно когда
простой на запись недопустим (production-таблица под нагрузкой), а не
"всегда на всякий случай".

## Q6. Агрегация и NULL в вычислениях

### AVG(actual_departure - scheduled_departure) с NULL

Добавил в данные рейсы без `actual_departure` (отменённые/ещё не
вылетевшие) и проверил:

```sql
SELECT AVG(actual_departure - scheduled_departure) AS avg_delay,
       COUNT(*) AS total_flights,
       COUNT(actual_departure) AS flights_with_actual_departure
FROM flights;
```
```
 avg_delay | total_flights | flights_with_actual_departure
-----------+---------------+--------------------------------
 00:06:40  |             7 |                              3
```

Всего рейсов — 7, но реальный вылет (`actual_departure`) зафиксирован
только у 3. `AVG` **молча исключает** строки с `NULL` из расчёта — то есть
среднее считается не как "сумма задержек / все рейсы", а как "сумма
задержек / только рейсы, где известна фактическая дата вылета". Это может
серьёзно искажать бизнес-метрику: если считать "средняя задержка" как
индикатор качества авиакомпании, а значительная часть рейсов отменена
(и потому не участвует в среднем), метрика будет выглядеть лучше, чем есть
на самом деле — отменённые рейсы, по сути худший случай для пассажира,
просто "не считаются". Для честной метрики отменённые рейсы стоит
учитывать отдельно (например, добавить `COUNT(*) FILTER (WHERE status = 'Cancelled')`
рядом со средней задержкой, а не полагаться на одно число `AVG`).

### COUNT(aircraft_code) vs COUNT(*)

```sql
SELECT COUNT(aircraft_code) AS count_col, COUNT(*) AS count_star FROM flights;
```

До добавления рейса с `aircraft_code IS NULL` оба давали одинаковое число
(6 = 6), потому что в тех данных `aircraft_code` был заполнен у всех строк.
После добавления рейса `PG0006` с `aircraft_code = NULL`:

```
 count_col | count_star
-----------+------------
         6 |          7
```

Значения **разошлись**. `COUNT(*)` считает все строки таблицы без
исключений. `COUNT(column)` считает только строки, где значение этой
конкретной колонки **не** `NULL` — это стандартное поведение всех
агрегатных функций Postgres (кроме `COUNT(*)`): `NULL` пропускается.
Разойтись эти два счётчика могут ровно в одном случае — если на уровне
схемы колонка **не** объявлена `NOT NULL` (как `aircraft_code` в моей
схеме) и хотя бы одна строка реально содержит `NULL`. Если бы на колонку
было наложено ограничение `NOT NULL`, `COUNT(column)` и `COUNT(*)` были бы
гарантированно равны всегда — сама схема исключала бы возможность `NULL`.
