# КОНСПЕКТ ЛЕКЦИИ №1
## Реляционная модель, моделирование данных и реляционная алгебра

---

### 0. Данные, СУБД, реляционная алгебра (выжимка)

- **Данные → Информация → Знания**: сырые факты → факты в контексте → правила и закономерности (см. лекция.md, раздел 1).
- **Типы данных по структурированности**: структурированные (таблицы → PostgreSQL), слабоструктурированные (JSON/XML → JSONB, MongoDB), неструктурированные (видео, текст → S3/Data Lake). В проектах — полиглотное хранение.
- **OLTP и OLAP** (лекция.md, раздел 1.6): OLTP — частые короткие транзакции, нормализованная схема, критична целостность; OLAP — редкие тяжёлые аналитические запросы, допустима денормализация, колоночные СУБД.
- **Жизненный цикл данных** (лекция.md, раздел 1.7): создание → хранение → использование → архивирование → удаление (для ПДн сроки хранения ограничены 152-ФЗ).
- **Нормативный контур** (лекция.md, раздел 1.5): 149-ФЗ (оборот информации, журналирование), 152-ФЗ (персональные данные: минимизация, согласие, обезличивание), 187-ФЗ (КИИ: отказоустойчивость, резервирование), 63-ФЗ (электронная подпись). Принципы работы с ПДн и коммерческой тайной: минимизация, обезличивание, разграничение доступа, журналирование.
- **Почему файлы — не СУБД** (лекция.md, раздел 3): CSV-хранение не обеспечивает целостность (нет ключей и ограничений), даёт проблемы реализации (парсинг, конкурентный доступ) и не гарантирует устойчивость при сбоях.
- **Типы баз данных** (лекция.md, раздел 2.1): реляционные, документные, графовые, векторные, «ключ-значение», колоночные, временных рядов — выбор зависит от типа данных и нагрузки.
- **СУБД** — ПО, управляющее БД: целостность, транзакции (ACID), конкурентный доступ (MVCC), безопасность, бэкапы, независимость от физического хранения.
- **Реляционная модель (Кодд, 1970)**: структура (отношения, атрибуты, домены), целостность (ограничения), манипуляция (декларативный API). Термины: отношение, кортеж, PK, FK.
- **DML**: процедурные языки (как искать) vs декларативные (что нужно — SQL).
- **Реляционная алгебра** (см. лекция.md, раздел 7): выборка `σ` (строки по предикату), проекция `π` (столбцы), объединение `∪`, пересечение `∩`, разность `−`, декартово произведение `×`, соединение `⋈` (по общим атрибутам), переименование `ρ`, деление `÷` (кортежи, связанные со ВСЕМИ кортежами делителя). Порядок операций влияет на производительность: сначала фильтруем, потом соединяем.

Далее — конспект по моделированию данных (опора семинара №1).

### 1. Процесс моделирования данных (4 шага)

Хорошая документация и чётко определённый процесс делают вас более способными создавать и внедрять решения. Процесс моделирования состоит из 4 этапов:

| Шаг | Название | Результат |
| :---: | :--- | :--- |
| **1** | **Анализ требований** | Понимание бизнеса, выявление сущностей и правил |
| **2** | **Концептуальная модель (ERD)** | Диаграмма сущностей и связей (без атрибутов) |
| **3** | **Логическая модель** | Таблицы, атрибуты, первичные/внешние ключи |
| **4** | **Физическая модель** | SQL-скрипты CREATE TABLE с типами и индексами |

### 2. Анализ требований (шаг 1)

Это **фундаментальная** фаза. Главное — участие заинтересованных лиц (бизнеса). Им не нужно знать, какой тип будет у поля `name`, но **нужно убедиться, что поле `name` действительно необходимо**.

**Шаги анализа требований:**

1. **Понимание проблемы** — цели, ограничения, контекст.
2. **Сбор требований** — интервью, документы, существующие системы.
3. **Анализ и документация** — поиск противоречий, фиксация.
4. **Проверка требований** — только когда мы создаём связи и диаграммы, мы замечаем, что чего-то не хватает.

### 3. Концептуальная модель (шаг 2) — ERD/ERM

Создаётся с помощью диаграмм «сущность-связь» (ERD). Помогает визуализировать сущности и их отношения **без учёта деталей реализации**.

#### 3.1. Сущности (Entities)

**Сущность** — объект реального мира. В таблице — это строка.

- **Абстрактная сущность** — общая концепция без конкретных характеристик (например, «Транспортное средство»).
- **Полная сущность** — конкретный экземпляр с отличительными чертами (например, «Автомобиль», «Мотоцикл»).

**По зависимости:**

- **Сильная сущность** — не зависит от существования другой сущности. (Прямоугольник с одной рамкой).
- **Слабая сущность** — зависит от другой сущности-владельца. Не имеет собственного первичного ключа, идентифицируется через владельца. (Прямоугольник с двойной рамкой).

*Пример:* `Заказ` (сильный) → `Позиция заказа` (слабый, зависит от заказа).

---

#### 3.2. Связи (Relationships)

**Связь** — это то, как сущности общаются и взаимодействуют друг с другом.

**Степени отношений:**

- **Бинарное** — участвуют две сущности (90% случаев).
- **Тройное** — участвуют три сущности.
- **N-арное** — четыре и более сущностей.

**Обозначение мощности (кардинальности):**

Различают **два основных типа мощности**:

- **Минимальная мощность** — сколько **обязательно** должно быть связано.
- **Максимальная мощность** — сколько **может** быть связано.

**Обозначения (стандарт (min, max)):**

| Обозначение | Смысл | Пример |
| :---: | :--- | :--- |
| **(0,1)** | Ноль или один | У клиента может быть не более одного паспорта |
| **(1,1)** | Строго один | У заказа ровно один клиент |
| **(0,N)** | Ноль или более | У клиента может быть много заказов (или ни одного) |
| **(1,N)** | Один или более | У отдела должен быть хотя бы один сотрудник |

**Примеры связей с мощностью:**

- **(1,1) → (1,1)**: Клиент имеет только один адрес, и адрес принадлежит только одному клиенту.
- **(1,1) → (1,N)**: В отделе может быть много сотрудников, но сотрудник работает только в одном отделе.
- **(0,N) → (0,N)**: Студент может посещать много курсов, и курс могут посещать много студентов (M:N).

> **Важно!** Связь **многие-ко-многим (M:N)** всегда требует **соединительной таблицы** (ассоциативной сущности) в реляционной модели.

---

#### 3.3. Атрибуты (Attributes)

**Атрибут** — характеристика сущности (поле таблицы).

**Типы атрибутов:**

| Тип | Описание | Пример |
| :--- | :--- | :--- |
| **Атомарный** | Неделимый, уникальный | ИНН, ID |
| **Составной** | Делится на части | Адрес (улица, город, индекс), Имя (имя, фамилия) |
| **Многозначный** | Может иметь несколько значений | Телефоны, email-адреса |
| **Производный** | Вычисляется из другого атрибута | Возраст ← Дата рождения |
| **Ключевой** | Используется как идентификатор | PK (первичный), FK (внешний) |

На ER-диаграмме атрибуты изображаются как ответвления от прямоугольника сущности (или овалы в нотации Чена).

### 4. Логическая модель (шаг 3)

Логическая модель — это **более детальное представление**, которое переводит концептуальную модель в термины, близкие к физической реализации.

**Что происходит на этом этапе:**

- Сущности → **Таблицы**.
- Атрибуты → **Столбцы**.
- Связи → **Внешние ключи (FK)**.

**Логическая модель НЕ включает:**
- Индексы.
- Конкретные типы данных (только общие: INTEGER, STRING, DATE).
- Ограничения (CHECK, DEFAULT).

**Что включает:**
- Все таблицы.
- Все столбцы с их логическими типами.
- Первичные ключи (PK).
- Внешние ключи (FK) и ссылочную целостность.
- Кардинальность связей (1:1, 1:M, M:N — с указанием промежуточных таблиц).

*Логическая модель служит основой для проектирования запросов и транзакций.*

---

### 5. Физическая модель (шаг 4)

Физическая модель — это **конкретная реализация** в выбранной СУБД (у нас — PostgreSQL).

**Что добавляется:**

- Конкретные типы данных: `VARCHAR(50)`, `INTEGER`, `TIMESTAMP`, `DECIMAL(10,2)`.
- Индексы (`CREATE INDEX ...`).
- Ограничения целостности: `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`.
- Партиционирование, табличные пространства, настройки хранения.

**Результат:**

- SQL-скрипты `CREATE TABLE`.
- Словарь данных (документация по всем полям).
- Схемы в репозитории (Git).

### 6. Сводная таблица трёх моделей

| Характеристика | Концептуальная | Логическая | Физическая |
| :--- | :--- | :--- | :--- |
| **Что?** | Сущности, связи | Таблицы, столбцы, PK/FK | Таблицы + типы данных + индексы |
| **Зависимость от СУБД?** | Нет | Нет | **Да** (PostgreSQL, Oracle) |
| **Для кого?** | Бизнес, аналитики | Разработчики, архитекторы | Администраторы БД, разработчики |
| **Детализация** | Низкая | Средняя | Высокая |
| **Что НЕ содержит?** | Атрибуты, ключи | Индексы, типы данных | Ничего лишнего — готова к деплою |

### 7. Практический пример (сквозной)

**Бизнес-домен:** Система отслеживания привычек.

**Концептуальная модель:**
```
[Контакт] ----< [Цель]
     |               |
     |               |
     ----< [Привычка] ----< [Трекинг]
```

**Логическая модель (таблицы):**

- `contacts` (id, name, surname, email, phone, status)
- `goals` (id, name, description, contact_id, start, end, achieved, status)
- `habits` (id, name, description, contact_id, per_week, per_month, per_year, status)
- `tracking` (id, habit_id, date, level)

**Физическая модель (SQL в PostgreSQL):**

```sql
CREATE TABLE contacts (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    surname VARCHAR(50) NOT NULL,
    email VARCHAR(50) NOT NULL,
    phone VARCHAR(50) NOT NULL,
    status BOOLEAN DEFAULT TRUE NOT NULL
);

CREATE TABLE goals (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    description VARCHAR(150) NOT NULL,
    contact_id INTEGER NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    achieved BOOLEAN DEFAULT FALSE NOT NULL,
    status BOOLEAN DEFAULT TRUE NOT NULL,
    CONSTRAINT fk_goals_contacts FOREIGN KEY (contact_id) REFERENCES contacts(id)
);

CREATE TABLE habits (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    description VARCHAR(150) NOT NULL,
    contact_id INTEGER NOT NULL,
    per_week INTEGER NOT NULL,
    per_month INTEGER NOT NULL,
    per_year INTEGER NOT NULL,
    status BOOLEAN DEFAULT TRUE NOT NULL,
    CONSTRAINT fk_habits_contacts FOREIGN KEY (contact_id) REFERENCES contacts(id)
);

CREATE TABLE tracking (
    id SERIAL PRIMARY KEY,
    habit_id INTEGER NOT NULL,
    tracking_date DATE NOT NULL,
    level BOOLEAN DEFAULT FALSE NOT NULL,
    CONSTRAINT fk_tracking_habits FOREIGN KEY (habit_id) REFERENCES habits(id)
);

-- Индексы для внешних ключей
CREATE INDEX idx_goals_contact_id ON goals(contact_id);
CREATE INDEX idx_habits_contact_id ON habits(contact_id);
CREATE INDEX idx_tracking_habit_id ON tracking(habit_id);
```

### 8. Советы по моделированию

1. **Следуйте процессу** — не пропускайте анализ требований и концептуальную модель.
2. **Документируйте всё** — словарь данных, ER-диаграммы, README.
3. **Проверяйте требования на этапе концептуальной модели** — дешевле исправить на бумаге.
4. **Избегайте M:N напрямую** — всегда создавайте соединительную таблицу.
5. **Именуйте связи глаголами** — «содержит», «оплачивает», «относится к».
6. **На физическом уровне** — всегда добавляйте индексы на внешние ключи.
7. **Храните модели в репозитории** — это часть кодовой базы.

### 9. Ключевые термины (глоссарий)

| Термин | Определение |
| :--- | :--- |
| **Сущность** | Объект реального мира (таблица) |
| **Сильная сущность** | Не зависит от других |
| **Слабая сущность** | Зависит от владельца, нет собственного PK |
| **Связь** | Взаимодействие между сущностями |
| **Бинарная связь** | Между двумя сущностями |
| **Тройная связь** | Между тремя сущностями |
| **Мощность (0,1)** | Ноль или один |
| **Мощность (1,N)** | Один или более |
| **Атомарный атрибут** | Неделимый |
| **Составной атрибут** | Делится на части |
| **Многозначный атрибут** | Может иметь несколько значений |
| **Производный атрибут** | Вычисляется из других данных |
