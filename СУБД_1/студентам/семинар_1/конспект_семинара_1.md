# КРАТКИЙ КОНСПЕКТ (Семинар 1)

## 1. Данные, информация, знания и типы данных

| Понятие | Определение | Пример |
|---------|-------------|--------|
| **Данные** | Сырые факты без интерпретации | `38.5` |
| **Информация** | Данные + контекст + смысл | «Температура 38.5°C» |
| **Знания** | Информация + правила, закономерности, опыт | «Если >39°C два часа – вызвать ветеринара» |

**Типы данных по структурированности:**

| Тип | Характеристика | Примеры | Хранение |
|-----|----------------|---------|----------|
| **Структурированные** | Чёткая схема, строки и столбцы | Таблицы клиентов, заказов | PostgreSQL, MySQL |
| **Слабоструктурированные** | Гибкая структура, может меняться | JSON, XML, логи | PostgreSQL (JSONB), MongoDB |
| **Неструктурированные** | Нет схемы, мультимедиа, текст | Видео, фото, сканы документов | S3/MinIO, файловые системы, Data Lake |

**Полиглотное хранение:** в реальных проектах комбинируют: PostgreSQL – для транзакций, S3 – для файлов, pgvector – для эмбеддингов.

**ПДн (персональные данные):** ФИО, телефон, email, адрес, паспорт, фото.

**Обязанности при работе с ПДн и коммерческой тайной:**
- Минимизировать (не хранить лишнее).
- Обезличивать (ФИО → ID).
- Разграничивать доступ (только уполномоченным).
- Журналировать все действия (кто, когда, что).
- Шифровать при передаче и хранении.

## 3. Карта данных и матрица доступа (для ПР №1 и №2)

**Карта данных** — таблица, где для каждого атрибута указано: источник, сущность, название, тип данных, обязательность, пример и категория (ПДн/коммерческая тайна/открытые).

**Матрица доступа** — таблица, где для каждой роли пользователя перечислены разрешённые операции (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) над сущностями. Обоснование ограничений — ссылки на 152-ФЗ или 149-ФЗ.

Пример ролей: `manager`, `developer`, `analyst`, `auditor`.

## 4. Основы моделирования данных

### Базовые понятия
- **Сущность** – объект (Проект, Задача).  
- **Атрибут** – свойство сущности (столбец).  
- **Связь** – отношение между сущностями.  
- **Мощность (кардинальность)** – сколько экземпляров одной сущности связано с другой.  
- **PK** – первичный ключ (уникальный идентификатор).  
- **FK** – внешний ключ (ссылка на PK другой таблицы).

### Сильные и слабые сущности
- **Сильная** – существует независимо, имеет свой PK (Проект, Сотрудник).  
- **Слабая** – зависит от владельца, не имеет собственного смысла без него (Задача зависит от Проекта, История статуса – от Задачи). В БД часто добавляем суррогатный PK, но сохраняем `ON DELETE CASCADE`.

### Типы атрибутов
- **Атомарный** (неделимый) – `task_id`.  
- **Составной** (делимый) – `address`.  
- **Многозначный** – `tags` (выносится в отдельную таблицу).  
- **Производный** – вычисляется (`days_since_creation`).

## 6. Нотации связей (не смешивать!)

### Crow’s Foot (воронья лапка)
Символ со стороны сущности показывает её участие:

| Символ | Значение | Аналог (min,max) |
|--------|----------|------------------|
| `│`    | Ровно один (обязательно) | `(1,1)` |
| `○`    | Ноль или один | `(0,1)` |
| `<` или `>` | Много (ноль или более) | `(0,N)` |
| `│<`   | Один или более | `(1,N)` |

Пример: `Проект │────○< Задача` → Один проект содержит ноль или много задач.

### Мощность (min, max)
Указывается парой чисел `(min, max)` у каждой сущности.

| Запись | Значение |
|--------|----------|
| `(1,1)` | Ровно один |
| `(0,1)` | Ноль или один |
| `(1,N)` | Хотя бы один |
| `(0,N)` | Ноль или много |

Пример: `Проект (1,1) ——— (0,N) Задача`

## 7. Практические реализации связей (проектная система)

| Связь | Бизнес-правило | Реализация в SQL |
|-------|----------------|------------------|
| **Проект → Задача** (1:N) | Задача не может существовать без проекта | `project_id INTEGER NOT NULL`, `FOREIGN KEY ... ON DELETE CASCADE` |
| **Сотрудник → Задача** (0..1 : 0..N) | Задача может быть без исполнителя | `assignee_id INTEGER` (допускает `NULL`), `FOREIGN KEY ... ON DELETE SET NULL` |
| **Задача ↔ Тег** (M:N) | У задачи много тегов, тег у многих задач | Связующая таблица `task_tags(task_id, tag_id)`, составной PK |
| **Задача → История статуса** (1:N) | Храним аудит изменений | `task_status_history` с `from_status`, `to_status`, `changed_at`, `changed_by`, FK на `tasks` с `CASCADE` |

## 8. Физическая модель: важные моменты

- **Денежные суммы** – `DECIMAL(10,2)`, не `FLOAT`.
- **Индексы** – обязательно на все внешние ключи (`CREATE INDEX idx_... ON table(FK_column)`).
- **ON DELETE CASCADE** – для слабых сущностей (если удаляем заказ – удаляем позиции заказа).  
- **ON DELETE RESTRICT** – если нельзя удалить родителя, пока есть зависимые записи (товар, который есть в заказах).  
- **ON DELETE SET NULL** – при удалении родителя обнуляем FK (увольнение сотрудника не удаляет задачи).
- **CHECK-ограничения** – кодируют бизнес-правила (`CHECK (deadline >= start_date)`, `CHECK (price >= 0)`).

## 10. Шпаргалка по ПДн и коммерческой тайне (практическое задание)

- **ПДн** – ФИО, телефон, адрес, email, паспорт, фото.
- **Коммерческая тайна** – списки клиентов, цены, договоры, технологии.
- **Что делать:**
  - Минимизировать сбор.
  - Обезличивать (заменять на ID).
  - Разграничивать доступ (роли, GRANT/REVOKE).
  - Журналировать (`audit_log` таблица или `task_status_history`).
  - Шифровать данные при передаче и хранении.
- **Для матрицы доступа:** указывать, какие роли имеют `SELECT`, `INSERT`, `UPDATE`, `DELETE` к таблицам, содержащим ПДн или коммерческую тайну, и ссылаться на ст. 7 152-ФЗ (конфиденциальность) и ст. 19 152-ФЗ (меры защиты).
