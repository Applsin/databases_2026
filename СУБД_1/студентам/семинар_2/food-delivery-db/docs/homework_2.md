# ДЗ №2 — расширение модели Food Delivery

## Новые таблицы

| Таблица | Назначение | PK | FK | Основные ограничения |
|---|---|---|---|---|
| `categories` | справочник категорий блюд | `category_id` | — | `NOT NULL`, `UNIQUE(name)` |
| `dish_categories` | связь блюд с категориями | `(dish_id, category_id)` | `dish_id -> dishes`, `category_id -> categories` | `NOT NULL`, составной PK |

## Реализация M:N

Между `dishes` и `categories` существует логическое отношение M:N: одно блюдо может иметь несколько категорий, а одна категория — несколько блюд.

Оно реализовано промежуточной таблицей `dish_categories`:

`dishes 1:N dish_categories N:1 categories`.

Составной PK `(dish_id, category_id)` запрещает повторение одной пары.

## Целостность

Используются:
- `PRIMARY KEY`;
- `FOREIGN KEY`;
- `NOT NULL`;
- `UNIQUE`;
- `CHECK`;
- `DEFAULT`.

Для `dish_categories` оба FK используют `ON DELETE CASCADE`.

Если удалить блюдо, удаляются его связи с категориями. Если удалить категорию, удаляются её связи с блюдами. Сами связанные сущности другого типа не удаляются.

`DROP TABLE categories CASCADE` действует иначе: он удаляет объект таблицы и зависимости от него на уровне схемы базы данных.

## Индексы

Индексы проверены относительно частых запросов ДЗ №1 и новых запросов.

| Запрос | Индекс |
|---|---|
| активные рестораны с рейтингом > 4.5 | `idx_restaurants_active_rating` |
| блюда за последние 7 дней | `idx_orders_created_at` |
| выручка ресторана за месяц | `idx_orders_restaurant_status_created_at` |
| доставки по курьеру | `idx_orders_courier_status` |
| блюда выбранной категории | `idx_dish_categories_category_id` |
| частые FK JOIN | индексы на соответствующих FK |

`PRIMARY KEY (dish_id, category_id)` уже эффективно поддерживает поиск по `dish_id`; отдельный индекс по `category_id` нужен для обратного направления связи.

На маленьких тестовых таблицах PostgreSQL может выбрать `Seq Scan`, даже при наличии подходящего индекса, потому что полный просмотр нескольких строк дешевле. Наличие и потенциальное использование индексов проверяется через `EXPLAIN (ANALYZE, BUFFERS)`.

## Демонстрация нарушений

`sql/03_constraint_violations.sql` демонстрирует:
- нарушение `UNIQUE`;
- нарушение `FOREIGN KEY`;
- нарушение `CHECK`;
- нарушение составного PK M:N;
- работу `ON DELETE CASCADE`.

Ошибки перехватываются внутри `DO ... EXCEPTION`, поэтому скрипт можно запускать целиком.
