
**Транзакция** — это логическая единица работы, состоящая из одной или нескольких операций с базой данных, которая переводит данные из одного согласованного состояния в другое. Транзакция обладает свойствами **ACID**:

- **Атомарность (Atomicity)** — либо все операции выполняются полностью, либо ни одна (откат при ошибке).
    
- **Согласованность (Consistency)** — транзакция не нарушает целостность данных и бизнес-правила.
    
- **Изолированность (Isolation)** — параллельно выполняемые транзакции не должны влиять друг на друга (степень влияния регулируется уровнем изоляции).
    
- **Долговечность (Durability)** — после фиксации (COMMIT) результат сохраняется даже при сбоях системы.
    

В PostgreSQL транзакция начинается с `BEGIN` (или неявно при первом запросе вне транзакции) и завершается `COMMIT` или `ROLLBACK`.

## 1. XID и CLOG

- **XID (Transaction ID)** — уникальный идентификатор транзакции.
  - Выдаётся **только при первом изменении данных** (INSERT/UPDATE/DELETE) или вызове `txid_current()`.  
  - `BEGIN; SELECT 1; COMMIT;` XID **не получает**.
- XID — 32-битный, зацикливается → **проблема wraparound**. Старые строки замораживаются (`FrozenTransactionId`) при помощи Autovacuum. Долгие транзакции мешают заморозке → **правило: короткие транзакции**.
- **CLOG (Commit Log)** — массив по 2 бита на транзакцию в `pg_xact`:
  - `00` – IN_PROGRESS
  - `01` – COMMITTED
  - `10` – ABORTED
  - `11` – SUBCOMMITTED

При чтении: берём `xmin` / `xmax` строки → CLOG → видимость по статусу и снапшоту.

## 2. MVCC и блокировки

- **MVCC** — одновременные версии строк. Читатели видят снапшот данных, **не блокируют и не блокируются** писателями (если нет `FOR UPDATE`).
- Проблема **Lost Update**: две транзакции прочитали одно значение, увеличили, записали — результат первой потерян.
- Два способа борьбы:
  - **Пессимистичный** – явная блокировка `SELECT ... FOR UPDATE`.
  - **Оптимистичный** – колонка `version`, обновление с проверкой.

## 3. Уровни изоляции

В PostgreSQL фактическое поведение (отличия от стандарта **выделены**):

| Уровень                 | Dirty Read | Non‑repeatable Read | Phantom Read | Lost Update (без доп. мер) |
|-------------------------|------------|---------------------|--------------|---------------------------|
| READ UNCOMMITTED (PG)   | ✗ (1)      | ✓                   | ✓            | ✓                         |
| READ COMMITTED (по ум.) | ✗          | ✓                   | ✓            | ✓                         |
| REPEATABLE READ         | ✗          | ✗                   | ✗ (2)        | ✓                         |
| SERIALIZABLE            | ✗          | ✗                   | ✗            | ✗                         |

*(1) В стандарте Dirty Read возможен, PostgreSQL повышает до Read Committed.*  
*(2) В стандарте Phantom Read возможен, в PG закрыт благодаря snapshot isolation.*

**Как работает снапшот:**
- Read Committed – новый снапшот **на каждый оператор**.
- Repeatable Read – один снапшот **на первый оператор** (не на `BEGIN`).
- Serializable – снапшот + отслеживание зависимостей (SSI). При конфликте – `serialization failure`.

## 4. Пессимистичная блокировка (`SELECT ... FOR UPDATE`)

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;  -- блокирует строку
-- другие транзакции, пытающиеся FOR UPDATE или UPDATE этой строки, ЖДУТ
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

- Обычный `SELECT` (без `FOR UPDATE`) **не блокируется** – видит закоммиченную версию.
- Обязательно устанавливайте `lock_timeout`:
  ```sql
  SET LOCAL lock_timeout = '2s';
  ```

**Python (SQLAlchemy) – пример:**
```python
with engine.begin() as conn:
    conn.execute(text("SET LOCAL lock_timeout = '2s'"))
    row = conn.execute(
        text("SELECT balance FROM accounts WHERE id = :id FOR UPDATE"),
        {"id": 1}
    ).fetchone()
    # ... обновление
```

## 5. Оптимистичная блокировка (по версии)

Таблица:
```sql
CREATE TABLE seminar_tickets (
    id INT PRIMARY KEY,
    status TEXT,
    version INT DEFAULT 0
);
```

Алгоритм:
1. Читаем `status, version` без блокировок.
2. Пытаемся обновить с условием совпадения версии:
   ```sql
   UPDATE seminar_tickets 
   SET status = 'booked_by_'||:user, version = version + 1
   WHERE id = :id AND version = :old_version;
   ```
3. Если `affected rows = 0` → конфликт, надо повторить (или сообщить «занято»).

**Python-фрагмент:**
```python
row = conn.execute(text("SELECT status, version FROM seminar_tickets WHERE id = :id"), {...}).fetchone()
res = conn.execute(text("""
    UPDATE seminar_tickets SET status = :new, version = version + 1
    WHERE id = :id AND version = :ver
"""), {"new": ..., "id": id, "ver": row[1]})
if res.rowcount == 0:
    print("Conflict, retry")
```

Плюс: нет блокировок, высокая пропускная способность.  
Минус: нужны повторные попытки при конфликтах.

## 6. Deadlock (взаимная блокировка)

**Причина:** Т1 держит строку А, ждёт строку Б; Т2 держит Б, ждёт А.  
PostgreSQL автоматически находит цикл и откатывает одну из транзакций с ошибкой `deadlock detected`.

**Как избежать:**
- Блокировать ресурсы **всегда в одном порядке**.
- Использовать `lock_timeout`, чтобы не висеть вечно.

**Мониторинг блокировок:**
```sql
SELECT blocked.pid, blocking.pid,
       blocked.query, blocking.query
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.wait_event IS NOT NULL;
```

## 7. Распределённые транзакции (кратко)

- **2PC (Two-Phase Commit)**: Prepare → Commit/Rollback. Уязвим к падению координатора, блокировки висят.  Есть еще многофазные коммиты, но там сложность сильно возрастает.
- **Saga**: цепочка локальных транзакций + компенсации. Eventual Consistency, система всегда доступна. 
	- **Оркестрация (Orchestration)** — централизованный подход.  
    Есть выделенный координатор (оркестратор), который по очереди вызывает нужные сервисы, принимает решения и запускает компенсирующие действия при ошибках.
    
	- **Хореография (Choreography)** — децентрализованный (распределённый) подход.  
    Нет единого центра. Каждый сервис сам знает, какое событие опубликовать после выполнения своей локальной транзакции, и на какие события подписываться для выполнения своего шага. Поток событий передаётся через брокер (Kafka, RabbitMQ и т.п.).

---

## 8. Практические правила

1. Транзакции – максимально короткие. Не ждать ввода пользователя.
2. Всегда одинаковый порядок блокировок.
3. Длинную аналитику – на реплику; если на основной базе нужен стабильный snapshot без serialization failure – `SERIALIZABLE READ ONLY DEFERRABLE`.
4. `FOR UPDATE` – только там, где реально нужно (списание, бронирование).
5. На Repeatable Read и Serializable – обязательно обрабатывать `serialization failure` с повтором.
