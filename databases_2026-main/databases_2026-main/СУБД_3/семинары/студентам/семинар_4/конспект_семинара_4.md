## 1. Фильтрация и сортировка

**Полуоткрытый диапазон дат** — стандарт фильтрации по таймстампам: правая граница строгая (`<`), иначе `BETWEEN '...08-01' AND '...08-31'` отсечёт рейсы 31.08 после 00:00.

```sql
-- Выполненные рейсы из московских аэропортов за август 2017 (1 913 строк)
SELECT flight_no, departure_airport, actual_departure
FROM flights
WHERE status = 'Arrived'
  AND departure_airport IN ('SVO', 'DME', 'VKO')
  AND actual_departure >= '2017-08-01'
  AND actual_departure <  '2017-09-01'
ORDER BY actual_departure;
-- Альтернатива списку кодов: IN (SELECT airport_code FROM airports WHERE city = 'Moscow')
```

**Трёхзначная логика и NULL.** Предикат с `NULL` даёт `NULL`, а не `TRUE`, поэтому строки с пустым `actual_arrival` (отменённые рейсы) сами выпадают из `WHERE`. Явные проверки пишутся только так: `IS NULL` / `IS NOT NULL` (не `= NULL!`), сравнение с учётом NULL — `IS DISTINCT FROM`.

```sql
-- Рейсы с опозданием более 2 часов (2 394 строки; рекорд — 281 мин)
SELECT flight_no, scheduled_arrival, actual_arrival,
       ROUND(EXTRACT(EPOCH FROM (actual_arrival - scheduled_arrival)) / 60) AS delay_min
FROM flights
WHERE actual_arrival > scheduled_arrival + INTERVAL '2 hours'
ORDER BY delay_min DESC;
-- Разность таймстампов = интервал; EXTRACT(EPOCH FROM ...) — секунды, делим на 60.
```

**Шаблоны LIKE.** `%` — любая последовательность, `_` — один символ. Префиксный шаблон `'PG04%'` потенциально умеет в индекс, шаблон с начальным `%` ('%77') — никогда (только Seq Scan).

```sql
-- Сколько рейсов выполнено каждым номером PG04xx (9 715 рейсов, 100 номеров)
SELECT flight_no, COUNT(*) AS flights_cnt
FROM flights
WHERE flight_no LIKE 'PG04%'
GROUP BY flight_no
ORDER BY flight_no;
-- Альтернативы: LEFT(flight_no, 4) = 'PG04' (не sargable), flight_no ~ '^PG04' (regex)
```

## 2. Группировки: одна и несколько колонок, HAVING

Порядок логических этапов: `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`. `HAVING` — единственный фильтр, видящий результат агрегатов.

```sql
-- Среднее опоздание по аэропортам с >500 рейсов (28 аэропортов; топ — CEK ~15,9 мин)
SELECT departure_airport, COUNT(*) AS flights_cnt,
       ROUND(AVG(EXTRACT(EPOCH FROM (actual_arrival - scheduled_arrival)) / 60), 1) AS avg_delay_min
FROM flights
WHERE actual_arrival IS NOT NULL          -- AVG игнорирует NULL, а COUNT(*) — нет: фильтр в WHERE
GROUP BY departure_airport
HAVING COUNT(*) > 500
ORDER BY avg_delay_min DESC;
```

**Группировка по паре колонок** = пара «откуда → куда». **Условная агрегация** `FILTER (WHERE ...)` — «сколько всего / сколько из них»; вариант без FILTER: `COUNT(CASE WHEN ... THEN 1 END)`. Множитель `100.0` (не `100`) — иначе целочисленное деление.

```sql
-- Пары аэропортов с >=100 рейсами: число рейсов, отмен и процент отмен
SELECT departure_airport, arrival_airport, COUNT(*) AS total_flights,
       COUNT(*) FILTER (WHERE status = 'Cancelled') AS cancelled,
       ROUND(100.0 * COUNT(*) FILTER (WHERE status = 'Cancelled') / COUNT(*), 2) AS pct_cancelled
FROM flights
GROUP BY departure_airport, arrival_airport
HAVING COUNT(*) >= 100
ORDER BY pct_cancelled DESC, total_flights DESC;   -- второй ключ — детерминированный порядок
```

**Многоуровневые итоги через ROLLUP** — сводная таблица «как в Excel» за один проход: помесячные суммы + общий итог (итоговая строка помечена `NULL` в колонке группировки).

```sql
-- Выручка по месяцам 2017 + итог (47 004 388 200; август — 13 517 932 000)
SELECT date_trunc('month', f.scheduled_departure)::date AS month, SUM(tf.amount) AS revenue
FROM flights f
JOIN ticket_flights tf ON tf.flight_id = f.flight_id
GROUP BY ROLLUP (1)
ORDER BY month;                 -- итоговая строка с month = NULL встанет последней
-- Функция GROUPING(month) = 1 помечает итоговую строку — удобно вывести 'ИТОГО'.
-- Альтернативы: GROUPING SETS ((month), ()) или UNION ALL двух запросов.
```

## 3. Соединения таблиц (JOIN)

```sql
-- Топ-10 самых дорогих билетов (рекорд 203 300,00; Москва ↔ Петропавловск)
SELECT t.passenger_name, tf.amount, f.flight_no,
       dep.city AS departure_city, arr.city AS arrival_city
FROM tickets t
JOIN ticket_flights tf ON tf.ticket_no = t.ticket_no
JOIN flights f         ON f.flight_id = tf.flight_id
JOIN airports dep      ON dep.airport_code = f.departure_airport
JOIN airports arr      ON arr.airport_code = f.arrival_airport
ORDER BY tf.amount DESC
LIMIT 10;
-- Одна таблица (airports) подключена дважды — алиасы dep/arr обязательны.
-- В плане: цепочка Hash Join'ов — норма для много табличного запроса.
```

**LEFT JOIN + COUNT(колонка)** — паттерн «покажи всех, даже без событий», и его главная ловушка: `COUNT(*)` после `LEFT JOIN` вернёт минимум 1 (строка левой таблицы остаётся даже без совпадений), поэтому считаем по колонке правой таблицы.

```sql
-- Все аэропорты с числом вылетающих рейсов (104 аэропорта; минимум — USK, 34)
SELECT a.airport_code, a.airport_name, COUNT(f.flight_id) AS flights_cnt
FROM airports a
LEFT JOIN flights f ON f.departure_airport = a.airport_code
GROUP BY a.airport_code, a.airport_name
ORDER BY flights_cnt;
-- Контраст: INNER JOIN потерял бы аэропорты без рейсов.
```

**Группируйте по ключу, а не по подписи.** Группировка только по `passenger_name` склеила бы одноимённых: условный ALEKSANDR IVANOV «купил» бы 5 458 билетов.

```sql
-- Топ-5 пассажиров по тратам (лидеры — 6 перелётов, ≈530 тыс.)
SELECT t.passenger_id, t.passenger_name, COUNT(*) AS flights_cnt, SUM(tf.amount) AS total_spent
FROM tickets t
JOIN ticket_flights tf ON tf.ticket_no = t.ticket_no
GROUP BY t.passenger_id, t.passenger_name
ORDER BY total_spent DESC
LIMIT 5;
```

## 4. Как мыслит оптимизатор: Методы доступа к данным

Когда вы пишете `SELECT`, PostgreSQL выбирает, как физически прочитать данные. В нижней части плана `EXPLAIN` всегда виден узел сканирования:

| Метод доступа | Как работает | Когда выбирается оптимизатором |
| :--- | :--- | :--- |
| **Seq Scan** | Полное последовательное чтение всей таблицы. | Таблица маленькая, или запрос запрашивает большую часть данных (низкая селективность). |
| **Index Scan** | Поиск в индексе, затем обращение к таблице за данными строки. | Высокая селективность (запрос возвращает очень малое количество строк). |
| **Bitmap Scan** | Строит в памяти битовую карту нужных страниц, затем читает только их. | Средняя селективность. Позволяет комбинировать несколько индексов. |
| **Index Only Scan** | Данные берутся только из индекса, без обращения к таблице. | Все запрашиваемые поля входят в индекс, а страницы обновлены `VACUUM` (Visibility Map). |

> **Красный флаг:** Если вы видите `Seq Scan` на таблице с миллионами строк, а запрос возвращает 5 строк — индекс отсутствует или запрос написан неоптимально (non-sargable).

## 5. Sargability (Search Argument Able)

**Правило:** Если вы применяете функцию к колонке в блоке `WHERE`, СУБД не может использовать индекс по этой колонке.

❌ **Non-Sargable:**
```sql
WHERE EXTRACT(MONTH FROM scheduled_departure) = 8 
  AND EXTRACT(YEAR FROM scheduled_departure) = 2017
-- Принудит СУБД сканировать всю таблицу (Seq Scan).
```

✅ **Sargable:**
```sql
WHERE scheduled_departure >= '2017-08-01' 
  AND scheduled_departure <  '2017-09-01'
-- Позволяет использовать Index Scan.
```

## 6. Оконные функции: Управление рамкой (RANGE vs ROWS)

По умолчанию в оконных функциях с `ORDER BY` используется рамка `RANGE`, которая заставляет PostgreSQL искать дубликаты в окне. Это медленно.

**Паттерн: Скользящий итог / среднее с CTE и `ROWS`**
Сначала агрегируем данные (уменьшаем объем), затем применяем оконную функцию с явной рамкой `ROWS`.

```sql
WITH daily_data AS (
    SELECT scheduled_departure::date AS flight_date,
           SUM(amount) AS daily_revenue
    FROM flights f JOIN ticket_flights tf ON f.flight_id = tf.flight_id
    WHERE f.scheduled_departure >= '2017-08-01' AND f.scheduled_departure < '2017-09-01'
    GROUP BY 1
)
SELECT flight_date, daily_revenue,
       SUM(daily_revenue) OVER (
           ORDER BY flight_date 
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM daily_data;
```

## 7. CTE и инлайнинг (PostgreSQL 12+)

По умолчанию CTE (конструкция `WITH`) встраиваются (inlined) в основной запрос. Но иногда нужно заставить СУБД выполнить подзапрос **ровно один раз** и сохранить результат в памяти.

**Паттерн: MATERIALIZED**
Используется, когда тяжелая агрегация не должна пересчитываться для каждой строки внешнего запроса.
```sql
WITH route_stats AS MATERIALIZED (
    SELECT departure_airport, arrival_airport, AVG(amount) AS avg_route_price
    FROM flights f JOIN ticket_flights tf ON f.flight_id = tf.flight_id
    GROUP BY departure_airport, arrival_airport
)
SELECT ... FROM flights f JOIN route_stats rs ON ...;
```
*В плане выполнения появится узел `CTE Scan`.*

## 8. Стратегии соединения таблиц (Join Strategies)

При выполнении `JOIN` или `LATERAL` PostgreSQL использует один из трех алгоритмов:

1. **Nested Loop (Вложенные циклы):** Для каждой строки внешней таблицы ищет совпадения во внутренней. **Быстр**, если внешняя таблица маленькая, а внутренняя проиндексирована.
2. **Hash Join (Хэширование):** Меньшая таблица полностью считывается и хэшируется в памяти. Затем сканируется внешняя таблица. Идеально для больших таблиц без индексов (требует память `work_mem`).
3. **Merge Join (Слияние):** Обе таблицы сортируются по ключу, а затем сливаются. Используется, если данные уже отсортированы.

### Паттерн: LATERAL JOIN для Top-N задач
Оконные функции (`RANK()`) требуют сортировки *всех* строк для вычисления ранга. `LATERAL` работает как `Nested Loop`: для каждой строки внешней таблицы (в нашем случае — для каждого из трёх аэропортов) он читает билеты по индексу `(flight_id, amount DESC)` уже в порядке убывания цены, а `LIMIT 3` отбрасывает всё лишнее на лету — ранжировать все билеты не нужно.

```sql
SELECT ta.departure_airport, lt.flight_id, lt.amount
FROM top_airports ta
CROSS JOIN LATERAL (
    SELECT f.flight_id, tf.amount
    FROM flights f JOIN ticket_flights tf ON f.flight_id = tf.flight_id
    WHERE f.departure_airport = ta.departure_airport
    ORDER BY tf.amount DESC
    LIMIT 3
) AS lt;
```
*Разница в скорости на демо-базе: ~900 ms (RANK) против ~400 ms (LATERAL с индексом `idx_tf_flight_amount`; с дополнительным индексом по `flights(departure_airport)` — ~300 ms). Разрыв растёт вместе с размером таблицы: оконный вариант обрабатывает все билеты, LATERAL останавливается на трёх лучших в каждой группе.*

## 9. Статистика и почему оптимизатор ошибается

Оптимизатор строит план на основе **статистики** (гистограмм распределения данных), которую собирает фоновый процесс `autovacuum`. 

**Как обнаружить ошибку:**
Если в `EXPLAIN ANALYZE` вы видите: `rows=1 ... (actual rows=100000)`, значит статистика врет. Планировщик ожидал 1 строку, а по факту обработал 100 тысяч. Из-за этого мог быть выбран `Nested Loop` вместо `Hash Join`, и запрос "повис".

**Как лечить:**
1. Обновить статистику вручную: `ANALYZE table_name;`
2. Если данные распределены неравномерно, увеличить точность гистограммы:
   ```sql
   ALTER TABLE flights ALTER COLUMN status SET STATISTICS 1000;
   ANALYZE flights;
   ```

## 10. Шпаргалка по домашнему заданию (Edge Cases)

1. **ANTI-JOIN (`NOT IN` vs `NOT EXISTS`):**
   - `NOT IN` опасен. Если в подзапросе вернется хотя бы один `NULL`, результат всего запроса станет пустым из-за трехзначной логики SQL.
   - `NOT EXISTS` безопасен и преобразуется в эффективный `Hash Anti Join`.
2. **Index Only Scan (Покрывающие индексы):**
   - Чтобы СУБД не ходила в таблицу, все запрашиваемые поля должны быть в индексе: `CREATE INDEX idx ON table (col_a) INCLUDE (col_b);`
   - Работает только если `VACUUM` обновил **Visibility Map** (страницы таблицы помечены как полностью видимые). Если `Heap Fetches > 0` в плане, значит СУБД все равно ходила в таблицу проверять видимость строк.
