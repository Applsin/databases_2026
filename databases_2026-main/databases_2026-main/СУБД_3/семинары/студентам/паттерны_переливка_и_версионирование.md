# Паттерны надёжной переливки данных и версионирования в PostgreSQL

Файл объединяет две родственные группы паттернов:

- **Переливка данных** — как изменить схему или перенести данные в работающей системе без простоя и без потерь: *Expand/Contract*, *Dual Writes*, *Backfill*, *CDC по WAL*, *Transactional Outbox*, *Inbox*, *Retry with Backoff*.
- **Версионирование данных** — как хранить историю изменений: *history-таблицы*, *temporal/bi-temporal*, *soft delete*, *event sourcing*, *SCD*, *снапшоты*.

---

# Часть 1. Переливка данных

## 1.1. Expand/Contract (миграция схемы без простоя)

### Суть

Никогда не менять схему и данные одним шагом. Сначала схема **расширяется** (новое добавляется рядом со старым), затем после перевода всех читателей/писателей — **сужается** (старое удаляется). Каждый шаг обратно совместим и откатываем.

### Схема работы

```
Шаг 1. EXPAND     Шаг 2. DUAL WRITE     Шаг 3. BACKFILL      Шаг 4. SWITCH    Шаг 5. CONTRACT
┌──────────────┐  ┌──────────────┐      ┌──────────────┐     ┌────────────┐   ┌──────────────┐
│ Создаём новую│  │ Приложение   │      │ Дозаполняем  │     │ Чтение     │   │ Удаляем      │
│ колонку/     │  │ пишет И в    │      │ новую колонку│ ──► │ переведено │─► │ старую       │
│ таблицу      │  │ старую, И в  │      │ из старой    │     │ на новую   │   │ колонку      │
│ (ничего не   │  │ новую        │      │ (батчами)    │     │ схему      │   │              │
│ ломаем)      │  │              │      │              │     │            │   │              │
└──────────────┘  └──────────────┘      └──────────────┘     └────────────┘   └──────────────┘
```

### Пример: NOT NULL колонка без блокировки

```sql
-- EXPAND: без DEFAULT и без NOT NULL (мгновенно)
ALTER TABLE orders ADD COLUMN delivery_type text;

-- BACKFILL: NOT NULL через NOT VALID-constraint (без долгой блокировки)
ALTER TABLE orders ADD CONSTRAINT delivery_type_nn
    CHECK (delivery_type IS NOT NULL) NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT delivery_type_nn;      -- скан без блокировки записи
ALTER TABLE orders ALTER COLUMN delivery_type SET NOT NULL;   -- теперь быстро
ALTER TABLE orders DROP CONSTRAINT delivery_type_nn;
```

## 1.2. Dual Writes + Backfill

### Суть

На время миграции приложение пишет **в обе структуры** (старую и новую), а исторические данные догоняются фоновым **backfill**'ом батчами.

```sql
-- Backfill батчами — НЕ одним UPDATE на 100 млн строк
DO $$
DECLARE rows_updated int;
BEGIN
    LOOP
        UPDATE orders SET delivery_type = 'standard'
        WHERE ctid IN (
            SELECT ctid FROM orders
            WHERE delivery_type IS NULL LIMIT 10000
        );
        GET DIAGNOSTICS rows_updated = ROW_COUNT;
        EXIT WHEN rows_updated = 0;
        COMMIT;                -- фиксируем батч, отпускаем блокировки
        PERFORM pg_sleep(0.1);
    END LOOP;
END $$;
```

### Недостаток

Dual writes **неатомарны**: приложение упало между двумя записями — данные разъехались. Нужны сверки (reconciliation job) или замена на CDC/Outbox (ниже).

## 1.3. CDC по WAL: репликация данных в другие таблицы и системы

### Суть

PostgreSQL пишет все изменения в **WAL (Write-Ahead Log)**. Механизм **логического декодирования** превращает WAL в поток логических изменений (какая строка, какой таблицы, старое/новое значение). Консьюмер читает этот поток и применяет изменения **в другую таблицу/базу/систему** — витрину, поисковый индекс, аналитическое хранилище, другую таблицу в той же БД.

### Схема работы

```
PRIMARY ──WAL──► [replication slot + logical decoding]
                      │  поток: INSERT/UPDATE/DELETE с old/new
                      ▼
              ┌───────────────┐     ┌────────────────┐
              │   Консьюмер   │ ──► │ целевые таблицы│
              │ (Debezium,    │     │ / Kafka /      │
              │  свой worker) │     │  Elastic / DWH │
              └───────────────┘     └────────────────┘
```

### Пример: чтение изменений прямо из PostgreSQL

```sql
-- Создать слот с плагином вывода (wal2json / pgoutput / test_decoding)
SELECT * FROM pg_create_logical_replication_slot('cdc_slot', 'test_decoding');

-- Посмотреть изменения БЕЗ подтверждения (peek)
SELECT * FROM pg_logical_slot_peek_changes('cdc_slot', NULL, NULL);

-- Получить изменения и ПОДТВЕРДИТЬ (get) — слот сдвигается, WAL может быть освобождён
SELECT * FROM pg_logical_slot_get_changes('cdc_slot', NULL, NULL);

-- Мониторинг: сколько WAL удерживает слот (опасность заполнения диска!)
SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;
```

### Три способа построить CDC — сравнение

| Способ | Источник истины | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Триггеры** в audit-таблицу | сама БД, в транзакции | просто, атомарно с записью | нагрузка на запись, логика в БД |
| **Polling** по `updated_at` | периодический SELECT | не требует инфраструктуры | не видит DELETE, пропускает быстрые изменения |
| **Logical decoding по WAL** | WAL | видит ВСЁ, включая DELETE; ноль нагрузки на таблицы | нужен консьюмер; слот копит WAL при простое |

### Проблемы, которые решает

1. Переливка в другую систему **без нагрузки на боевые таблицы** и без dual writes в коде.
2. Гарантированно полный поток изменений (WAL — единственный источник истины в PostgreSQL).
3. Поддержка топологий «одна БД → много витрин».

### Недостатки

1. Остановленный консьюмер = слот копит WAL до **переполнения диска primary** — мониторинг обязателен.
2. Консьюмер должен сам решать идемпотентность и порядок (см. Inbox ниже).
3. DDL (изменения схемы) не реплицируются логическим декодированием — их надо синхронизировать отдельно.

## 1.4. Transactional Outbox (транзакционный исходящий ящик)

### Когда применять

- Приложение должно **атомарно** изменить данные И отправить событие/записать в другое место (Kafka, другая таблица, внешний API). Двойная запись «сначала в БД, потом в брокер» неатомарна: между шагами приложение может упасть.

### Суть

В **одной транзакции** с бизнес-записью пишется строка в специальную таблицу `outbox`. Отдельный процесс (**relay**) читает outbox, доставляет событие в целевое место и **только после успешной доставки** ставит пометку об обработке (`processed_at`). При падении relay строки остаются непомеченными и будут доставлены повторно — это гарантия **at-least-once**.

### Схема работы

```
┌─── Транзакция приложения ───────────┐
│  UPDATE orders SET status = 'paid'  │
│  INSERT INTO outbox (event...)      │   ← атомарно: либо обе, либо ни одной
└─────────────────────────────────────┘
                  │
                  ▼
        ┌──────────────────┐   доставка   ┌────────────────┐
        │   Outbox relay   │ ───────────► │ Kafka / другая │
        │ (фоновый worker) │              │ таблица / API  │
        └────────┬─────────┘              └────────────────┘
                 │  только после УСПЕХА:
                 ▼
        UPDATE outbox SET processed_at = now() WHERE id = ...
```

### Реализация в PostgreSQL

```sql
CREATE TABLE outbox (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_id  bigint      NOT NULL,      -- например, order_id
    event_type    text        NOT NULL,      -- 'order_paid'
    payload       jsonb       NOT NULL,      -- тело события
    created_at    timestamptz NOT NULL DEFAULT now(),
    processed_at  timestamptz                -- NULL = ещё не доставлено
);
CREATE INDEX ON outbox (id) WHERE processed_at IS NULL;  -- частичный индекс по необработанным

-- В бизнес-транзакции:
BEGIN;
UPDATE orders SET status = 'paid' WHERE order_id = 42;
INSERT INTO outbox (aggregate_id, event_type, payload)
VALUES (42, 'order_paid', '{"order_id": 42, "status": "paid"}');
COMMIT;

-- Relay забирает пачку событий с блокировкой строк (не мешая другим relay):
SELECT id, event_type, payload FROM outbox
WHERE processed_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;

-- После успешной доставки:
UPDATE outbox SET processed_at = now() WHERE id = ANY(:delivered_ids);
```

Вариант вместо polling: relay читает outbox через **логическое декодирование WAL** (Debezium Outbox Event Router) — тогда таблицу можно сразу очищать (`TRUNCATE`-подобно), а события попадают в брокер из потока WAL.

Для пробуждения relay без постоянного polling удобен `LISTEN/NOTIFY` (с осторожностью: уведомления доставляются только после COMMIT и не персистентны).

### Проблемы, которые решает

1. **Атомарность** бизнес-записи и события — нет окна, где данные записаны, а событие потеряно.
2. Доставка переживает падения приложения и брокера.
3. Развязывает OLTP и интеграции: бизнес-транзакция не ждёт внешнюю систему.

### Недостатки

1. **At-least-once = дубли.** Консьюмер обязан быть идемпотентным (см. Inbox).
2. Задержка доставки (пока сработает relay) — не для синхронных сценариев.
3. Нужна ротация outbox (удалять/архивировать обработанные строки, лучше партициями).
4. Порядок событий гарантируется только в пределах ключа упорядочивания (обычно `aggregate_id`).

## 1.5. Inbox (идемпотентный консьюмер)

### Суть

Зеркальный паттерн для Outbox: консьюмер перед обработкой события записывает его `id` в таблицу `inbox` (в той же транзакции, что и бизнес-эффект). Повторная доставка того же `id` — отклоняется уникальным ключом.

```sql
CREATE TABLE inbox (
    event_id     uuid PRIMARY KEY,          -- уникальный ключ идемпотентности
    received_at  timestamptz NOT NULL DEFAULT now()
);

BEGIN;
INSERT INTO inbox (event_id) VALUES (:event_id);   -- дубль → ошибка уникальности → пропуск
-- ... бизнес-обработка события ...
COMMIT;
```

Outbox (на стороне отправителя) + Inbox (на стороне получателя) вместе дают **effectively-once** обработку поверх ненадёжного транспорта.

## 1.6. Retry with Backoff — обязательный спутник переливок

Любая фоновая переливка встретит deadlock'и (`40P01`), serialization failure (`40001`), таймауты. Паттерн: повторять с экспоненциальной задержкой и «джиттером», внутри транзакции — `SAVEPOINT` для точечного отката.

```python
import time, random
def with_retry(fn, max_attempts=5):
    for attempt in range(max_attempts):
        try:
            return fn()
        except RetryableError:                      # 40001, 40P01...
            if attempt == max_attempts - 1: raise
            time.sleep(min(2 ** attempt, 30) + random.uniform(0, 1))
```

# Часть 2. Версионирование данных

## 2.1. History-таблица через триггер

Самый распространённый способ аудита: перед UPDATE/DELETE снимок старой строки кладётся в отдельную таблицу.

```sql
CREATE TABLE orders_history (
    history_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id    bigint NOT NULL,
    data        jsonb NOT NULL,            -- снимок строки ДО изменения
    changed_at  timestamptz NOT NULL DEFAULT now(),
    changed_by  text NOT NULL DEFAULT current_user,
    operation   char(1) NOT NULL           -- 'U' / 'D'
);

CREATE OR REPLACE FUNCTION save_order_version() RETURNS trigger AS $$
BEGIN
    INSERT INTO orders_history(order_id, data, operation)
    VALUES (OLD.order_id, to_jsonb(OLD), TG_OP::char(1));
    RETURN COALESCE(NEW, OLD);
END $$ LANGUAGE plpgsql;

CREATE TRIGGER trg_orders_versioning
    BEFORE UPDATE OR DELETE ON orders
    FOR EACH ROW EXECUTE FUNCTION save_order_version();
```

**Плюсы:** просто, универсально, работает с любой таблицей. **Минусы:** запрос «состояние на дату» требует сборки из jsonb-снимков; история раздувается (лечится партицированием по `changed_at`).

## 2.2. Temporal-таблица (valid-time)

Версия хранится в самой строке с интервалом действия. Запрос «на дату» — обычный SELECT.

```sql
CREATE TABLE contracts (
    id         bigint NOT NULL,
    version    int    NOT NULL,
    payload    jsonb  NOT NULL,
    valid_from timestamptz NOT NULL,
    valid_to   timestamptz NOT NULL DEFAULT 'infinity',
    PRIMARY KEY (id, version),
    EXCLUDE USING gist (id WITH =, tstzrange(valid_from, valid_to) WITH &&)
);
-- Текущее состояние: WHERE valid_to = 'infinity'
-- Состояние на дату:  WHERE valid_from <= :d AND valid_to > :d
```

**Плюсы:** естественные запросы «на дату», GIST-индекс по интервалам. **Минусы:** усложняет все запросы к «текущему состоянию» (удобно обернуть во VIEW); UPDATE превращается в «закрыть старую строку + вставить новую».

## 2.3. Bi-temporal (две оси времени)

Расширение temporal-подхода: отдельно `valid_time` (когда факт был истинен в реальности) и `system_time` (когда мы о нём узнали). Позволяет отвечать на вопрос «что мы знали о договоре на 1 марта по состоянию на 15 марта». Используется в банковском/страховом учёте. Цена — максимальная сложность запросов и 4 временных колонки.

## 2.4. Soft Delete

Вместо `DELETE` ставится `deleted_at`; все запросы добавляют `WHERE deleted_at IS NULL` (удобно через VIEW или Row-Level Security).

```sql
ALTER TABLE orders ADD COLUMN deleted_at timestamptz;
CREATE VIEW orders_active AS SELECT * FROM orders WHERE deleted_at IS NULL;
-- Уникальность «среди живых»: частичный индекс
CREATE UNIQUE INDEX ON orders (number) WHERE deleted_at IS NULL;
```

**Плюсы:** мгновенное восстановление. **Минусы:** забытый фильтр = утечка удалённых данных; FK и уникальность требуют частичных индексов.

## 2.5. Event Sourcing (журнал событий как источник истины)

Радикальный вариант: хранится не состояние, а **поток всех событий** (`order_created`, `order_paid`, ...). Текущее состояние — результат проекции (fold) событий.

```sql
CREATE TABLE events (
    seq           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_id  bigint NOT NULL,
    event_type    text   NOT NULL,
    payload       jsonb  NOT NULL,
    occurred_at   timestamptz NOT NULL DEFAULT now()
);
-- Таблица append-only: UPDATE/DELETE запрещены (правилами/правами)
```

**Плюсы:** полная история из коробки, любые проекции/витрины перестраиваются из событий. **Минусы:** состояние надо материализовывать (это уже CQRS), схема событий версионируется сама, модель непривычна команде.

## 2.6. SCD Type 2 (медленно меняющиеся измерения)

Подход из DWH: при изменении атрибута старая строка измерения «закрывается» (`valid_to`), вставляется новая с новым суррогатным ключом. По сути — temporal-таблица под аналитику: факты ссылаются на версию измерения, актуальную на момент факта. Type 1 — перезапись без истории, Type 2 — с историей; выбирается по колонке.

## 2.7. Снапшоты и ветвление на уровне хранилища

Copy-on-write снапшоты всей базы (Neon branching, ZFS, облачные снапшоты дисков): «версия» — это снимок кластера целиком. Подходит для демо, тестовых окружений, аналитики «как было вчера», но **не** для построчного аудита.

## Сравнение способов версионирования

| Способ | История | Запрос «на дату» | Сложность записи | Сложность чтения | Типовой случай |
| :--- | :--- | :--- | :--- | :--- | :--- |
| History-таблица | полная (jsonb) | сложный | триггер | простое | аудит любых таблиц |
| Temporal | полная (строки) | естественный | сложная | среднее | договоры, тарифы, справочники |
| Bi-temporal | полная ×2 | естественный | высокая | высокое | банковский учёт |
| Soft delete | нет (только факт удаления) | нет | простая | простое + фильтр | восстановимое удаление |
| Event Sourcing | полная (события) | перестроением | append | нужны проекции | системы с богатой историей |
| SCD Type 2 | по измерениям | по суррогатному ключу | ETL-процесс | простое | аналитические витрины |
| Снапшоты | вся БД | открыть снапшот | нулевая | отдельная копия | демо, тесты, DR |

## Чек-лист внедрения

- [ ] Миграция схемы разбита на Expand → Dual write/CDC → Backfill → Switch → Contract.
- [ ] Backfill идёт батчами с `COMMIT` между ними и ретраями с backoff.
- [ ] Интеграции через Transactional Outbox; консьюмеры идемпотентны (Inbox).
- [ ] CDC-слоты под мониторингом (`restart_lsn`, объём удерживаемого WAL).
- [ ] Для версионирования выбран способ по таблице из сравнительной таблицы, история партицируется и имеет retention.
- [ ] Настроена ротация outbox/history (DETACH старых партиций).
