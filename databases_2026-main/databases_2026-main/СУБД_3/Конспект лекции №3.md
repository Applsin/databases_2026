# Лекция 3. Хранение в базах данных (часть I)

## 1. Термины и базовые понятия

| Термин | Определение |
|---|---|
| **Disk-oriented DBMS** | СУБД, где основное хранилище — энергонезависимый диск; данные обрабатываются после загрузки в память |
| **Volatile storage** | Память, теряющая содержимое при отключении питания; быстрый произвольный доступ с байтовой адресацией (DRAM) |
| **Non-volatile storage** | Хранилище, сохраняющее данные после выключения питания; блочный доступ (SSD, HDD, сетевое хранилище) |
| **Block-addressable** | Способ доступа, где минимальная единица чтения/записи — блок (обычно 4 КБ) |
| **Sequential access** | Чтение непрерывного диапазона данных; значительно быстрее случайного на реальных устройствах |
| **Random access** | Переход в произвольные места на диске; медленнее последовательного |
| **Page** | Фиксированный блок данных на диске, базовая единица ввода-вывода СУБД |
| **Page ID** | Уникальный идентификатор страницы (смещение в файле или логический ID) |
| **Page Directory** | Метаданные, отображающие логический page ID в физическое расположение; хранит информацию о свободном месте |
| **Heap file** | Неупорядоченный набор страниц фиксированного размера; кортежи размещаются в произвольном порядке |
| **Slotted page** | Макет страницы: массив слотов (смещений) в начале, данные кортежей — с конца; растут навстречу друг другу |
| **Slot array** | Фиксированный массив в заголовке slotted page со смещениями начала каждого кортежа |
| **Tuple** | Запись в реляционной БД (строка таблицы); последовательность байтов с заголовком и данными атрибутов |
| **Tuple header** | Метаданные кортежа: битовая карта NULL-значений, информация о видимости транзакциями |
| **Record ID / Tuple ID** | Уникальный идентификатор физического местоположения кортежа (file ID + page ID + slot number) |
| **Overflow page** | Отдельная страница для хранения больших значений атрибутов, не помещающихся в основную страницу |
| **External value storage** | Хранение больших объектов (BLOB) вне файлов БД; в кортеже — только ссылка (путь/URI) |
| **Padding / Alignment** | Добавление пустых байтов для выравнивания следующего атрибута по границе машинного слова (обычно 64 бита) |

### Свойства памяти
- **Volatile:** байтовая адресация, случайный доступ
- **Non-volatile:** блочная адресация, последовательный доступ быстрее случайного. Блоки обычно по 4 КБ

### Время доступа (relative scale)
- L1 Cache — 1 ns (1 sec)
- L2 Cache — 4 ns (4 sec)
- RAM — 100 ns (100 sec)
- SSD — 16 000 ns (4.4 hours)
- HDD — 2 000 000 ns (3.3 weeks)
- Network Storage — 50 000 000 ns (1.5 years)
- Магнитная лента — 1 000 000 000 ns (31.7 years)

## 2. Архитектура диск-ориентированной СУБД

База данных — набор слоёв с чёткими API (снизу вверх):
- **Disk Manager** — читает/записывает данные с диска
- **Buffer Manager** — загружает страницы с диска в память
- **Access Methods** — доступ к данным для операторов запросов
- **Query Planner/Optimizer** — преобразует SQL в физические планы

### Цели проектирования
- Работа с БД, превышающей объём доступной памяти
- Минимизация остановок при ожидании I/O
- Максимизация последовательного доступа
- Эффективное переиспользование загруженных данных

## 3. Файловое хранение (File Storage)

База данных — файлы на диске. **Storage Manager** управляет файлами БД:
- Представляет файлы как набор страниц фиксированного размера
- Отслеживает прочитанные/записанные данные и свободное место
- Может переопределять порядок чтения/записи для производительности
- **Не отвечает** за репликацию данных (это уровень ФС или выше)

### СУБД против ОС
Использовать `mmap` **нельзя**: при страничном промахе процесс блокируется. СУБД контролирует всё сама, так как обладает большей информацией о данных и запросах, чем ОС.

Механизмы ОС для точечного использования:
- `madvise` — подсказка о планируемом чтении
- `mlock` — запрет выгрузки диапазонов в своп
- `msync` — принудительный сброс на диск

## 4. Страницы базы данных (Database Pages)

Три понятия страницы:
1. **Аппаратная (hardware):** обычно 4 КБ, максимальный размер атомарной записи
2. **ОС (OS page):** по умолчанию 4 КБ (huge pages: 2 МБ – 1 ГБ)
3. **БД (database page):** 512 байт – 32 КБ

**Выбор размера страницы БД:**
- **Read-heavy:** большие страницы (до 1 МБ) — последовательные сканирования читают больше полезных данных за раз
- **Write-heavy:** небольшие страницы (4–16 КБ) — изменение одного байта требует перезаписи всей страницы

Если страница БД > аппаратной, нужны дополнительные меры для безопасной записи.

## 5. Heap File (Куча)

Неупорядоченная коллекция страниц фиксированного размера; кортежи хранятся в произвольном порядке. Наиболее распространённая структура в диск-ориентированных СУБД.

**Свойства:**
- Неупорядоченность — нет сортировки по ключу или атрибуту
- Гибкое размещение — кортеж на любой странице со свободным местом
- API: создать страницу, получить по ID, последовательно просканировать все страницы
- Метаданные в **Page Directory** — свободное место, пустые страницы, типы страниц
- Для поиска по ключу требуются отдельные индексы

## 6. Макет страницы (Page Layout)

**Заголовок страницы** содержит:
- Размер страницы
- Контрольная сумма (checksum)
- Версия СУБД
- Информация о видимости транзакций
- Схема таблицы (опционально)
- Эскизы (sketches) значений для ускорения поиска

Три подхода к размещению данных:
1. **Tuple-oriented** — кортеж целиком непрерывно в странице
2. **Log-structured** — дельты изменений вместо самого кортежа
3. **Index-organized** — данные в структуре дерева

### Slotted Pages
- **Заголовок** → **Slot Array** (массив смещений, растёт вперёд)
- **Данные кортежей** — с конца страницы, растут назад
- Страница заполнена, когда массив и данные встречаются

**Преимущества:**
- При удалении и уплотнении обновляется только запись в slot array
- Внешние индексы не изменяются
- Уплотнение в памяти дёшево по сравнению с чтением с диска

## 7. Record ID

Уникальный идентификатор физического местоположения кортежа: **file ID + page ID + slot number**. Обычно не хранится внутри кортежа, а вычисляется во время выполнения. Может меняться при перемещении данных (compaction). Приложение не должно полагаться на Record ID.

## 8. Макет кортежа (Tuple Layout)

**Tuple Header:**
- Информация о видимости (какая транзакция создала/модифицировала)
- **Null Column Bitmap** — битовая карта NULL-значений (1 бит на атрибут)
- **В PostgreSQL:** служебные поля `xmin` (ID транзакции, создавшей версию кортежа) и `xmax` (ID транзакции, удалившей/изменившей её) — физическая основа MVCC

**Tuple Data:**
- Атрибуты в порядке `CREATE TABLE`
- Выровнены по 64-битной границе (word aligned)

### Padding / Alignment
Добавление заполнителей после атрибутов для выравнивания следующего атрибута по границе машинного слова. Альтернатива — переупорядочить столбцы для плотной упаковки (в коммерческих СУБД обычно не применяется).

## 9. Представление данных

### Целочисленные типы
Хранятся в нативном формате C/C++ с учётом endianness.

### Числа с плавающей точкой
- **FLOAT / REAL:** IEEE-754, аппаратная реализация, быстры, но не гарантируют точного представления десятичных дробей (0.1 + 0.2 ≠ 0.3)
- **NUMERIC / DECIMAL:** фиксированная точность, программная реализация. Хранится метаинформация о положении точки и масштабе + массив байтов. Гарантирует точность (финансы, банкинг), но на порядки медленнее аппаратного сложения

### Строки и бинарные данные
- **Небольшие значения:** хранятся inline (длина + байты)
- **Большие значения (> 2 КБ):** выносятся в **overflow pages**; в кортеже — указатель (record ID) и размер
- **Оптимизации:** сжатие overflow-страниц, prefix truncation (префикс значения в кортеже для фильтрации без обращения к overflow)
- **External Value Storage:** значения > 128 КБ — вне БД (B-Files, FileStream); транзакционная безопасность не гарантируется. TOAST в PostgreSQL сюда **не относится**: данные остаются внутри БД и полностью транзакционны

### Дата и время
32- или 64-битное целое — микросекунды/миллисекунды от внутренней точки отсчёта: в PostgreSQL `timestamp` — 64-битное число микросекунд с 1 января 2000 года, в Unix-подобных системах — от Unix epoch (1 января 1970).

### NULL-значения
1. **Null Column Bitmap Header** — битовая карта в заголовке кортежа (распространён в row-stores)
2. **Special Values** — специальное значение домена (например, `INT32_MIN`; применяется в column-stores)
3. **Per-Attribute Null Flag** — флаг перед каждым значением (крайне нежелателен: раздувает размер, требует выравнивания)

### запросы для метаданных страницы в PostgreSql
- SELECT pg_relation_filepath('demo.bookings.flights'); -- путь к файлу таблицы
- SELECT pg_relation_size('demo.bookings.flights') AS size_bytes,
       pg_relation_size('demo.bookings.flights') / 8192 AS size_pages; -- размер таблицы в байтах и страницах
- SELECT (pg_stat_file(pg_relation_filepath(
         'demo.bookings.flights'))).*; -- информация о файле на диске
- -- lower: конец массива слотов,

- SELECT * FROM page_header(
  get_raw_page('demo.bookings.flights', 0)); -- посмотреть заголовок страницы
- SELECT lp, lp_off, lp_flags, lp_len
FROM heap_page_items(
  get_raw_page('demo.bookings.flights', 0))
ORDER BY lp; -- посмотреть номера слотов и их смещения у страницы
- 
SELECT lp, t_xmin, t_xmax, t_field3, t_ctid,
       t_infomask, t_infomask2, t_hoff,
       t_bits, t_data
FROM heap_page_items(
  get_raw_page('demo.bookings.flights', 0))
ORDER BY lp; - -- Полный заголовок кортежа + сырые данные

- SELECT lp, t_xmin, t_xmax, t_ctid, t_data
FROM heap_page_items(
  get_raw_page('demo.bookings.flights', 0))
WHERE lp IN (1, 2)
ORDER BY lp; - информация об MVCC у кортежа

- SELECT ctid,
  (ctid::text::point)[0]::int AS page_number,
  (ctid::text::point)[1]::int AS slot_number
FROM demo.bookings.flights
LIMIT 10; - просмотр служебных страниц таблицы
