
# Конспект семинара: DDL, DML, DCL и блокировки в PostgreSQL

## 1. Классификация команд SQL

SQL делится на несколько подъязыков по назначению:

- **DDL** (Data Definition Language) – работа со структурой объектов (таблиц, индексов).
- **DML** (Data Manipulation Language) – работа с данными (чтение, добавление, изменение, удаление строк).
- **DCL** (Data Control Language) – управление доступом (`GRANT`, `REVOKE`).
- **TCL** (Transaction Control Language) – управление транзакциями (`COMMIT`, `ROLLBACK`).

---

## 2. DDL – команды определения данных

DDL-команды меняют схему БД. В PostgreSQL большинство из них требуют **эксклюзивную блокировку всей таблицы** (`AccessExclusiveLock`), которая несовместима ни с каким другим доступом. Это значит: пока операция не завершится (и пока не завершатся все транзакции, работающие с таблицей), **никто не может читать или изменять эту таблицу**.

**Основные DDL-команды и их влияние:**

| Команда | Блокирует всю таблицу? | Примечание |
|--------|------------------------|------------|
| `CREATE TABLE` | Нет | Создаётся новый объект, не мешает другим. |
| `ALTER TABLE ... ADD COLUMN` (без DEFAULT) | **Да** (кратковременно) | Мгновенная блокировка для правки каталога. Данные не переписываются. |
| `ALTER TABLE ... ADD COLUMN ... DEFAULT const` | **Да** (кратковременно) | С **PostgreSQL 11+** выполняется мгновенно (метаданные). Данные не переписываются. |
| `ALTER TABLE ... DROP COLUMN` | **Да** (кратковременно) | Блокировка только для удаления метаданных. Физическая очистка произойдет позже при `VACUUM`. |
| `ALTER TABLE ... ALTER COLUMN TYPE` | **Да** (длительно) | Полная блокировка + **перезапись всей таблицы** и индексов. |
| `ALTER TABLE ... ADD CONSTRAINT` | **Да** | Длительная блокировка на время проверки существующих данных. |
| `DROP TABLE` / `TRUNCATE TABLE` | **Да** | Эксклюзивная блокировка. |
| `CREATE INDEX` (без `CONCURRENTLY`) | **Да** (блокирует запись) | Блокирует `INSERT/UPDATE/DELETE`, но разрешает `SELECT` (блокировка `ShareLock`). |
| `CREATE INDEX CONCURRENTLY` | **Нет** | Не мешает чтению/записи. Строится дольше, требует отдельного сканирования. |
| `REINDEX` (без `CONCURRENTLY`) | **Да** | Эксклюзивная блокировка таблицы. |
| `CLUSTER` | **Да** | Перезапись таблицы, длительная блокировка. |

> **Важно:** Даже если сам `ALTER TABLE` выполняется быстро (миллисекунды), он **ждёт завершения всех текущих транзакций**, работающих с таблицей. Висящий `BEGIN; SELECT ...;` (без `COMMIT`) заблокирует изменение схемы неограниченно долго.

---

## 3. DML – команды манипулирования данными

DML работает с содержимым таблиц. В PostgreSQL используется **MVCC** (многоверсионность), поэтому:
- `SELECT` никогда не блокирует другие операции (за исключением `SELECT ... FOR UPDATE`).
- `INSERT`, `UPDATE`, `DELETE` блокируют только **отдельные строки**, не мешая параллельным чтениям или изменениям других строк.

| Команда | Блокирует всю таблицу? | Примечание |
|--------|------------------------|------------|
| `SELECT` | **Нет** | Чистое чтение, не блокирует никого. |
| `INSERT` | **Нет** | Блокирует только вставляемые строки. |
| `UPDATE` / `DELETE` | **Нет** | Блокирует только изменяемые строки на время транзакции. |
| `SELECT ... FOR UPDATE` | **Нет** | Явная блокировка выбранных строк до конца транзакции. |
| `LOCK TABLE ... IN ACCESS EXCLUSIVE MODE`| **Да** | Ручная принудительная блокировка всей таблицы (аналог DDL). |

**Вывод:** На production-таблице можно свободно использовать `SELECT`, `INSERT`, `UPDATE`, `DELETE` — они не останавливают работу других пользователей.

---

## 4. DCL – команды управления доступом

DCL управляет правами пользователей. Эти команды **не блокируют таблицы**, так как меняют только системные каталоги.

| Команда | Блокирует таблицы? | Примечание |
|--------|--------------------|------------|
| `GRANT` | **Нет** | Выдача прав. |
| `REVOKE` | **Нет** | Отзыв прав. |

---

## 5. Какие операции блокируют всю таблицу (шпаргалка)

**Полностью блокируют таблицу (`AccessExclusiveLock`):**
- `ALTER TABLE ... DROP COLUMN`
- `ALTER TABLE ... ALTER COLUMN TYPE`
- `ALTER TABLE ... ADD CONSTRAINT`
- `DROP TABLE` / `TRUNCATE TABLE`
- `REINDEX` (без `CONCURRENTLY`)
- `CLUSTER`

**Блокируют запись, но разрешают чтение:**
- `CREATE INDEX` (без `CONCURRENTLY`)

**Не блокируют таблицу (безопасно для Production):**
- Все DML-команды (`SELECT`, `INSERT`, `UPDATE`, `DELETE`)
- `CREATE INDEX CONCURRENTLY` / `REINDEX CONCURRENTLY`
- `ALTER TABLE ... ADD COLUMN` (с `DEFAULT` или без, начиная с PG 11)
- `GRANT`, `REVOKE`

## 6. Мониторинг блокировок

Для наблюдения за блокировками используются системные представления `pg_locks` и `pg_stat_activity`.

### 6.1. Посмотреть все блокировки в базе
```sql
SELECT locktype, relation::regclass AS table_name,
       mode, granted, pid
FROM pg_locks
WHERE relation IS NOT NULL;
```

### 6.2. Найти ожидающие блокировки (кто кого ждёт)
*Современный подход с использованием встроенной функции `pg_blocking_pids` (PostgreSQL 9.6+), работает надежнее сложных JOIN'ов:*
```sql
SELECT
    blocked.pid AS blocked_pid,
    blocked.query AS blocked_query,
    blocking.pid AS blocking_pid,
    blocking.query AS blocking_query,
    now() - blocked.xact_start AS blocked_duration
FROM pg_stat_activity blocked
JOIN pg_stat_activity blocking 
  ON blocking.pid = ANY(pg_blocking_pids(blocked.pid))
WHERE blocked.state = 'active';
```

### 6.3. Найти долгие незавершённые транзакции (частую причину зависаний DDL)
```sql
SELECT pid, state, state_change, query, age(now(), xact_start) AS xact_duration
FROM pg_stat_activity
WHERE state = 'idle in transaction'
  AND xact_start < now() - interval '1 minute';
```

### 6.4. Принудительное завершение мешающей транзакции
Если транзакция с `pid = 12345` блокирует работу и её можно безопасно прервать:
```sql
SELECT pg_terminate_backend(12345);
```
*Применять с осторожностью, только после анализа.*

## 7. Рекомендации по безопасной работе с нагруженными таблицами

- **Никаких DDL без подготовки.** Планируйте изменения схемы на периоды минимальной нагрузки.
- **Проверяйте активные транзакции** перед `ALTER TABLE` (запрос 6.3).
- **Используйте `CREATE INDEX CONCURRENTLY`** для построения индексов без простоя.
- **Не бойтесь добавлять столбцы с `DEFAULT`** в PostgreSQL 11+, но избегайте добавления `NOT NULL` с `DEFAULT` на гигантских таблицах без проверки (иногда требует сканирования).
- **Не держите транзакции открытыми** дольше необходимого; закрывайте их (`COMMIT` / `ROLLBACK`).
- **Мониторьте блокировки** с помощью приведённых запросов, особенно при жалобах на «зависания».
