## 1. Базовые понятия и DDL

**СУБД (Система Управления Базами Данных)** — ПО, которое управляет БД. Главное: обеспечивает целостность, транзакции (ACID), безопасность и скрывает физическое хранение данных от приложения.

**DDL (Data Definition Language)** — язык определения данных (создание структуры БД).

| Команда | Что делает | Заметка |
| :--- | :--- | :--- |
| `CREATE TABLE` | Создает таблицу | |
| `ALTER TABLE` | Изменяет структуру | Можно добавлять колонки и ограничения |
| `DROP TABLE` | Удаляет таблицу целиком | |
| `TRUNCATE` | Очищает таблицу | **Важно:** В PostgreSQL транзакционна (можно откатить через `ROLLBACK`). По умолчанию **не** сбрасывает счётчики `SERIAL` — для сброса нужна опция `RESTART IDENTITY`. Нельзя использовать, если на таблицу ссылаются внешние ключи других таблиц (без опции `CASCADE`). |

## 2. Ограничения целостности (Constraints)

Это правила, которые СУБД проверяет автоматически при добавлении/изменении данных. Если правило нарушено — операция отменяется.

| Ограничение | Суть | Пример |
| :--- | :--- | :--- |
| **`PRIMARY KEY`** | Уникальный ID + не может быть NULL | `task_id SERIAL PRIMARY KEY` |
| **`FOREIGN KEY`** | Ссылка на PK другой таблицы | `FOREIGN KEY (project_id) REFERENCES projects(id)` |
| **`UNIQUE`** | Значения в колонке не повторяются | `email VARCHAR UNIQUE` |
| **`NOT NULL`** | Запрещает пустые значения | `title VARCHAR NOT NULL` |
| **`CHECK`** | Пользовательское условие (бизнес-логика) | `CHECK (deadline >= start_date)` |
| **`EXCLUDE`** | Запрет пересечений (диапазоны, площади); требует расширения `btree_gist` | `EXCLUDE USING gist (room_id WITH =, period WITH &&)` |

> ⚠️ **Важно по `CHECK` и `NULL`:** В SQL логика трехзначна. Выражение `NULL > 0` дает `UNKNOWN` (не `FALSE`). Поэтому `CHECK (price > 0)` **пропустит** `NULL`. Если нужен запрет на `NULL`, добавляйте `NOT NULL`.

### Каскадные операции (для `FOREIGN KEY`)
Что делать с дочерними записями при удалении родителя?
*   `ON DELETE CASCADE` — удалить все дочерние записи (например, удаляем проект → удаляются его задачи).
*   `ON DELETE SET NULL` — обнулить внешний ключ у дочерних записей (уволили сотрудника → в задачах исполнитель стал `NULL`).
*   `ON DELETE RESTRICT` — запретить удаление родителя, если есть дочерние записи.

## 3. Нормализация (Нормальные формы)

**Цель нормализации:** убрать избыточность данных и аномалии (когда при обновлении одной строки нужно менять еще десяток строк).

**Сквозной пример нормализации:**
*Допустим, есть одна плоская таблица: `(EmployeeID, ProjectID, EmployeeName, ProjectName, ManagerDept, ManagerID)`*

### 1НФ (Первая нормальная форма)
*   **Правило:** Все значения атомарны (неделимы), есть первичный ключ.
*   **Действие:** Убираем списки в ячейках (например, теги через запятую выносим в отдельную таблицу). Назначаем составной PK: `(EmployeeID, ProjectID)`.
*   *Проблема:* Имя сотрудника дублируется во многих строках.

### 2НФ (Вторая нормальная форма)
*   **Правило:** Таблица в 1НФ + неключевые атрибуты зависят от **всего** составного ключа, а не от его части.
*   *(Актуально только для составных PK)*
*   **Действие:** `EmployeeName` зависит только от `EmployeeID`, а `ProjectName` — от `ProjectID`. Разбиваем на 3 таблицы: `Employees`, `Projects` и связующую `Task_Assignments`.

### 3НФ (Третья нормальная форма)
*   **Правило:** Таблица в 2НФ + нет транзитивных зависимостей (неключевые атрибуты зависят только от ключа).
*   **Действие:** В таблице `Projects` было: `ProjectID` → `ManagerID` → `ManagerDept`. Отдел зависит от менеджера, а не от проекта. Выносим менеджеров в отдельную таблицу `Managers`.

### BCNF (Нормальная форма Бойса-Кодда)
*   **Правило:** Таблица в 3НФ + каждый детерминант (атрибут, от которого что-то зависит) является потенциальным ключом.
*   **Действие:** Если один менеджер ведет строго один проект, то `ManagerID` определяет `ProjectID`. Но `ManagerID` не является ключом в таблице связей. Нужно вынести связь `ManagerID ↔ ProjectID` в отдельную таблицу, оставив в связях только привязку сотрудника к проекту.

## 4. Денормализация
Это **намеренное** возвращение избыточности (обратный процесс).
*   **Зачем:** Для ускорения чтения (OLAP, дашборды, BI). Чтобы не делать 5 JOIN-ов на каждый запрос.
*   **Как:** Через создание `VIEW` (представлений) или материализованных витрин.

## 5. Практика: SQL-шпаргалка

### Сложные ограничения
```sql
-- 1. Проверка формата Email через регулярку
CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$')

-- 2. Проверка дат
CHECK (deadline >= start_date)

-- 3. Сложное условие (через OR / AND)
-- Если статус 'done', то assignee_id не может быть NULL
ALTER TABLE tasks ADD CONSTRAINT check_done_has_assignee 
    CHECK (status != 'done' OR assignee_id IS NOT NULL);
```

### Денормализованное представление (VIEW)
```sql
CREATE VIEW v_task_report AS
SELECT 
    t.task_id, t.title, 
    p.name AS project_name,
    -- Склеиваем теги из другой таблицы в одну строку (денормализация)
    COALESCE(
        (SELECT string_agg(tag.name, ', ')
         FROM task_tags tt JOIN tags tag ON tt.tag_id = tag.tag_id
         WHERE tt.task_id = t.task_id),
        'Нет тегов'
    ) AS tags
FROM tasks t
LEFT JOIN projects p ON t.project_id = p.project_id;
```

### Загрузка данных из CSV
В PostgreSQL `COPY` работает на сервере, а `\copy` — на клиенте (psql).
```sql
\copy projects (name, start_date, deadline) 
FROM '/path/file.csv' DELIMITER ',' CSV HEADER;
```

**Безопасная загрузка (с пропуском ошибок):**
Если в CSV есть кривые данные, `COPY` упадет с ошибкой. Чтобы этого избежать, грузим во временную таблицу, а оттуда фильтруем в основную:
```sql
CREATE TEMP TABLE temp_tasks (LIKE tasks INCLUDING DEFAULTS);
-- список колонок обязателен: во временной таблице есть task_id, которого нет в CSV
\copy temp_tasks (project_id, assignee_id, title, description, status, priority, estimated_hours, created_date) FROM '/path/file.csv' DELIMITER ',' CSV HEADER;

INSERT INTO tasks (project_id, assignee_id, title, description, status, priority, estimated_hours, created_date)
SELECT project_id, assignee_id, title, description, status, priority, estimated_hours, created_date
FROM temp_tasks
WHERE estimated_hours > 0; -- фильтруем мусор
```

### Работа с JSONB (PostgreSQL feature)
Позволяет хранить гибкие данные без создания новых таблиц.
```sql
-- Добавление колонки
ALTER TABLE tasks ADD COLUMN metadata JSONB;

-- Поиск: содержит ли массив внутри JSON элемент "urgent"
SELECT * FROM tasks WHERE metadata @> '{"labels": ["urgent"]}';

-- Добавление нового ключа в JSON (COALESCE обязателен: NULL || jsonb = NULL!)
UPDATE tasks SET metadata = COALESCE(metadata, '{}'::jsonb) || '{"reviewed": true}'::jsonb;
```
