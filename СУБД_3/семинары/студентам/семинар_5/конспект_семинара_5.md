## 1. Архитектура и путь запроса (кратко)

- **Process-per-connection**: `postmaster` порождает отдельный backend-процесс для каждого клиента; клиенты изолированы, один тяжёлый запрос не роняет остальных.
- Фоновые процессы: `checkpointer` (контрольные точки), `background writer` (сброс грязных страниц), `walwriter` (сброс WAL), `autovacuum launcher` (уборка мёртвых версий строк).
- **Путь чтения**: Parser → Analyzer → Rewriter → Planner (статистика `pg_statistic`) → Executor → Buffer Manager (`shared_buffers`) → ОС → диск.
- **Путь записи**: страница в `shared_buffers` → новая версия строки (MVCC) → запись в WAL-буфер → при COMMIT: fsync WAL в `pg_wal/` → фоном: checkpoint и autovacuum сбрасывают страницы и чистят «мусор».

```bash
# посмотреть процессы
docker exec -it pg16_check bash -c "ps aux | grep postgres"
```

## 2. MVCC: версии строк и видимость

**MVCC** (Multi-Version Concurrency Control) — изоляция через версии строк: читатели не блокируют писателей, писатели — читателей.

У каждой версии строки в заголовке:
- `xmin` — xid транзакции, **создавшей** версию;
- `xmax` — xid транзакции, **удалившей/заменившей** версию (`0` — жива).

`UPDATE` = **DELETE + INSERT**: старая версия получает `xmax`, рядом создаётся новая с новым `xmin`. Старые версии, невидимые всем снимкам, — «мусор», их убирает **autovacuum**.

**Правило видимости** (упрощённо): транзакция со снимком S видит версию, если `xmin` зафиксировалась до S, а `xmax` пуст или не зафиксировался до S. «Настоящая» версия — всегда вопрос снимка.

Последствия:
- **Bloat**: много UPDATE/DELETE без autovacuum → таблица раздувается.
- Длинные транзакции удерживают старые снимки → autovacuum не может очистить версии → bloat растёт ещё быстрее.
- Xid имеет конечный размер (32 бита): старые строки «замораживаются» (freeze), иначе — **xid wraparound** (катастрофа, PostgreSQL останавливает запись).

## 3. ACID — реализация в PostgreSQL

| Свойство | Реализация |
|---|---|
| **A — Atomicity** | WAL: незафиксированная транзакция откатывается при сбое (redo только committed). |
| **C — Consistency** | Constraints, CHECK, FK, триггеры — проверяются при выполнении. |
| **I — Isolation** | MVCC: снимки данных, уровни изоляции (раздел 4). |
| **D — Durability** | При COMMIT WAL синхронно сбрасывается на диск (`pg_wal/`, `fsync`). |

## 4. Уровни изоляции и аномалии

**Феномены (аномалии):**
- **Dirty read** — чтение чужих незафиксированных данных. В PostgreSQL **невозможен**.
- **Non-repeatable read** — повторный SELECT вернул другое значение.
- **Phantom read** — повторный SELECT вернул новые строки.
- **Serialization anomaly** — результат параллельного выполнения не эквивалентен никакому последовательному.

| Уровень | Снимок | Допускает | Применение |
| :--- | :--- | :--- | :--- |
| **READ COMMITTED** (дефолт) | на каждый оператор | non-repeatable read, phantom | типовой OLTP |
| **REPEATABLE READ** | на всю транзакцию | serialization anomaly | отчёты, стабильные проверки |
| **SERIALIZABLE** | на всю транзакцию + SSI-проверки | ничего | денежные инварианты; требует retry |

- Попытка изменить строку, изменённую и зафиксированную после начала снимка: в RR/SERIALIZABLE → `ERROR: could not serialize access due to concurrent update` (SQLSTATE **40001** → перезапуск транзакции).
- Код под RR/SERIALIZABLE обязан уметь **retry** (как и при `deadlock detected`, 40P01).

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- ... работа ...
COMMIT;
```

## 5. Блокировки

### Строковые блокировки

```sql
SELECT ... WHERE id = $1 FOR UPDATE;        -- эксклюзивная строковая
SELECT ... WHERE id = $1 FOR NO KEY UPDATE; -- слабее (не конфликтует с KEY SHARE)
SELECT ... WHERE id = $1 FOR SHARE;         -- разделяемая
SELECT ... WHERE id = $1 FOR KEY SHARE;     -- weakest (для FK-проверок)
-- модификаторы ожидания:
FOR UPDATE NOWAIT    -- не ждать: сразу ERROR could not obtain lock
FOR UPDATE SKIP LOCKED -- пропустить заблокированные строки (очереди)
```

### Блокировки таблицы (режимы по возрастанию тяжести)

| Режим | Кто берёт | Конфликтует с |
| :--- | :--- | :--- |
| `ACCESS SHARE` | любой SELECT | только ACCESS EXCLUSIVE |
| `ROW SHARE` | `SELECT ... FOR UPDATE` | EXCLUSIVE, ACCESS EXCLUSIVE |
| `ROW EXCLUSIVE` | INSERT/UPDATE/DELETE | SHARE*, EXCLUSIVE, ACCESS EXCLUSIVE |
| `SHARE UPDATE EXCLUSIVE` | VACUUM, ANALYZE | сам с собой, SHARE*, EXCLUSIVE, ACCESS EXCLUSIVE |
| `SHARE` | `CREATE INDEX` | ROW EXCLUSIVE и тяжелее |
| `EXCLUSIVE` | явный `LOCK TABLE ... IN EXCLUSIVE MODE` | ROW SHARE, ROW EXCLUSIVE, SHARE*, EXCLUSIVE, ACCESS EXCLUSIVE |
| `ACCESS EXCLUSIVE` | `ALTER TABLE`, `DROP TABLE`, `TRUNCATE` | **со всем**, включая SELECT |

*(SHARE\* = `SHARE` и `SHARE ROW EXCLUSIVE`; «конфликтует» = нельзя получить одновременно с перечисленными режимами.)*

### Очередь и deadlock

- Ожидание блокировки видно: `pg_locks` (`granted = f`), `pg_stat_activity.wait_event = 'Lock'`.
- FIFO **не гарантируется** — возможно голодание ожидающих транзакций.
- **Deadlock**: цикл ожиданий. PostgreSQL обнаруживает его (`deadlock_timeout`, ~1 с) и убивает одну транзакцию: `ERROR: deadlock detected`. Профилактика: блокировки брать в одном порядке (например, по возрастанию id), транзакции держать короткими.

```sql
-- кто и чего ждёт
SELECT pid, locktype, mode, granted FROM pg_locks WHERE NOT granted;
SELECT pid, state, wait_event FROM pg_stat_activity WHERE wait_event = 'Lock';
```

## 6. Паттерны работы с транзакциями

1. **Короткие транзакции** — никаких «диалогов с пользователем» внутри; длинные транзакции = блокировки + bloat + lag репликации.
2. **Атомарный UPDATE с проверкой в WHERE**: `UPDATE accounts SET balance = balance - X WHERE acc_no = N AND balance >= X` → 0 строк = «не хватило средств». Убирает гонку «проверил и изменил».
3. **Идемпотентность**: `INSERT ... ON CONFLICT (id) DO NOTHING` + уникальный индекс (webhook'ы, повторные отправки).
4. **Retry на 40001** (`could not serialize...`, `deadlock detected`) — обязателен для RR/SERIALIZABLE.
5. **Оптимистичные блокировки**: колонка `version`, `UPDATE ... WHERE id = N AND version = V` → 0 строк = конфликт, перечитать и повторить.
6. **Очереди через `SKIP LOCKED`**: воркеры забирают задачи без ожиданий и дублей.
7. **Savepoints**: `SAVEPOINT s; ... ROLLBACK TO s;` — частичный откат внутри большой транзакции.
8. **READ ONLY для отчётов**: `BEGIN; SET TRANSACTION READ ONLY; ...` — страховка от случайной записи.
9. **Знать дефолт**: в READ COMMITTED «проверил-потом-вставил» — гонка; либо изоляция выше, либо паттерн №2.

## 7. WAL и durability

**WAL** (Write-Ahead Log) — append-only журнал **физических** изменений страниц («в страницу N файла X записаны байты Y»), а не SQL-операторов. Записи redo-идемпотентны.

**Три опоры WAL:**
1. **Crash recovery** — при старте после сбоя PostgreSQL повторяет (redo) зафиксированные изменения от последнего checkpoint.
2. **Репликация** — standby применяет поток WAL (единственный источник правды для синхронизации).
3. **PITR** (Point-in-Time Recovery) — базовая копия + архив WAL = восстановление на любой момент времени.

**Путь записи:** изменение страницы в `shared_buffers` → WAL-запись в `wal_buffers` → при COMMIT: `walwriter` → `pg_wal/` (сегменты 16 МБ) → `fsync` → ответ клиенту. Фоном checkpoint отмечает точку, до которой WAL больше не нужны, и запускает сброс страниц в файлы таблиц.

**Нюансы:**
- **Group commit**: конкурентные COMMIT'ы сливаются в один fsync.
- **`synchronous_commit`**: `on` (ждём диск, дефолт) / `off` (ждём ОС, риск потери при крахе ОС) / `remote_apply` (ждём применения на синхронной реплике).
- **full_page_writes**: после checkpoint первое изменение страницы пишет её целиком — защита от «рваных» страниц при сбое.

```sql
SELECT pg_current_wal_lsn();                          -- позиция в WAL
SELECT pg_wal_lsn_diff(lsn2, lsn1);                   -- сколько байт между позициями
SELECT * FROM pg_stat_wal;                            -- статистика записи WAL (PG 14+)
SELECT pg_switch_wal();                               -- принудительно переключить сегмент
```

```bash
# физические сегменты WAL
docker exec -it pg16_check ls -lh /var/lib/postgresql/data/pg_wal/
```

## 8. DCL: роли и привилегии — справочник

### 8.1 Роли: пользователи и группы

В PostgreSQL одна сущность — **роль**. Роль с `LOGIN` — «пользователь»; без `LOGIN` — «группа».

```sql
CREATE ROLE ivanov LOGIN PASSWORD '***' CONNECTION LIMIT 5 VALID UNTIL '2027-01-01';
CREATE ROLE analyst NOLOGIN;                  -- группа

-- членство в группе (права наследуются, INHERIT по умолчанию)
GRANT analyst TO ivanov;

-- просмотр
\du            -- роли и атрибуты
\drg analyst   -- члены группы
SELECT * FROM pg_roles;
```

**Атрибуты роли** (только суперпользователь может выдавать опасные):
| Атрибут | Смысл |
| :--- | :--- |
| `LOGIN` | разрешён вход в БД |
| `SUPERUSER` | обход всех проверок прав — только для администрирования |
| `CREATEDB` / `CREATEROLE` | создание баз / ролей |
| `REPLICATION` | подключение для репликации |
| `BYPASSRLS` | обход row-level security |
| `INHERIT` | наследовать права групп (дефолт) |
| `CONNECTION LIMIT`, `VALID UNTIL` | лимиты |

### 8.2 Уровни привилегий

| Объект | Привилегии |
| :--- | :--- |
| DATABASE | `CONNECT`, `CREATE`, `TEMP` |
| SCHEMA | `USAGE`, `CREATE` |
| TABLE / VIEW | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` |
| COLUMN | `SELECT (col, ...)`, `INSERT (...)`, `UPDATE (...)` |
| SEQUENCE | `USAGE`, `SELECT`, `UPDATE` |
| FUNCTION | `EXECUTE` |

```sql
GRANT SELECT, INSERT ON bookings.tickets TO analyst;
GRANT SELECT (ticket_no, book_ref) ON bookings.tickets TO analyst;   -- на колонки
GRANT USAGE ON SCHEMA bookings TO analyst;
GRANT CONNECT ON DATABASE demo TO analyst;
REVOKE DELETE ON bookings.tickets FROM analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA bookings TO analyst;            -- на существующие
```

### 8.3 ALTER DEFAULT PRIVILEGES — права на будущие объекты

`GRANT ... ON ALL TABLES IN SCHEMA` действует только на **уже существующие** объекты. Новые таблицы получат права через шаблон:

```sql
-- всё, что создаст роль app_owner в схеме bookings — читабельно для analyst
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA bookings
  GRANT SELECT ON TABLES TO analyst;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA bookings
  GRANT USAGE ON SEQUENCES TO analyst;
```

### 8.4 Ловушки

1. **`PUBLIC`**: по умолчанию имеет `CONNECT`/`TEMP` на базы и `USAGE`/`CREATE` на схему `public` (в PG ≤ 14). Лишнее отзывать: `REVOKE ALL ON DATABASE demo FROM PUBLIC;`
2. **Схема**: без `USAGE` на схему права на таблицу бесполезны — `permission denied for schema`.
3. **Последовательности**: `INSERT` в таблицу с `SERIAL`/`IDENTITY` требует `USAGE` на связанную sequence.
4. **Новые объекты без прав**: см. `ALTER DEFAULT PRIVILEGES`.
5. **Владелец**: owner объекта имеет все права на него и может менять структуру. При увольнении: `REASSIGN OWNED BY ivanov TO app_owner; DROP OWNED BY ivanov;`

### 8.5 Служебные команды

```sql
SET ROLE analyst;          -- «sudo» на роль внутри сессии
RESET ROLE;
SET SESSION AUTHORIZATION ivanov;  -- сильнее: меняет и текущего пользователя
\dp bookings.tickets       -- права на конкретный объект
\l+, \dn+                  -- права на базы и схемы
SELECT * FROM information_schema.table_privileges WHERE table_schema = 'bookings';
SELECT * FROM information_schema.column_privileges  WHERE table_schema = 'bookings';
```

## 9. Паттерны управления ролевым доступом (enterprise)

Как доступ обычно устроен в зрелых компаниях:

1. **Принцип наименьших привилегий (least privilege).** Роль получает ровно то, что нужно для функции — не «на всякий случай». Для ПДн — обязательна минимизация (152-ФЗ): колоночные гранты, маскирование на уровне приложения.
2. **Роли-персоны отделены от ролей-функций.** Человек — `LOGIN`-роль (учётная запись, отвечает за действия в аудите), входит в no-login группы по должности. Приложение — отдельная роль на сервис, минимум прав, никогда не `SUPERUSER`.
3. **Разделение по средам и ролям в данных.** `app_prod_ro` (чтение для аналитики), `app_prod_rw` (runtime), владелец схемы — отдельная роль: DDL только через контролируемые миграции, не из приложения.
4. **Цепочки ролей (role chaining).** `LOGIN`-роль человека → функциональная группа (`analyst`) → группа доступа к данным (`bookings_read`). Права выдаются только «верхним» группам; людей добавляют/удаляют в членах — без пересмотра грантов.
5. **`ALTER DEFAULT PRIVILEGES` в шаблоне схемы.** Скрипт создания схемы сразу включает шаблон прав, иначе новые таблицы «невидимы» сервисным ролям.
6. **Секреты вне кода.** Пароли — в vault/переменных окружения с ограниченным доступом, не в репозитории и не в docker-compose под контролем версий «как есть». Ротация паролей; у каждой роли-персоны — свой пароль.
7. **Аудируемость.** Действия должно быть возможно отнести к человеку: персональные роли вместо «общего analyst», включённые `log_connections`/`log_statement` (или расширение `pgaudit`) для чувствительных таблиц.
8. **Офбординг.** Увольнение: отозвать членство в группах, `REASSIGN OWNED`/`DROP OWNED`, ротация паролей и сертификатов, проверка оставшихся сессий (`pg_stat_activity`).
9. **Аналитика не на primary.** Отчётные запросы — на read-реплике; на ней же `default_transaction_read_only = on` как страховка.
10. **Анти-паттерны:** приложение под `postgres`/суперпользователем; `GRANT ALL`; общий пароль команды; права, раздаваемые миграциями без ревью; хранение паролей в коде.

## 10. Аудит действий пользователей (149-ФЗ) — справочно

Журналирование доступа и действий — требование для информации, составляющей коммерческую тайну.

```sql
ALTER SYSTEM SET log_connections = 'on';
ALTER SYSTEM SET log_statement = 'all';     -- все SQL-запросы (шумно; в бою избирательно)
SELECT pg_reload_conf();                    -- применить без перезапуска
SHOW log_directory;
```

Настройки пишутся в `postgresql.auto.conf` (не редактируйте его руками). Детальный аудит таблиц — расширение **pgaudit**.

В официальном Docker-образе `logging_collector` выключен, логи идут в stdout контейнера:

```bash
docker logs pg16_check --tail 30
# если logging_collector включён:
docker exec -it pg16_check sh -c 'ls -lh /var/lib/postgresql/data/log/ && tail -n 20 /var/lib/postgresql/data/log/postgresql-*.log'
```

Полезно также: `log_line_prefix` (pid, пользователь, БД, время), `log_min_duration_statement` — логировать только медленные запросы.

## 11. Резервное копирование (187-ФЗ) — справочно

**Логическое резервирование** — выгрузка объектов в SQL/архив:

```bash
# дамп одного объекта
MSYS_NO_PATHCONV=1 docker exec -i pg16_check \
  bash -c "pg_dump -U postgres -d demo -t bookings.aircrafts > /tmp/aircrafts_backup.sql"

# кастомный формат (сжатый, восстанавливается через pg_restore)
docker exec -i pg16_check pg_dump -U postgres -d demo -Fc -f /tmp/demo.fc

# удаление и восстановление объекта
MSYS_NO_PATHCONV=1 docker exec -i pg16_check \
  psql -U postgres -d demo -c "DROP VIEW bookings.aircrafts CASCADE;"
MSYS_NO_PATHCONV=1 docker exec -i pg16_check \
  psql -U postgres -d demo -f /tmp/aircrafts_backup.sql
```

**Физическое резервирование и PITR:** базовая копия (`pg_basebackup`) + непрерывный архив WAL (`archive_mode`, `archive_command`) → восстановление на любой момент времени (см. раздел 7).

**Правило 3-2-1:** не менее 3 копий, на 2 разных носителях, 1 — вне офиса (офсайт/другой регион).

Связь с 187-ФЗ (КИИ): резервирование критичных данных и проверка восстановления — обязательные элементы защиты объектов критической информационной инфраструктуры.
