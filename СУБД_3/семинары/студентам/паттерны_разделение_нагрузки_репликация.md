# Паттерны разделения нагрузки в PostgreSQL: репликация, Read/Write Separation, CQRS, Materialized Views, кэширование, шардирование

Обзор системных паттернов, которые отвечают на один вопрос: **как обслуживать больше запросов, чем может один сервер PostgreSQL**. Паттерны расположены от простого к сложному; в конце — сводная таблица выбора.

---

## 1. Read/Write Separation (разделение чтения и записи)

### Когда применять

- Приложение выполняет **намного больше чтений, чем записей** (типично для веб‑сервисов: соотношение 10:1 и выше).
- Один сервер PostgreSQL (primary) перестаёт справляться: CPU в 100%, растут задержки.
- Тяжёлые аналитические запросы (отчёты, выгрузки) мешают OLTP‑трафику.

### Суть

Все **записи** идут на единственный **primary**. PostgreSQL непрерывно пересылает данные из WAL (write-ahead-log) на **реплики** (standby), которые применяют изменения и обслуживают **только чтение**. Роутинг выполняет приложение, ORM или прокси (PgBouncer, HAProxy, облачные endpoint'ы).

### Схема работы

```
                    ┌──────────────────────────────┐
   Клиенты ───────► │  Роутинг (app / ORM / proxy) │
                    └───────┬──────────────┬───────┘
                     WRITE  │              │  READ
                            ▼              ▼
                    ┌──────────────┐  ┌──────────────┐
                    │   PRIMARY    │  │  REPLICA 1   │
                    │  (RW, WAL)   │  │     (RO)     │
                    └──────┬───────┘  └──────────────┘
                           │ WAL stream      ▲
                           ├─────────────────┘
                           ▼
                    ┌──────────────┐
                    │  REPLICA 2   │   (аналитическая,
                    │     (RO)     │    отчёты, бэкапы)
                    └──────────────┘
```

### Реализация в PostgreSQL

```sql
-- Слот репликации и мониторинг отставания
SELECT * FROM pg_create_physical_replication_slot('replica_1_slot');

SELECT client_addr, state, sync_state,
       write_lag, replay_lag,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag_bytes
FROM pg_stat_replication;
```

Виды репликации:

- **Физическая (streaming)** — копируется весь кластер побайтово; реплика идентична primary. Простая и быстрая, но «всё или ничего».
- **Логическая (publication/subscription)** — реплицируются отдельные таблицы, возможна фильтрация строк/колонок (PG 15+), работа между разными мажорными версиями:

```sql
-- На издателе
CREATE PUBLICATION orders_pub FOR TABLE orders WHERE (region = 'eu');
-- На подписчике
CREATE SUBSCRIPTION orders_sub
    CONNECTION 'host=primary dbname=shop user=replicator'
    PUBLICATION orders_pub;
```

- **Каскадная** — реплика сама раздаёт WAL дальше (снимает нагрузку с primary при большом числе реплик).
- **Синхронная vs асинхронная** — `synchronous_commit = remote_apply` гарантирует, что запись видна на реплике до ответа клиенту (durability ценой latency).

### Проблемы, которые решает

1. Масштабирование чтения почти линейно по числу реплик.
2. Изоляция аналитики от OLTP.
3. Отказоустойчивость: реплика готова к promotion.

### Недостатки

1. **Replication lag → eventual consistency.** Клиент записал и, прочитав с реплики, не видит свою запись (read‑your‑writes). Решения: sticky read на primary после записи, проверка LSN, синхронная репликация.
2. **Запись не масштабируется** — primary остаётся единственной точкой записи.
3. **Split‑brain** при автоматическом failover без кворума (нужны Patroni/etcd, фенсинг).
4. Забытые слоты репликации копят WAL до переполнения диска primary.
5. `hot_standby`‑конфликты: длинные SELECT на реплике отменяются применяемым WAL.

## 2. CQRS (Command Query Responsibility Segregation)

### Когда применять

- Модель данных для записи (нормализованная, транзакционная) принципиально отличается от модели для чтения (денормализованная, под конкретные экраны/отчёты).
- Read/Write Separation уже есть, но запросы на чтение всё равно тяжёлые: десятки JOIN, агрегации на лету.
- Разным типам чтения нужны разные хранилища (OLTP-база + поисковый индекс + витрина).

### Суть

Следующий шаг после Read/Write Separation — разделить не только **трафик**, но и **модели данных**:

- **Command side (write model)** — нормализованные таблицы, валидация бизнес‑правил, транзакции. Оптимизирована под корректность записи.
- **Query side (read model)** — отдельные денормализованные структуры, заточенные под конкретные запросы. Оптимизированы под скорость чтения.

Между ними — **канал синхронизации**: CDC по WAL, события приложения, триггеры или периодический rebuild.

### Схема работы

```
            Команды (INSERT/UPDATE/DELETE)          Запросы (SELECT)
                    │                                     ▲
                    ▼                                     │
            ┌───────────────┐   синхронизация   ┌────────┴────────┐
            │  WRITE MODEL  │ ────────────────► │   READ MODEL    │
            │ нормализована │  (CDC по WAL /    │ денормализована │
            │  PostgreSQL   │   события / MV)   │ (MV, витрины,   │
            └───────────────┘                   │  Elastic, Redis)│
                                                └─────────────────┘
```

Важно: CQRS **не требует** двух разных СУБД. Частый минимум в PostgreSQL — одна база, где read model реализована **материализованными представлениями** или отдельными витринными таблицами.

### Проблемы, которые решает

1. Чтение и запись масштабируются и оптимизируются **независимо**.
2. Сложные отчёты не конкурируют с транзакциями и не требуют JOIN на лету.
3. Можно эволюционировать схемы записи и чтения раздельно.

### Недостатки

1. **Eventual consistency между моделями** — read model отстаёт; это надо учитывать в UX («данные обновятся в течение минуты»).
2. Двойная схема = двойная работа: миграции, мониторинг, тесты ×2.
3. Нужен надёжный канал синхронизации (см. файл про переливку данных: CDC, Outbox).
4. Для простых CRUD‑приложений — избыточная сложность.

## 3. Materialized View как read model

### Когда применять

- Нужны быстрые выборки по тяжёлой агрегации/JOIN, а данные допускают **небольшую устарелость** (секунды–часы).
- Хочется CQRS‑эффекта без выноса read model в отдельную систему.

### Суть

`MATERIALIZED VIEW` — это результат запроса, **физически сохранённый** как таблица. Читается мгновенно (это уже не запрос, а скан готовых данных), обновляется отдельной командой `REFRESH`.

### Пример

```sql
CREATE MATERIALIZED VIEW mv_sales_daily AS
SELECT date_trunc('day', created_at) AS day,
       region,
       count(*)            AS orders_cnt,
       sum(amount)         AS revenue
FROM orders
GROUP BY 1, 2;

-- Уникальный индекс нужен для CONCURRENTLY-обновления
CREATE UNIQUE INDEX ON mv_sales_daily (day, region);

-- Обновление БЕЗ блокировки чтения (старая версия доступна во время refresh)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_sales_daily;
```

### Схема работы

```
orders (OLTP) ──расчёт──► REFRESH (cron / pg_cron / триггер-событие)
                              │
                              ▼
                    mv_sales_daily ──► SELECT занимает миллисекунды
```

### Проблемы, которые решает

1. Убирает повторяющиеся тяжёлые вычисления из горячего пути чтения.
2. Простая реализация read model внутри одной БД — «CQRS для бедных».

### Недостатки

1. **Данные устаревают** между refresh — не подходит для данных, требующих актуальности.
2. Полный `REFRESH` пересчитывает всё (нет встроенного инкрементального обновления; обходные пути — pg_ivm, собственные дельта‑таблицы, партиционные витрины).
3. `REFRESH` без `CONCURRENTLY` блокирует чтение.
4. Рост числа MV усложняет сопровождение: зависимости, время обновления, диск.

## 4. Кэширование перед БД (Cache-Aside, Read/Write-Through, Write-Behind)

### Суть

Самое агрессивное разделение нагрузки — вообще **не дойти до БД**: горячие данные кладутся в Redis/Memcached.

### Схема Cache-Aside (самый частый)

```
Чтение:  app ──► Redis ──hit──► ответ
               └──► miss ──► PostgreSQL ──► положить в Redis ──► ответ
Запись:  app ──► PostgreSQL ──► инвалидировать/обновить ключ в Redis
```

### Варианты

| Паттерн | Запись | Плюс | Минус |
| :--- | :--- | :--- | :--- |
| Cache‑Aside | в БД, кэш инвалидируется | простота, кэш не критичен | рассинхрон на окно TTL |
| Read/Write‑Through | через кэш-слой | кэш всегда консистентен | кэш-слой сложнее |
| Write‑Behind | в кэш, в БД — асинхронно | очень быстрые записи | риск потери при падении кэша |

### Недостатки

1. Инвалидация кэша — классическая «сложная задача»; возможны устаревшие данные.
2. Cache stampede (одновременный промах множества клиентов по одному ключу) — лечится lock'ом/`GETEX`+early refresh.
3. Ещё одна система в продакшене: память, мониторинг, отказоустойчивость.

## 5. Шардирование (Sharding)

### Когда применять

- Уперлись в предел **записи** одного primary или в размер одного диска — репликация уже не помогает (она масштабирует только чтение).

### Суть

Данные разрезаются по **ключу шардирования** (tenant_id, hash(user_id), гео) на независимые узлы; каждый шард — полноценный PostgreSQL (часто со своими репликами). В PostgreSQL-мире это Citus, либо шардирование на уровне приложения, либо партицирование с `postgres_fdw`.

### Схема

```
                ┌──────────────┐
   app ────────►│   Роутер /   │
                │  координатор │
                └──┬───┬───┬───┘
                   ▼   ▼   ▼
                ┌────┐┌────┐┌────┐
                │SH 1││SH 2││SH 3│   (у каждого свои реплики)
                └────┘└────┘└────┘
```

### Недостатки

1. Кросс‑шардовые JOIN и транзакции — дорого или невозможно.
2. Решардирование (добавление узла) — сложная миграция.
3. Ключ шардирования выбирается раз и навсегда; ошибка в выборе не лечится.

## Сводная таблица: какой паттерн когда

| Симптом | Паттерн | Что масштабирует | Цена |
| :--- | :--- | :--- | :--- |
| Много чтений, primary загружен | Read/Write Separation + реплики | чтение | lag, eventual consistency |
| Тяжёлые агрегации в горячем пути | Materialized View / витрины | чтение (конкретные запросы) | устаревание, refresh |
| Разные модели записи и чтения | CQRS | и чтение, и эволюцию схем | двойная схема, синхронизация |
| Повторяющиеся точечные чтения | Cache‑Aside (Redis) | чтение (горячие ключи) | инвалидация |
| Упёрлись в запись / объём | Шардирование | запись и объём | кросс‑шардовая сложность |

Паттерны комбинируются: типичный стек большого сервиса — primary + реплики (RW separation) + Redis (кэш) + витрины/MV (read models) + CDC в аналитическое хранилище.

## Чек-лист внедрения

- [ ] Сначала измерено: что именно перегружено — чтение, запись или конкретные запросы.
- [ ] Для read scaling подняты реплики, настроен мониторинг `pg_stat_replication`.
- [ ] Решена проблема read‑your‑writes (sticky read / LSN / sync replication).
- [ ] Тяжёлые отчёты вынесены в MV/витрины с расписанием refresh (pg_cron).
- [ ] Failover отработан и защищён от split‑brain.
