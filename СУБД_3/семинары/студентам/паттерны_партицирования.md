# Паттерн: партицирование больших таблиц (Table Partitioning) в PostgreSQL

## Когда применять

- Таблица выросла до **десятков миллионов строк / сотен гигабайт**: запросы, `VACUUM`, `ANALYZE`, построение индексов стали медленными.
- Данные имеют **естественную ось горизонтального разделения**: время (логи, события, заказы), регион, диапазон идентификаторов.
- Часто выполняются запросы вида «данные за последний месяц» или «удалить данные старше года».
- Нужно быстро **выгружать/удалять целые эпохи данных** без `DELETE` по миллионам строк.

## Суть паттерна

Одна логическая таблица разбивается на множество физических **партиций** (секций) по ключу партицирования. Приложение продолжает работать с одной таблицей, а PostgreSQL сам:

- **направляет** каждую строку в нужную партицию (partition routing);
- **отсекает** ненужные партиции при планировании запроса (partition pruning) — сканируются только релевантные секции.

PostgreSQL поддерживает декларативное партицирование трёх видов:

- **RANGE** — диапазоны значений (классика: партиция на каждый месяц);
- **LIST** — по списку дискретных значений (например, по регионам);
- **HASH** — равномерное распределение по остатку от деления хеша (когда оси разреза нет, но нужно размазать нагрузку).

## Схема работы

```
                    ┌─────────────────────────┐
   INSERT/SELECT ──►│  orders (партицированная│
                    │  таблица, без данных)   │
                    └───────────┬─────────────┘
              routing по дате заказа
        ┌───────────────┬───────┴────────┬──────────────┐
        ▼               ▼                ▼              ▼
┌───────────────┐ ┌───────────────┐ ┌────────────┐ ┌────────────┐
│ orders_2025_07│ │ orders_2025_08│ │orders_2025_│ │ orders_    │
│ (свои индексы)│ │ (свои индексы)│ │   09       │ │ default    │
└───────────────┘ └───────────────┘ └────────────┘ └────────────┘
```

### Пример: RANGE-партицирование по месяцам

```sql
CREATE TABLE orders (
    order_id    bigint GENERATED ALWAYS AS IDENTITY,
    customer_id bigint      NOT NULL,
    created_at  timestamptz NOT NULL,
    amount      numeric(12,2) NOT NULL
) PARTITION BY RANGE (created_at);
-- Внимание: первичный/уникальный ключ обязан включать ключ партицирования!

CREATE TABLE orders_2025_08 PARTITION OF orders
    FOR VALUES FROM ('2025-08-01') TO ('2025-09-01');

CREATE TABLE orders_2025_09 PARTITION OF orders
    FOR VALUES FROM ('2025-09-01') TO ('2025-10-01');

CREATE TABLE orders_default PARTITION OF orders DEFAULT;

CREATE INDEX ON orders_2025_09 (customer_id);  -- индексы — на каждой партиции
```

### Главная выгода: операции с эпохами — O(1)

```sql
-- Удаление старых данных: мгновенно, без VACUUM-мусора
ALTER TABLE orders DETACH PARTITION orders_2024_01;
DROP TABLE orders_2024_01;          -- или архив: pg_dump этой таблицы

-- Подключение заранее подготовленной партиции без блокировки данных
ALTER TABLE orders ATTACH PARTITION orders_2025_10
    FOR VALUES FROM ('2025-10-01') TO ('2025-11-01');
```

### Проверка отсечения партиций

```sql
EXPLAIN (COSTS OFF)
SELECT * FROM orders
WHERE created_at >= '2025-09-01' AND created_at < '2025-09-15';
-- В плане должна быть ТОЛЬКО orders_2025_09 (partition pruning).
-- Если в плане все партиции — предикат non-sargable или включён constraint_exclusion off.
```

## Какие проблемы решает

1. **Быстрые запросы по диапазону** — partition pruning заменяет скан гигантской таблицы сканом одной маленькой секции; индексы каждой партиции помещаются в память.
2. **Дешёвое удаление исторических данных** — `DETACH`/`DROP PARTITION` вместо `DELETE`, без bloat и тяжёлого `VACUUM`.
3. **Управляемое обслуживание** — `VACUUM`, `REINDEX`, бэкап можно делать попартиционно.
4. **Lifecycle-политики (ILM)** — старые партиции можно переносить на дешёвое хранилище (tablespaces) или выгружать в архив.
5. **Локальность данных** — LIST-партиции по региону упрощают соответствие требованиям хранения данных.

## Недостатки и подводные камни

1. **Уникальность только с ключом партицирования.** Нельзя создать глобальный `UNIQUE (order_id)`, если `order_id` не входит в ключ — приходится менять дизайн ключей или контролировать уникальность в приложении.
2. **Ограничения внешних ключей.** FK на партицированную таблицу поддерживаются с ограничениями; FK между партициями требуют аккуратности.
3. **Число партиций ограничено практикой.** Сотни партиций — нормально; тысячи — раздувают время планирования и каталог. Правило: «партиции — это десятки/сотни, не миллионы».
4. **Нет автоматического создания партиций из коробки** (до PG 17 — вручную, через pg_partman или cron-скрипты). Если забыть создать партицию на следующий месяц, данные упадут в `DEFAULT` и сломают pruning.
5. **«Горячая» партиция не исчезает.** Если вся нагрузка идёт в текущий месяц, партицирование само по себе не снижает write-нагрузку (это решают репликация и шардирование).
6. **Некоторые запросы ускоряются, другие — нет.** Запросы без условия по ключу партиционирования сканируют ВСЕ секции и могут стать даже медленнее, чем по монолитной таблице.
7. **Перепартицирование существующей огромной таблицы** — отдельная миграция: обычно создают новую партицированную таблицу и переливают данные (см. файл про паттерны переливки данных).

## Чек-лист внедрения

- [ ] Выбран ключ и стратегия (RANGE по времени — самый частый случай).
- [ ] Ключ партиционирования входит во все уникальные/первичные ключи.
- [ ] Настроено автоматическое создание будущих партиций (pg_partman / cron).
- [ ] Есть DEFAULT-партиция + мониторинг её размера (там не должно быть данных).
- [ ] Проверен `EXPLAIN`: partition pruning реально срабатывает на типовых запросах.
- [ ] Описана процедура архивации/удаления старых партиций.
