\## Q1. Уникальные рейсы и сортировка



\*\*1.1.\*\* С точки зрения итогового набора данных DISTINCT и GROUP BY по одному столбцу дают одно и то же, то есть список уникальных значений flight\_no. Разница в плане: DISTINCT оптимизатор обычно превращает в HashAggregate или Unique поверх сортировки. GROUP BY тоже идёт через HashAggregate или GroupAggregate. В PostgreSQL планы для таких запросов часто совпадают, потому что DISTINCT внутри переписывается в группировку. Различие в плане может появиться, если данных много и один из вариантов даёт возможность использовать индекс. Например, GROUP BY иногда эффективнее с индексом на flight\_no, а DISTINCT с HashAggregate. Но результат одинаковый.



\*\*1.2.\*\* ASC это поведение по умолчанию для ORDER BY, поэтому писать его явно не обязательно. Сортировка строк зависит от локали базы (collation). В стандартной локали C сортировка идёт по байтам: заглавные латинские буквы (A-Z) идут раньше строчных (a-z). Поэтому PG0001 окажется раньше pg0001, потому что P (0x50) меньше p (0x70). В локалях типа ru\_RU.UTF-8 или en\_US.UTF-8 порядок может быть другим, там сравнение идёт по правилам языка, и регистр может не влиять так сильно. То есть ответ зависит от collation базы.



\## Q2. Аэропорты и выручка за билеты



\*\*2.1.\*\* Если один пассажир купил два билета на один рейс (разные места), то в ticket\_flights будет две строки с одинаковым passenger\_id, но разными ticket\_no и seat\_no. SUM(amount) просуммирует обе суммы, выручка считается корректно, двойного счёта денег нет, это реальные две покупки. А вот COUNT(\*) посчитает две строки, то есть дважды учтёт одного пассажира. Если нужно именно количество уникальных пассажиров на рейсе, надо использовать COUNT(DISTINCT passenger\_id), а не COUNT(\*).



\*\*2.2.\*\* Если рейс есть в flights, но билетов на него нет, при INNER JOIN он вообще не попадёт в выборку, потому что нет совпадающих строк в ticket\_flights. Чтобы такой рейс остался с нулевой выручкой, нужен LEFT JOIN от flights к ticket\_flights: все строки из flights сохранятся, а на месте отсутствующих билетов будут NULL. Тогда COALESCE(SUM(amount), 0) даст 0. INNER JOIN тут не подходит именно потому, что он отбрасывает строки левой таблицы, для которых нет пары справа.



\## Q3. Отменённые рейсы и города



\*\*3.1.\*\* Ситуация: в airports есть аэропорт, которого нет в flights. По формулировке «города, из которых ни один рейс не был отправлен со статусом Cancelled», да, такой город должен попасть в результат: раз рейсов из него не было, то и отменённых среди них тоже не было. Через NOT IN это сработает, но с оговоркой (см. 3.2). Через NOT EXISTS тоже сработает и безопаснее:



SELECT DISTINCT a.city

FROM airports a

WHERE NOT EXISTS (

&#x20;   SELECT 1

&#x20;   FROM flights f

&#x20;   WHERE f.departure\_airport = a.airport\_code

&#x20;     AND f.status = 'Cancelled'

);



Внешний запрос идёт по всем аэропортам, включая те, у которых вообще нет рейсов. Для них подзапрос NOT EXISTS вернёт TRUE, и город останется.



\*\*3.2.\*\* Ловушка NOT IN с NULL: если подзапрос вернёт хотя бы одно значение NULL, то выражение city NOT IN (список с NULL) даёт UNKNOWN, а не TRUE. В SQL WHERE пропускает только строки, где условие истинно, поэтому весь результат окажется пустым. Пример:



SELECT DISTINCT a.city

FROM airports a

WHERE a.city NOT IN (

&#x20;   SELECT f.departure\_airport

&#x20;   FROM flights f

&#x20;   WHERE f.status = 'Cancelled'

);



Если среди departure\_airport есть NULL (например, у рейса не указан аэропорт вылета), NOT IN сломается. NOT EXISTS этой проблемы лишён: он проверяет, есть ли хоть одна строка, удовлетворяющая условию, и с NULL внутри подзапроса это работает корректно, потому что NULL просто не удовлетворяет условию status = 'Cancelled' и не попадает в рассмотрение.



\## Q4. Места на борту и дубликаты



\*\*4.1.\*\* Если у одного пассажира два посадочных талона на разные места, то при выборке пассажиров рейса он появится дважды. Чтобы получить уникальных пассажиров:



SELECT DISTINCT passenger\_id

FROM boardings

WHERE flight\_id = ...;



или



SELECT passenger\_id

FROM boardings

WHERE flight\_id = ...

GROUP BY passenger\_id;



По эффективности: GROUP BY и DISTINCT в PostgreSQL часто дают один и тот же план (HashAggregate). Если есть индекс на (flight\_id, passenger\_id), оба варианта могут использовать его для получения уникальных значений через Unique поверх Index Scan. На практике DISTINCT короче и читается проще, но GROUP BY удобнее, если потом надо добавить агрегаты (например, COUNT(\*) талонов на пассажира). Большой разницы в производительности нет.



\*\*4.2.\*\* Аномалия: пассажир сдал билет (его нет в ticket\_flights), но посадочный талон в boardings остался. Если запрос соединяет tickets с boardings через INNER JOIN, то пассажир не попадёт в список, не будет совпадающей строки в tickets или ticket\_flights. Если используется LEFT JOIN от tickets к boardings, он попадёт, но с NULL в полях билета. С точки зрения бизнес-логики, такой пассажир уже не должен считаться летящим: билет сдан, значит, посадочный талон недействителен. Поэтому правильнее использовать INNER JOIN, и аномалия автоматически отсеется. Это как раз хороший пример того, что JOIN сам по себе может работать как фильтр целостности.



\## Q5. DDL и блокировки на живой таблице



\*\*5.1.\*\* ALTER TABLE flights ADD COLUMN weather\_data JSONB; в PostgreSQL требует блокировку AccessExclusiveLock на таблицу flights. Она несовместима ни с чем, в том числе с AccessShareLock, который держит открытая транзакция с SELECT COUNT(\*) FROM flights;. Пока транзакция не завершится (COMMIT или ROLLBACK), ALTER TABLE будет ждать. Причём это не зависание, команда стоит в очереди на блокировку. И тут есть опасный побочный эффект: все последующие запросы к flights (даже обычные SELECT) встанут за ALTER TABLE в очередь, потому что PostgreSQL не пропускает их вперёд ожидающего AccessExclusiveLock. Это может положить всю работу с таблицей. Поэтому на проде такие команды делают в окно низкой нагрузки и предварительно проверяют, нет ли долгих транзакций (pg\_stat\_activity, pg\_locks).



\*\*5.2.\*\* В PostgreSQL 11+ ADD COLUMN ... DEFAULT const выполняется мгновенно, потому что значение по умолчанию не пишется в каждую строку физически. Вместо этого в системном каталоге (pg\_attribute) сохраняется ссылка на дефолтное выражение (attmissingval), и когда строка читается, PostgreSQL подставляет это значение на лету, если в физической версии строки колонки ещё нет. Таблица не переписывается, меняются только метаданные. Если потом изменить DEFAULT на true, то новый дефолт будет применяться только к новым INSERT. Уже существующие строки останутся с прежним значением по умолчанию (false), потому что оно уже привязано к ним через attmissingval. Чтобы поменять значения у старых строк, нужен явный UPDATE.



\*\*5.3.\*\* CREATE INDEX idx\_flights\_status ON flights(status); без CONCURRENTLY берёт ShareLock на таблицу. ShareLock разрешает другим сессиям читать (SELECT), но блокирует запись, все INSERT, UPDATE, DELETE ждут завершения построения индекса. На большой таблице построение может занять минуты и даже часы, и всё это время запись стоит. Чтобы не блокировать запись, используют:



CREATE INDEX CONCURRENTLY idx\_flights\_status ON flights(status);



CONCURRENTLY строит индекс в несколько проходов, не блокируя запись. Компромисс: строится дольше (примерно в 2-3 раза), требует отдельного сканирования таблицы, и если что-то пойдёт не так, останется invalid index, который надо удалять вручную. Поэтому CONCURRENTLY это не серебряная пуля, а инструмент для случаев, когда простой на запись недопустим. В оффлайн-окне, наоборот, быстрее и надёжнее обычный CREATE INDEX.



\## Q6. Агрегация и NULL в вычислениях



\*\*6.1.\*\* AVG(actual\_departure - scheduled\_departure) исключает строки, где actual\_departure или scheduled\_departure равны NULL. Любая арифметика с NULL даёт NULL, а агрегатные функции (кроме COUNT(\*)) игнорируют NULL. То есть отменённые рейсы (где actual\_departure IS NULL) в расчёт средней задержки не попадут вообще. Если таких рейсов много, средняя задержка окажется смещённой: считаем только по фактически выполненным рейсам, отменённые как бы не существуют. Иногда это то, что нужно, иногда нет. Если хочется учесть отменённые, надо явно обработать NULL: например, COALESCE(actual\_departure, scheduled\_departure) или отдельно считать долю отменённых.



\*\*6.2.\*\* COUNT(aircraft\_code) считает только не-NULL значения этого столбца. COUNT(\*) считает все строки. Если на aircraft\_code стоит NOT NULL, результаты совпадут. Если ограничения нет и в столбце есть NULL, то COUNT(aircraft\_code) будет меньше COUNT(\*). Это, кстати, хороший способ быстро проверить, есть ли NULL в столбце: сравнить два счётчика.
