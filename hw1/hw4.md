NOT EXISTS использует Anti Join, что эффективнее, чем NOT IN, потому что не требует материализации подзапроса и корректно обрабатывает NULL. Сравните время: NOT EXISTS ~0.2 мс, NOT IN ~0.3 мс. При наличии NULL в подзапросе NOT IN вернул бы пустой результат.



ANTI-JOIN (NOT IN vs NOT EXISTS):
NOT IN опасен. Если в подзапросе вернется хотя бы один NULL, результат всего запроса станет пустым из-за трехзначной логики SQL.
NOT EXISTS безопасен и преобразуется в эффективный Hash Anti Join.
Index Only Scan (Покрывающие индексы):
Чтобы СУБД не ходила в таблицу, все запрашиваемые поля должны быть в индексе: CREATE INDEX idx ON table (col_a) INCLUDE (col_b);
Работает только если VACUUM обновил Visibility Map (страницы таблицы помечены как полностью видимые). Если Heap Fetches > 0 в плане, значит СУБД все равно ходила в таблицу проверять видимость строк.

До создания индекса использовался Seq Scan (последовательное сканирование всей таблицы flights). PostgreSQL читал все страницы с диска/кэша и группировал данные через HashAggregate.

После создания индекса idx_flights_status и выполнения VACUUM планировщик переключился на Index Only Scan — это видно в строке Index Only Scan using idx_flights_status on flights. Ключевое значение Heap Fetches: 0 означает, что ни разу не пришлось обращаться к самой таблице — все нужные данные (значения status) взяты напрямую из индекса. Это стало возможным благодаря Visibility Map, которую обновил VACUUM.

Группировка выполняется через GroupAggregate (память 39 КБ). Данные практически полностью из кэша (shared hit=1 read=57). Время выполнения: 0.039 мс — запрос стал быстрее, чем при Seq Scan.

Вывод: Index Only Scan значительно ускоряет запрос, потому что исключает обращение к таблице (heap). Это критически важно для больших таблиц, где чтение всех страниц с диска занимает много времени.

LUP создаёт дополнительную строку, где month = NULL — это и есть общий итог.

Как HAVING работает с ROLLUP:
HAVING фильтрует уже сгруппированные строки. Обычное условие SUM(amount) > 10000000000 отфильтровало бы итоговую строку, потому что у неё month = NULL, а NULL > 10000000000 = UNKNOWN (не TRUE, не FALSE). Поэтому в HAVING добавлено OR EXTRACT(MONTH FROM ...) IS NULL — это позволяет итоговой строке пройти фильтр. В плане видно Rows Removed by Filter: 2 — значит, два месяца не прошли порог в 10 млрд, но итоговая строка осталась.

План выполнения: используется MixedAggregate (специальный тип для ROLLUP) с группировкой по Hash Key: EXTRACT(MONTH FROM ...). Сортировка через quicksort (25 КБ). Буферы: shared hit=1208, read=19304 — часть данных из кэша, часть с диска. Время выполнения: 5006 мс (5 секунд).

Анализ доп. задачи 3 (Sargability):

Неоптимизированный запрос использует EXTRACT(DOW FROM actual_departure) IN (0, 6) — функция применяется к колонке. Это нарушает SARGability: индекс по actual_departure не может быть использован, потому что базе нужно вычислить функцию для каждой строки. В плане виден Seq Scan и большое количество прочитанных строк.

Оптимизированный запрос заменяет функцию на диапазоны дат: actual_departure >= '...' AND actual_departure < '...'. Колонка стоит «голая», поэтому индекс по actual_departure может использоваться. В плане это отражается как Index Scan (или Bitmap Index Scan), что читает меньше страниц и работает быстрее.

Разница в планах: в плохом запросе — Seq Scan с фильтром по функции; в хорошем — Index Scan с диапазонным поиском. Оптимизированный запрос выполняется быстрее и читает меньше буферов.
