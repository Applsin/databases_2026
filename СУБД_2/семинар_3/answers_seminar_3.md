# Домашнее задание (Семинар 3)

## Q1. Уникальные рейсы и сортировка

### 1. `DISTINCT` и `GROUP BY`

Запросы

```sql
SELECT DISTINCT flight_no
FROM flights
ORDER BY flight_no;
```

и

```sql
SELECT flight_no
FROM flights
GROUP BY flight_no
ORDER BY flight_no;
```

в данном случае дадут одинаковый итоговый набор данных. Оба запроса оставляют только уникальные значения `flight_no` и сортируют их по возрастанию.

Но физический план выполнения (`EXPLAIN`) теоретически может отличаться. PostgreSQL сам выбирает план, поэтому в одном случае может использоваться один способ удаления дубликатов, а в другом другой. Например, это может быть `HashAggregate`, `GroupAggregate` или сортировка с удалением одинаковых значений.

То есть результат для пользователя будет одинаковый, но способ его получения внутри БД не обязательно один и тот же.

### 2. Почему `ASC` можно не писать

`ASC` является направлением сортировки по умолчанию в PostgreSQL. Поэтому

```sql
ORDER BY flight_no
```

и

```sql
ORDER BY flight_no ASC
```

по смыслу одинаковые.

Если в `flight_no` есть символы разного регистра, например `'PG0001'` и `'pg0001'`, то это разные строки. Точный порядок при сортировке зависит от используемой локали и collation. Поэтому нельзя просто считать, что PostgreSQL всегда поставит большие буквы перед маленькими.

## Q2. Аэропорты и выручка за билеты

### 1. Два билета одного пассажира

Если один пассажир купил два билета на один рейс, например два разных места, то в `ticket_flights` будет две строки.

Поэтому если использовать:

```sql
COUNT(*)
```

то эти две строки будут посчитаны как два пассажира. На самом деле пассажир один, поэтому для подсчета именно уникальных пассажиров правильнее использовать:

```sql
COUNT(DISTINCT passenger_id)
```

А `SUM(amount)` при этом будет считать стоимость обоих билетов, что как раз нужно для расчета общей выручки.

### 2. Рейс без проданных билетов

Если использовать `INNER JOIN` между `flights` и `ticket_flights`, то рейс без билетов вообще не попадет в результат. Это потому что `INNER JOIN` оставляет только строки, для которых нашлось соответствие в обеих таблицах.

Здесь нужен `LEFT JOIN`:

```sql
FROM flights f
LEFT JOIN ticket_flights tf
    ON tf.flight_id = f.flight_id
```

Тогда рейс из `flights` останется в результате даже если билетов нет.

Для нулевой выручки удобно использовать:

```sql
COALESCE(SUM(tf.amount), 0)
```

То есть рейс есть → показываем его, билетов нет → сумма `0`.

## Q3. Отмененные рейсы и города

### 1. Аэропорт, который вообще не встречается в `flights`

Если в `airports` есть аэропорт, из которого вообще никогда не выполнялись рейсы, то он не должен считаться аэропортом, из которого был отмененный рейс. Поэтому такой город тоже должен попасть в результат.

Удобно использовать `NOT EXISTS`:

```sql
SELECT a.city
FROM airports a
WHERE NOT EXISTS (
    SELECT 1
    FROM flights f
    WHERE f.departure_airport = a.airport_code
      AND f.status = 'Cancelled'
);
```

Для каждого аэропорта проверяем: существует ли хотя бы один отмененный рейс из него.

Если такого рейса нет, аэропорт остается в результате. Поэтому аэропорт без единого рейса тоже попадет в выборку.

### 2. Проблема `NOT IN` и `NULL`

Конструкция типа

```sql
city NOT IN (
    SELECT departure_airport
    FROM flights
    WHERE status = 'Cancelled'
)
```

может дать неожиданный результат, если подзапрос вернет `NULL`.

`NOT IN` фактически проверяет, что значение не равно ни одному значению из списка. При наличии `NULL` сравнение с ним дает `UNKNOWN`, а не `TRUE` или `FALSE`.

Например, условие логически содержит что-то вроде:

```text
city <> 'MOW'
AND city <> 'LED'
AND city <> NULL
```

Последняя часть дает `UNKNOWN`, поэтому строка не проходит условие `WHERE`.

`NOT EXISTS` этой проблемы не имеет, потому что он просто проверяет наличие подходящей строки:

```sql
WHERE NOT EXISTS (
    SELECT 1
    FROM flights f
    WHERE f.departure_airport = a.airport_code
      AND f.status = 'Cancelled'
)
```

Если подходящей строки нет — условие истинно. Поэтому для такой задачи `NOT EXISTS` надежнее.

## Q4. Места на борту и дубликаты

### 1. Два посадочных талона одного пассажира

Если один пассажир по ошибке получил два посадочных талона на одном рейсе, то после `JOIN` таблицы `boardings` могут появиться две строки с одним и тем же `passenger_id`.

Если нужны именно уникальные пассажиры, можно использовать:

```sql
SELECT DISTINCT passenger_id
FROM boardings;
```

или:

```sql
SELECT passenger_id
FROM boardings
GROUP BY passenger_id;
```

В данном случае оба варианта дадут одинаковый результат.

По производительности нельзя сказать, что `DISTINCT` всегда быстрее или всегда медленнее `GROUP BY`. PostgreSQL сам выбирает план выполнения. Для обоих запросов может использоваться сортировка или хеширование.

Если нам просто нужно убрать дубликаты, я бы использовал `DISTINCT`, потому что по смыслу запроса сразу понятно, что нужны уникальные пассажиры. `GROUP BY` больше нужен, когда вместе с группировкой мы еще считаем `COUNT`, `SUM` и т.д.

### 2. Есть boarding, но нет билета

Если пассажира нет в `ticket_flights`, но запись о посадочном талоне в `boardings` существует, то результат зависит от типа `JOIN`.

Если запрос построен через `INNER JOIN`, например:

```sql
FROM ticket_flights tf
JOIN boardings b
    ON b.ticket_no = tf.ticket_no
```

то такой пассажир не попадет в результат, потому что соответствующей строки в `ticket_flights` нет.

Если же начать запрос с `boardings` и использовать `LEFT JOIN` к `ticket_flights`, тогда пассажир может попасть в результат, а поля из `ticket_flights` будут `NULL`.

Поэтому тут важно не только какие таблицы соединяем, но и какой `JOIN` используется.

## Q5. DDL и блокировки на живой таблице

### 1. `ALTER TABLE` во время долгого `SELECT`

Если один пользователь выполняет:

```sql
BEGIN;

SELECT COUNT(*)
FROM flights;
```

то на таблицу берется блокировка `ACCESS SHARE`.

Когда второй пользователь запускает:

```sql
ALTER TABLE flights
ADD COLUMN weather_data JSONB;
```

PostgreSQL должен получить более сильную блокировку — `ACCESS EXCLUSIVE`.

Она конфликтует с `ACCESS SHARE`, поэтому `ALTER TABLE` не сможет выполниться сразу.

Получается примерно так:

```text
Пользователь 1:
BEGIN
SELECT COUNT(*) FROM flights;
        ↓
держит ACCESS SHARE

Пользователь 2:
ALTER TABLE flights ...
        ↓
ждет ACCESS EXCLUSIVE
```

Пока первая транзакция не закончится и не отпустит свою блокировку, `ALTER TABLE` будет ждать.

### 2. `DEFAULT false` без переписывания всей таблицы

В PostgreSQL 11+ добавление колонки с постоянным значением `DEFAULT`, например:

```sql
ALTER TABLE flights
ADD COLUMN is_delayed BOOLEAN DEFAULT false;
```

может выполняться очень быстро без физического переписывания всей таблицы.

PostgreSQL сохраняет значение default в системном каталоге и может считать, что старые строки имеют это значение, не записывая `false` отдельно в каждую строку.

Если потом выполнить:

```sql
ALTER TABLE flights
ALTER COLUMN is_delayed SET DEFAULT true;
```

это изменит значение default для новых вставок. Старые строки при этом не станут `true`.

Получится примерно так:

```text
старые строки → false
новые INSERT после изменения DEFAULT → true
```

При параллельных `INSERT` PostgreSQL сам обеспечивает согласованность DDL и DML: после изменения default новые вставки используют уже новое значение.

### 3. Обычный индекс и `CREATE INDEX CONCURRENTLY`

Обычная команда:

```sql
CREATE INDEX idx_flights_status
ON flights(status);
```

во время построения индекса блокирует изменения таблицы на соответствующих этапах. Поэтому `INSERT`, `UPDATE` и `DELETE` могут ждать.

Для production-таблицы можно использовать:

```sql
CREATE INDEX CONCURRENTLY idx_flights_status
ON flights(status);
```

`CONCURRENTLY` позволяет строить индекс без блокировки, которая полностью останавливает запись в таблицу.

Но есть компромисс: такой индекс строится дольше, требует больше ресурсов и выполняется в несколько этапов. Поэтому `CONCURRENTLY` особенно полезен для больших и активно используемых таблиц, но не всегда является самым удобным вариантом.

## Q6. Агрегация и NULL в вычислениях

### 1. `AVG` и отмененные рейсы

Если написать:

```sql
SELECT AVG(actual_departure - scheduled_departure)
FROM flights;
```

то строки, в которых `actual_departure` равен `NULL`, не будут участвовать в вычислении.

Потому что:

```sql
NULL - scheduled_departure
```

дает `NULL`, а агрегатная функция `AVG` игнорирует `NULL`.

Например, если задержки получились:

```text
10 минут
20 минут
NULL
30 минут
```

то среднее будет:

```text
(10 + 20 + 30) / 3 = 20 минут
```

а не деление на 4.

То есть отмененные рейсы не учитываются в среднем. Если таких рейсов много, среднее показывает задержку только тех рейсов, у которых есть `actual_departure`.

### 2. `COUNT(aircraft_code)` и `COUNT(*)`

Эти запросы:

```sql
SELECT COUNT(aircraft_code)
FROM flights;
```

и

```sql
SELECT COUNT(*)
FROM flights;
```

могут дать разные результаты.

`COUNT(*)` считает все строки таблицы, включая строки, где `aircraft_code IS NULL`.

А `COUNT(aircraft_code)` считает только строки, где `aircraft_code` не равен `NULL`.

Например, если в таблице 100 рейсов и у 3 из них `aircraft_code` отсутствует:

```text
COUNT(*)             = 100
COUNT(aircraft_code) = 97
```

Если же на уровне схемы у `aircraft_code` стоит `NOT NULL`, то `NULL` там быть не может и результаты будут одинаковыми.

То есть всё зависит от ограничения таблицы: если `NOT NULL` нет, разница возможна.
