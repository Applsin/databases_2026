Q1 (Уникальные рейсы и сортировка)
1. SELECT DISTINCT flight_no и SELECT flight_no... GROUP BY flight_no дают одинаковый итоговый набор - уникальные значения flight_no, отсортированные по возрастанию. Семантически DISTINCT убирает дубликаты, GROUP BY группирует строки. Физический план может различаться DISTINCT чаще использует HashAggregate, а GROUP BY — GroupAggregate или HashAggregate. Для одного столбца без подсчётов это одно и то же. Внутри база может выполнять их по-разному, но результат всегда одинаковый.
2. ORDER BY flight_no работает без ASC, потому что ASC- это порядок по умолчанию, его можно не писать. Если в данных есть 'PG0001' и 'pg0001', то при сортировке всё зависит от настроек базы: в одних настройках заглавные буквы идут раньше строчных, в других они считаются одинаковыми, и порядок между ними может быть любым
Q2 (Аэропорты и выручка за билеты)
1. Если один пассажир купил два билета на один рейс, то SUM(amount) посчитает выручку правильно  - сложит обе суммы. А COUNT(*) посчитает две строки, то есть два билета, а не одного пассажира. Это ошибка -пассажир посчитается дважды. Чтобы посчитать именно людей, нужно писать COUNT(DISTINCT passenger_id) — тогда один пассажир посчитается один раз, даже если у него два билета
2. Если у рейса нет билетов, то INNER JOIN не покажет этот рейс вообще. Чтобы рейс попал в результат с нулевой выручкой, нужно использовать LEFT JOIN - он оставляет все рейсы, даже без билетов. 
Q3 (Отмененные рейсы и города)
1. Аэропорт, которого нет в flights, должен попасть в результат, потому что из него не было рейсов, значит, не было и отменённых. Чтобы этого добиться, нужно использовать NOT EXISTS, а не NOT IN
SELECT a.city
FROM airports a
WHERE NOT EXISTS (
    SELECT 1
    FROM flights f
    WHERE f.departure_airport = a.airport_code
      AND f.status = 'Cancelled '
);
NOT EXISTS проверяет, есть ли хотя бы один отменённый рейс из этого аэропорта. Если рейсов нет вообще - подзапрос вернёт ноль строк, NOT EXISTS даст истину, и город попадёт в результат.
2. city NOT IN (SELECT departure_airport ... WHERE status = 'Cancelled') может вернуть пустой результат, потому что NOT IN работает как цепочка сравнений !=. Если в подзапросе есть хотя бы один NULL, то сравнение city != NULL даёт не ложь, а неизвестно, и строка не проходит фильтр. Если таких NULL достаточно, результат окажется пустым.
У NOT EXISTS этой проблемы нет, потому что он не сравнивает значения, а проверяет наличие строк. NULL в данных ему не мешает.
Q4 (Места на борту и дубликаты)
1. Для вывода уникальных пассажиров можно использовать и DISTINCT, и GROUP BY - результат одинаковый, и внутри база часто делает одно и то же. DISTINCT проще писать, GROUP BY удобнее, если потом нужно что-то посчитать.

Q5 (DDL и блокировки на живой таблице)
1. Если один пользователь держит открытую транзакцию с SELECT, а в это время делается ALTER TABLE ... ADD COLUMN, то ALTER TABLE зависнет. Он попытается заблокировать всю таблицу, а эта блокировка несовместима с той, которую держит SELECT. Необходимо будет ждать, когда пользователь завершит транзакцию.
2. В PostgreSQL 11 и новее добавление колонки со значением по умолчанию выполняется мгновенно, потому что значение по умолчанию записывается в системный каталог, а не в каждую строку. Старые строки получают это значение при чтении, новые — сразу при вставке. Если потом изменить значение по умолчанию, старые строки останутся с прежним значением, а новые будут получать новое.
3. CREATE INDEX без CONCURRENTLY блокирует вставку, обновление и удаление, потому что накладывает блокировку на таблицу. Чтобы не блокировать запись, нужно использовать CREATE INDEX CONCURRENTLY. Но он работает дольше, требует отдельного прохода и не может выполняться внутри транзакции
