## 0. Кто, зачем и когда использует PL/pgSQL (5 мин, в начале теории)

**Кто чаще всего пишет на PL/pgSQL?**
- **Администраторы баз данных (DBA)** — автоматизация обслуживания, архивирование, перестроение индексов, сбор статистики.
- **Архитекторы данных / Data Engineers** — ETL-процедуры, трансформация данных внутри хранилища.
- **Бэкенд-разработчики в монолитах** — вынос критичной по производительности логики ближе к данным.
- **DevOps/SRE** — скрипты мониторинга, обёртки над `pg_stat_*` и `pg_locks`.

**Зачем?**  
PL/pgSQL позволяет выполнять логику **внутри процесса PostgreSQL**, рядом с данными, избегая тысяч сетевых round-trips. Главные сценарии:
- **Аудит и 152-ФЗ:** триггеры логируют каждое изменение, даже если оно сделано в обход API.
- **Пакетная обработка:** процедуры с контролем транзакций (например, удаление старых партиций порциями).
- **Инкапсуляция доступа:** `SECURITY DEFINER` функции дают пользователям ровно те данные, которые нужны, без прямого доступа к таблицам.
- **Кастомная логика в индексах/ограничениях:** функции `IMMUTABLE` для GiST-индексов, вычисляемых полей и сложных `CHECK`.

**Когда не надо:**  
Бизнес-правила, сложные расчёты, взаимодействие с внешними сервисами, оркестрация микросервисов — всё это должно оставаться в прикладном коде. Хранимый код — инструмент для инфраструктурного слоя и работы с данными, а не для предметной логики.

## 2. Теоретическая вставка (25 мин)

### 2.1 Как работает PL/pgSQL
PL/pgSQL — блочно-ориентированный императивный язык внутри PostgreSQL. При первом вызове в сессии текст функции разбирается в синтаксическое дерево, которое кэшируется в хэш-таблице сессии. Это не байт-код, а внутреннее представление, которое затем интерпретируется. Главный выигрыш — **локальность данных**: вычисления происходят в том же процессе, где лежат данные, без сетевых обменов.

### 2.2 Функции vs Процедуры (детали и ограничения)

| Характеристика               | Функция (`CREATE FUNCTION`)                  | Процедура (`CREATE PROCEDURE`)           |
|------------------------------|----------------------------------------------|------------------------------------------|
| Вызов                        | Внутри `SELECT`, `FROM`, выражений           | `CALL proc(...)`                         |
| Возврат значения             | Обязан (может быть `VOID`)                   | Не возвращает напрямую; с PG14 можно вернуть значения через `OUT`-параметры |
| Управление транзакциями      | Запрещено                                    | Разрешено (`COMMIT`, `ROLLBACK`)         |
| Использование в запросах     | Да                                           | Нет                                      |

**Ключевые ограничения процедурных транзакций:**
- `COMMIT`/`ROLLBACK` работают **только если `CALL` выполняется вне явного блока транзакции**. В psql с автокоммитом — работает. В приложении с `BEGIN; CALL ...; COMMIT;` — получите `ERROR: invalid transaction termination`.
- Управление транзакциями в процедурах доступно с PostgreSQL 11 (в функциях оно запрещено по-прежнему). Работает оно только в «неатомарном» контексте вызова: `CALL` не должен выполняться внутри явной транзакции или из тела функции. Отдельных ключевых слов `ATOMIC`/`NONATOMIC` в синтаксисе `CREATE PROCEDURE` нет (проверено на PostgreSQL 16 — синтаксическая ошибка); не путайте с конструкцией `BEGIN ATOMIC … END` для SQL-функций, появившейся в PostgreSQL 14, — она к управлению транзакциями отношения не имеет.
- При `COMMIT` внутри процедуры закрываются все открытые курсоры, сбрасываются значения `DECLARE`-переменных.
- Если после `COMMIT` внутри процедуры происходит ошибка, предыдущие зафиксированные изменения остаются в базе — нельзя откатить всё.

### 2.3 Триггеры: полный арсенал

**Типы:**
- **`BEFORE`** — до записи. Можно изменить `NEW`, отменить операцию (`RAISE EXCEPTION`). Для автозаполнения полей и жёстких инвариантов.
- **`AFTER`** — после записи. Для аудита, уведомлений, обновления кэша. Возврат `NEW`/`OLD` игнорируется (можно возвращать `NULL`).
- **`INSTEAD OF`** — для представлений, переопределяет поведение.

**FOR EACH ROW vs FOR EACH STATEMENT (демонстрация):**
- `FOR EACH ROW` — функция вызывается **на каждую изменённую строку**. Доступны `NEW` и `OLD`. Идеален для аудита значений.
- `FOR EACH STATEMENT` — функция вызывается **один раз на SQL-оператор** (даже если затронуто много строк). `NEW` и `OLD` не определены (NULL). Хорош для логирования факта операции или инвалидации кэша.
- **Выбор:** если вам нужны старые и новые значения — только `ROW`. Если важна лишь метка «кто-то менял таблицу» — `STATEMENT` дешевле.

**Порядок выполнения:** алфавитный по имени триггера. Не полагайтесь на это в сложной логике.

**Наследование:** триггеры родительской таблицы наследуются дочерними, если не указано `ONLY`. Может привести к каскадным эффектам.

**Репликация:** на физическом стендбае триггеры **не выполняются** — изменения приезжают по WAL уже с учётом сработавших на мастере триггеров, а локальных записей на стендбае нет. На логическом подписчике триггеры по умолчанию не срабатывают (apply-воркер работает с `session_replication_role = 'replica'`); включить их можно через `ENABLE REPLICA` / `ENABLE ALWAYS` в `ALTER TABLE … ENABLE TRIGGER`.

### 2.4 Категории волатильности (VOLATILE / STABLE / IMMUTABLE)

- **`VOLATILE`** (по умолчанию) — может менять БД, выдавать разные результаты при одинаковых аргументах. Пересчитывается при каждом обращении. Нельзя в индексах.
- **`STABLE`** — не меняет данные, но зависит от состояния БД (например, `now()`). В рамках одного запроса гарантированно возвращает один результат для одинаковых аргументов (хотя физически может вычисляться несколько раз). В определениях индексов использовать нельзя, и условие со STABLE-функцией не даст Index Scan.
- **`IMMUTABLE`** — результат зависит только от аргументов. Идеально для чистых вычислений. Только IMMUTABLE-функции допускаются в выражениях индексов и позволяют планировщику использовать индекс по условию с функцией.

**Практическое правило:** всегда явно указывайте категорию. Функции, читающие таблицы — `STABLE`. Арифметические, строковые преобразования без SQL — `IMMUTABLE`.

### 2.5 SECURITY DEFINER и опасность search_path

**`SECURITY INVOKER`** (по умолчанию) — функция выполняется с правами вызывающего. Безопасно, если у пользователя есть доступ к объектам.
**`SECURITY DEFINER`** — функция выполняется с правами владельца. Позволяет дать доступ к данным через функцию, не давая прямых прав на таблицы.

**Уязвимость search_path (живая демонстрация):**
```sql
-- Шаг 1: злоумышленник создаёт функцию-обманку в схеме public
CREATE FUNCTION public.my_now() RETURNS timestamptz AS $$
BEGIN
    RETURN '2000-01-01'::timestamptz;
END;
$$ LANGUAGE plpgsql;

-- Шаг 2: администратор создаёт SECURITY DEFINER функцию без явного search_path
CREATE OR REPLACE FUNCTION get_sensitive_data()
RETURNS TABLE(data TEXT, ts timestamptz) AS $$
BEGIN
    RETURN QUERY SELECT 'secret', my_now();  -- my_now() без явной схемы!
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Шаг 3: обычный пользователь вызывает функцию и видит подменённую дату
SELECT * FROM get_sensitive_data();
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):**

```text
  data  |           ts           
--------+------------------------
 secret | 2000-01-01 00:00:00+00
```

*Почему вывод именно такой:* внутри `SECURITY DEFINER`-функции поиск `my_now()` идёт по `search_path` **вызывающей сессии** (в базе demo это `public, bookings`). Схема `public` просматривается раньше системного каталога-исключения, поэтому вместо «честной» функции подставляется обманка злоумышленника из `public`, и вместо текущего времени возвращается 1 января 2000 года.

**Защита:**
```sql
ALTER FUNCTION get_sensitive_data() SET search_path = pg_catalog, pg_temp;
```

После этого вызов падает с ошибкой `ERROR: function my_now() does not exist` — функция видит только системный каталог, где обманки нет (в реальном коде вместо подставной `my_now()` использовалась бы, например, `now()` из `pg_catalog`, и функция продолжила бы работать корректно). `pg_temp` должна быть последней, чтобы временные таблицы не могли перекрыть системные объекты. Никогда не доверяйте `public`.

### 2.6 Обработка ошибок и отладка *(справочно: устно не разбираем — отрабатывается руками в практикуме 3.5)*

**Блок EXCEPTION — дорогой savepoint:**  
Каждый `EXCEPTION` создаёт неявный savepoint перед началом блока. Это увеличивает потребление памяти, замедляет выполнение и удерживает блокировки до завершения блока. При частых ошибках — деградация производительности. По возможности проверяйте условия `IF` до того, как возникнет ошибка.

**Правильное логирование с GET STACKED DIAGNOSTICS (шаблон):**
```sql
EXCEPTION WHEN OTHERS THEN
    DECLARE
        err_detail TEXT;
        err_hint TEXT;
    BEGIN
        GET STACKED DIAGNOSTICS err_detail = PG_EXCEPTION_DETAIL,
                                err_hint = PG_EXCEPTION_HINT;
        INSERT INTO error_log(proc_name, error_msg, error_detail)
        VALUES ('my_proc', SQLERRM, COALESCE(err_detail, err_hint));
        RAISE; -- перевыбрасываем ошибку
    END;
```
**Важное ограничение:** лог-запись будет откачена, если внешняя транзакция откатится. Для гарантированного сохранения нужны автономные транзакции (через `dblink` или `pg_background`). В учебных целях допустимо простое логирование.

**Отладка:**
- `RAISE NOTICE 'var=%', var;` — трассировка.
- pgAdmin Debugger — пошаговое выполнение PL/pgSQL.
- `GET STACKED DIAGNOSTICS` — в продакшене.

### 2.7 Динамический SQL и защита от инъекций *(справочно: устно не разбираем — отрабатывается руками в практикуме 3.3)*

Если нужно построить запрос динамически (например, имя таблицы — параметр), используйте `EXECUTE` с функцией `format()`:

```sql
CREATE OR REPLACE FUNCTION count_rows(tbl_name text)
RETURNS bigint AS $$
DECLARE
    result bigint;
BEGIN
    -- %I экранирует идентификатор, %L — литерал
    EXECUTE format('SELECT count(*) FROM %I', tbl_name) INTO result;
    RETURN result;
END;
$$ LANGUAGE plpgsql STABLE;
```

Никогда не склеивайте строки с пользовательским вводом через `||` — это прямой путь к SQL-инъекциям.

### 2.8 Представления (VIEW) и материализованные представления (MATERIALIZED VIEW)

**Обычное представление — виртуальная таблица.** По учебнику (dbtech.txt, гл. 4.3.10):

> «Представление является виртуальной таблицей: имя представления можно использовать в запросах в тех же местах, где можно использовать имена таблиц, однако содержимое представления специфицируется запросом (оператором SELECT) и обычно не хранится в базе данных».

**Зачем нужны VIEW:**
- **Инкапсуляция сложных запросов:** «представления часто используются для того, чтобы записать сложные или часто встречающиеся подзапросы... представления можно рассматривать как некоторый аналог процедур или функций в императивных языках программирования» (dbtech.txt).
- **Изменение структуры и формата данных** для потребителя без изменения физической схемы.
- **Разграничение доступа:** дать роли доступ к представлению, не давая прав на базовые таблицы.

**Важно о производительности:** не следует думать, что представление полностью вычисляется при каждом запросе — «для вычисления результатов запроса могут быть нужны не все строки представления, а только небольшая их часть. Во многих случаях система управления базами данных в состоянии определить, какие именно строки представления необходимы... и не пытается вычислить остальные» (dbtech.txt).

**Обновляемые представления.** «В общем случае обновление представлений возможно только для ограниченного класса запросов... Смысл этих ограничений в том, что по строке представления должна однозначно вычисляться строка хранимой таблицы, к которой нужно применить обновление» (dbtech.txt). Простое представление над одной таблицей без агрегации обновляемо автоматически; `WITH CHECK OPTION` запрещает вставлять/изменять строки, не удовлетворяющие условию `WHERE` представления. Для расширения класса обновляемых представлений PostgreSQL предоставляет «механизм правил... и механизм триггеров INSTEAD OF, которые описывают действия, выполняемые при попытке обновления тех объектов, на которых такие триггеры определены» (dbtech.txt).

**Материализованное представление.** По учебнику (dbtech.txt, гл. 15.2.1):

> «В отличие от обычных представлений материализованные представления хранятся в базе данных как таблицы, но, в отличие от таблиц, их содержимое определяется запросом, как для обычных представлений».

- **Когда применять:** «в тех случаях, когда необходимо многократное повторение ресурсоемких вычислений (соединение нескольких таблиц и агрегирование)... наибольшая результативность достигается, если результаты вычислений оказываются значительно меньшими по объему, чем промежуточные результаты» (dbtech.txt). Запрос к построенному MV выполняется моментально.
- **Индексы:** «как и для таблиц, для материализованных представлений можно строить индексы» (dbtech.txt).
- **Актуализация:** данные MV **не обновляются автоматически** при изменении базовых таблиц. «В системе PostgreSQL для актуализации материализованных представлений предусмотрен оператор SQL REFRESH MATERIALIZED VIEW. Этот оператор полностью заменяет все данные... на результат нового вычисления запроса... при указании режима CONCURRENTLY доступ к материализованному представлению на чтение допускается» (dbtech.txt). Для `CONCURRENTLY` на MV должен существовать **уникальный индекс** без `WHERE`, покрывающий все строки.
- **Расписание и устаревание:** «обычно оператор актуализации... запускается автоматически на основе расписания, реализуемого средствами операционной системы (например, cron)... применять материализованные представления можно, только если использование устаревших данных явно или неявно допускается функциональными требованиями» (dbtech.txt). Типичный сценарий: отчётные витрины, обновляемые раз в сутки в часы наименьшей нагрузки.

**Сравнение:**

| Критерий | VIEW | MATERIALIZED VIEW |
|---|---|---|
| Хранение данных | Не хранит, запрос выполняется при обращении | Хранит результат запроса физически |
| Актуальность | Всегда актуальные данные | Могут устаревать до REFRESH |
| Скорость чтения | Скорость базового запроса | Моментальное чтение + индексы |
| Обновление через объект | Простые VIEW — да; сложные — через INSTEAD OF | Нет (только REFRESH) |
| Типичное применение | Инкапсуляция запросов, безопасность | Аналитические витрины, кэш агрегатов |

### 2.9 Триггеры в микросервисах: антипаттерны и best practices

**Антипаттерны:**
1. Бизнес-логика в триггерах (расчёт ставок, сложные проверки статусов).
2. Каскадные триггеры → дедлоки и невозможность отладки.
3. Внешние вызовы из триггеров (HTTP, Kafka) → нарушение консистентности при откате.
4. Тяжёлые триггеры на таблицах с частыми `ALTER TABLE`.

**Допустимо (best practices):**
- Аудит (152-ФЗ) — AFTER-триггеры.
- Автоматические `updated_at`, `created_at`.
- Жёсткие инварианты состояния (запрет удаления активного оборудования) — как часть инфраструктурной целостности.
- Простые уведомления через `pg_notify` (если слушатель внутри БД).

Теоретический арсенал разобран: мы знаем, чем функция отличается от процедуры, зачем нужны категории волатильности и чем опасен `SECURITY DEFINER` без явного `search_path`. Дальше каждый пункт этой теории закрепим работающим кодом: напишем функции всех трёх категорий, процедуру с `COMMIT`, триггеры аудита и представления — и будем сверять вывод с ожидаемым.

## 3. Практикум 1: Функции и процедуры (20 мин)

### 3.1 Скалярная функция с IMMUTABLE
```sql
CREATE OR REPLACE FUNCTION calculate_tax(amount NUMERIC, tax_rate NUMERIC DEFAULT 0.13)
RETURNS NUMERIC
AS $$
BEGIN
    IF amount < 0 THEN
        RAISE EXCEPTION 'Сумма не может быть отрицательной: %', amount;
    END IF;
    RETURN amount * tax_rate;
END;
$$ LANGUAGE plpgsql IMMUTABLE;

SELECT flight_id, amount, calculate_tax(amount) AS tax FROM ticket_flights;
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):**

```text
 flight_id |  amount  |    tax    
-----------+----------+-----------
         1 | 15000.00 | 1950.0000
         1 | 18000.50 | 2340.0650
         2 | 22000.00 | 2860.0000
(3 rows)
```

*Почему вывод именно такой:* функция вызывается один раз на строку `ticket_flights` и считает `amount * 0.13` (ставка по умолчанию). Тип `NUMERIC` не округляет результат: 18000.50 × 0.13 = 2340.0650 — четыре знака после запятой сохраняются, об этом стоит предупредить студентов, привыкших к «денежным» двум знакам. Пометка `IMMUTABLE` здесь корректна: результат зависит только от аргументов, обращений к таблицам нет.

### 3.2 Табличная функция STABLE
```sql
CREATE OR REPLACE FUNCTION get_flights_by_airport(p_airport_code VARCHAR)
RETURNS TABLE (flight_id INT, flight_no VARCHAR, scheduled_departure TIMESTAMP) AS $$
BEGIN
    RETURN QUERY
    SELECT f.flight_id, f.flight_no, f.scheduled_departure
    FROM flights f
    WHERE f.departure_airport = p_airport_code
    ORDER BY f.scheduled_departure DESC;
END;
$$ LANGUAGE plpgsql STABLE;

SELECT * FROM get_flights_by_airport('DME');
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):**

```text
 flight_id | flight_no | scheduled_departure 
-----------+-----------+---------------------
         2 | SU5678    | 2025-06-15 12:30:00
         1 | SU1234    | 2025-06-15 08:00:00
(2 rows)
```

*Почему вывод именно такой:* в `flights` два рейса из DME; `RETURN QUERY` возвращает результат вложенного `SELECT` как набор строк, а `ORDER BY … DESC` ставит более поздний рейс первым. Функция помечена `STABLE`, а не `IMMUTABLE`: она читает таблицу, поэтому результат зависит от состояния БД — честная маркировка позволяет планировщику не кэшировать результат между запросами.

### 3.3 Динамический SQL с защитой (5 минут)
```sql
CREATE OR REPLACE FUNCTION count_rows(tbl_name text)
RETURNS bigint AS $$
DECLARE
    result bigint;
BEGIN
    EXECUTE format('SELECT count(*) FROM %I', tbl_name) INTO result;
    RETURN result;
END;
$$ LANGUAGE plpgsql STABLE;

SELECT count_rows('flights');
```

Объясните: `%I` — идентификатор (кавычки), `%L` — литерал. Никаких слияний строк!

**Ожидаемый вывод (для преподавателя, проверено в Docker):** `count_rows` возвращает `3` — в учебной таблице `flights` три строки. Для контраста попросите студентов вызвать `count_rows('ticket_flights')` — получат тоже `3` (после вставки из практикума 6.2 станет `4`): `%I` подставляет имя таблицы как идентификатор, поэтому любая строка-параметр безопасна, но и ограничена: передать через `%I` условие `WHERE` нельзя — для значений служит `%L`.

### 3.4 Процедура с COMMIT (сжатая демонстрация)
```sql
CREATE OR REPLACE PROCEDURE bulk_insert_logs(p_count INT)
AS $$
DECLARE
    i INT;
BEGIN
    FOR i IN 1..p_count LOOP
        INSERT INTO iot_telemetry (sensor_id, temperature, reading_ts)
        VALUES ('PROC_TEST', random()*100, now());
        IF i % 1000 = 0 THEN
            COMMIT;
            RAISE NOTICE 'Закоммичено % строк', i;
        END IF;
    END LOOP;
    COMMIT;
END;
$$ LANGUAGE plpgsql;

-- В psql с AUTOCOMMIT ON:
CALL bulk_insert_logs(5000);
SELECT count(*) FROM iot_telemetry WHERE sensor_id = 'PROC_TEST'; -- 5000

-- А теперь ошибка в явной транзакции:
BEGIN;
CALL bulk_insert_logs(100); -- ERROR: invalid transaction termination
ROLLBACK;
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):**

```text
NOTICE:  Закоммичено 1000 строк
NOTICE:  Закоммичено 2000 строк
NOTICE:  Закоммичено 3000 строк
NOTICE:  Закоммичено 4000 строк
NOTICE:  Закоммичено 5000 строк
CALL
 count 
-------
  5000
```

А при `CALL` внутри явной транзакции: `ERROR: invalid transaction termination` с `CONTEXT: PL/pgSQL function bulk_insert_logs(integer) line 13 at COMMIT`.

*Почему вывод именно такой:* `COMMIT` срабатывает на каждой тысячной итерации — поэтому пять NOTICE и пять порций по 1000 строк, зафиксированных независимо; упади процедура на 4500-й строке, в базе остались бы первые 4000. В явной транзакции (`BEGIN; CALL …`) контекст вызова «атомарный», и PostgreSQL запрещает прерывать её изнутри процедуры — отсюда ошибка именно на строке с `COMMIT`. Напомните студентам связку с Семинаром 8: клиентские библиотеки (psycopg, SQLAlchemy) по умолчанию сами открывают транзакцию, поэтому из Python такую процедуру вызывают только с `autocommit=True`.

### 3.5 Отладка и обработка ошибок
```sql
CREATE OR REPLACE FUNCTION safe_divide(a NUMERIC, b NUMERIC)
RETURNS NUMERIC AS $$
BEGIN
    RAISE NOTICE 'Делим % на %', a, b;
    IF b = 0 THEN
        RAISE EXCEPTION 'Деление на ноль';
    END IF;
    RETURN a / b;
EXCEPTION WHEN OTHERS THEN
    DECLARE
        err_detail TEXT;
    BEGIN
        GET STACKED DIAGNOSTICS err_detail = PG_EXCEPTION_DETAIL;
        RAISE WARNING 'Ошибка: %, детали: %', SQLERRM, err_detail;
        RETURN NULL;
    END;
END;
$$ LANGUAGE plpgsql STABLE;

SELECT safe_divide(10, 0);
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):** сначала `NOTICE: Делим 10 на 0` (трассировка до точки отказа), затем `WARNING: Ошибка: Деление на ноль, детали:` — поле деталей пустое, потому что наш `RAISE EXCEPTION` не содержал `DETAIL`, — и запрос возвращает **NULL** (пустая ячейка). Для сравнения `SELECT safe_divide(10, 4);` вернёт `2.5000000000000000` — покажите студентам оба вызова.

*Почему вывод именно такой:* исключение перехватывается блоком `EXCEPTION WHEN OTHERS`, функция не падает, а возвращает `NULL` — вызывающий запрос завершается успешно. Это удобно для демонстрации, но в бою «проглатывание» ошибки опасно: вызывающий код не отличит NULL-результат от NULL-из-за-ошибки. Обсудите со студентами, когда правильнее дать функции упасть (и вспомните из теории, что `EXCEPTION`-блок — это неявный savepoint со своей ценой).

**Самостоятельное задание (3–5 мин, без подсказки):** напишите скалярную функцию `flight_label(p_flight_no VARCHAR, p_airport VARCHAR) RETURNS TEXT`, возвращающую строку вида `'SU1234 (DME)'`, пометьте её правильной категорией волатильности и выведите метки всех рейсов запросом `SELECT flight_label(flight_no, departure_airport) FROM flights;`.

**Проверьте себя:** решение — `CREATE OR REPLACE FUNCTION flight_label(p_flight_no VARCHAR, p_airport VARCHAR) RETURNS TEXT AS $$ BEGIN RETURN p_flight_no || ' (' || p_airport || ')'; END; $$ LANGUAGE plpgsql IMMUTABLE;`. Запрос вернёт три строки: `SU1234 (DME)`, `SU5678 (DME)`, `AB999 (SVO)`. Категория — `IMMUTABLE`: функция не читает таблицы, результат зависит только от аргументов. Типичная ошибка — пометить `STABLE`: не страшно, но это неточность, и такую функцию нельзя будет использовать в выражении индекса.

## 4. Практикум 2: AFTER-триггеры аудита (ROW + STATEMENT) (10 мин)

### 4.1 ROW-триггер для детального аудита
```sql
CREATE OR REPLACE FUNCTION log_application_changes_row()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'DELETE') THEN
        INSERT INTO audit_log (table_name, operation, old_data)
        VALUES (TG_TABLE_NAME, 'D', to_jsonb(OLD));
    ELSIF (TG_OP = 'UPDATE') THEN
        INSERT INTO audit_log (table_name, operation, old_data, new_data)
        VALUES (TG_TABLE_NAME, 'U', to_jsonb(OLD), to_jsonb(NEW));
    ELSIF (TG_OP = 'INSERT') THEN
        INSERT INTO audit_log (table_name, operation, new_data)
        VALUES (TG_TABLE_NAME, 'I', to_jsonb(NEW));
    END IF;
    RETURN NULL; -- AFTER триггер, возврат не важен
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_loan_row
AFTER INSERT OR UPDATE OR DELETE ON loan_applications
FOR EACH ROW EXECUTE FUNCTION log_application_changes_row();
```

### 4.2 STATEMENT-триггер для лёгкого логирования факта операции
```sql
CREATE OR REPLACE FUNCTION log_operation_statement()
RETURNS TRIGGER AS $$
BEGIN
    INSERT INTO audit_log (table_name, operation, changed_by)
    VALUES (TG_TABLE_NAME, TG_OP, current_user);
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_audit_loan_stmt
AFTER INSERT OR UPDATE OR DELETE ON loan_applications
FOR EACH STATEMENT EXECUTE FUNCTION log_operation_statement();

-- Тест: массовая вставка покажет разницу
INSERT INTO loan_applications (borrower_name, amount) VALUES ('Анна', 100000), ('Борис', 200000);

SELECT table_name, operation, new_data IS NOT NULL AS has_details FROM audit_log;
-- 2 строки от ROW-триггера с деталями, 1 строка от STATEMENT-триггера без деталей
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):**

```text
    table_name     | operation | has_details 
-------------------+-----------+-------------
 loan_applications | I         | t
 loan_applications | I         | t
 loan_applications | INSERT    | f
(3 rows)
```

*Почему вывод именно такой:* один оператор `INSERT` со списком `VALUES` затрагивает **две строки**, поэтому ROW-триггер вызывается дважды и пишет две записи с кодом `'I'` и полными данными (`to_jsonb(NEW)`). STATEMENT-триггер срабатывает ровно один раз на весь оператор и пишет имя операции (`TG_OP = 'INSERT'`) без `NEW`/`OLD` — отсюда `has_details = f`. Наглядный вывод для студентов: на массовых операциях ROW-аудит пишет столько записей, сколько строк затронуто (дорого, но детально), STATEMENT — одну (дёшево, но без содержимого).

## 5. Практикум 3: BEFORE-триггеры для инфраструктурных задач (10 мин)

```sql
CREATE OR REPLACE FUNCTION equipment_maintenance()
RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'UPDATE') THEN
        NEW.updated_at := now();
    ELSIF (TG_OP = 'DELETE') THEN
        IF OLD.status = 'ACTIVE' THEN
            RAISE EXCEPTION 'Нельзя удалить активное оборудование (id=%)', OLD.id;
        END IF;
        RETURN OLD;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_equipment_before
BEFORE UPDATE OR DELETE ON equipment
FOR EACH ROW EXECUTE FUNCTION equipment_maintenance();

-- Тесты
INSERT INTO equipment (name) VALUES ('Сервер A');
-- DELETE FROM equipment WHERE id = 1; -- ошибка
UPDATE equipment SET name = 'Сервер B' WHERE id = 1;
SELECT id, name, updated_at FROM equipment;
UPDATE equipment SET status = 'INACTIVE' WHERE id = 1;
DELETE FROM equipment WHERE id = 1; -- успешно
```

**Ожидаемый вывод (для преподавателя, проверено в Docker):** после первого `UPDATE` запрос `SELECT id, name, updated_at FROM equipment;` вернёт `Сервер B` с **заполненным** `updated_at` (текущее время) — его проставил триггер, хотя сам оператор колонку не трогал. Раскомментированный `DELETE` при `status = 'ACTIVE'` падает: `ERROR: Нельзя удалить активное оборудование (id=1)`. После перевода в `'INACTIVE'` — `DELETE 1`, таблица пуста.

*Почему вывод именно такой:* `BEFORE`-триггер срабатывает до записи строки, поэтому присваивание `NEW.updated_at := now()` попадает в итоговую версию строки. В ветке `DELETE` функция возвращает `OLD` (разрешить удаление) либо прерывает оператор исключением — вместе с исключением откатывается весь оператор, строка остаётся на месте. Обратите внимание: если из `BEFORE ROW`-триггера вернуть `NULL`, операция для этой строки молча отменяется без ошибки — ещё один способ «мягкого» запрета, здесь не используется.

**Границы:** это инфраструктурный инвариант, а не бизнес-правило. Мы не проверяем «есть ли активные заявки» — такое только в сервисе.

Мы научились реагировать на изменения строк автоматикой. Следующий шаг — обратная задача: не реагировать на запись, а заранее приготовить данные для чтения. Переходим к представлениям: сначала виртуальным (VIEW), затем материализованным — где за скорость чтения платим актуальностью.

## 6. Практикум 4: VIEW и MATERIALIZED VIEW (15 мин; подраздел 6.3 — демонстрационно, без самостоятельного повторения)

Используются таблицы `flights` и `ticket_flights`, созданные в разделе 1.

### 6.1 Обновляемое VIEW с WITH CHECK OPTION
```sql
-- 1. Обычное VIEW с WITH CHECK OPTION
CREATE OR REPLACE VIEW v_dme_flights AS
SELECT flight_id, flight_no, departure_airport, scheduled_departure
FROM flights
WHERE departure_airport = 'DME'
WITH CHECK OPTION;

-- 2. Вставка через VIEW (работает, так как условие соблюдено)
INSERT INTO v_dme_flights (flight_no, departure_airport, scheduled_departure)
VALUES ('SU9999', 'DME', '2025-06-15 10:00:00');

-- Проверка: строка появилась в базовой таблице
SELECT * FROM flights WHERE flight_no = 'SU9999';

-- Нарушение CHECK OPTION: вставка рейса не из DME отклоняется
INSERT INTO v_dme_flights (flight_no, departure_airport, scheduled_departure)
VALUES ('SU0001', 'SVO', '2025-06-15 11:00:00');
-- ERROR:  new row violates check option for view "v_dme_flights"
```
Обсудите: представление простое (одна таблица, без агрегации) — обновляемо автоматически; `flight_id` заполнился значением по умолчанию из последовательности `SERIAL`. `WITH CHECK OPTION` превращает представление в инструмент контроля качества данных: через него физически нельзя записать «чужой» аэропорт.

### 6.2 MATERIALIZED VIEW: агрегат-витрина и REFRESH CONCURRENTLY
```sql
-- 3. MATERIALIZED VIEW (агрегация + JOIN)
CREATE MATERIALIZED VIEW mv_flight_revenue AS
SELECT f.flight_id, f.flight_no,
       COUNT(tf.ticket_no) AS tickets,
       COALESCE(SUM(tf.amount), 0) AS revenue
FROM flights f
LEFT JOIN ticket_flights tf ON f.flight_id = tf.flight_id
GROUP BY f.flight_id, f.flight_no;

-- 4. Уникальный индекс для REFRESH CONCURRENTLY
CREATE UNIQUE INDEX idx_mv_flight_revenue_pk ON mv_flight_revenue(flight_id);

-- Чтение из MV — моментально, без пересчёта JOIN и агрегации
SELECT * FROM mv_flight_revenue ORDER BY revenue DESC;

-- 5. Обновление данных и REFRESH
INSERT INTO ticket_flights VALUES ('1234567893', 1, 25000);

-- До REFRESH в MV старые данные!
SELECT * FROM mv_flight_revenue WHERE flight_id = 1;

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_flight_revenue;

-- После REFRESH данные актуальны
SELECT * FROM mv_flight_revenue WHERE flight_id = 1;
```

**Ожидаемый вывод (для преподавателя, проверен в Docker):** сразу после создания MV содержит три строки — `SU1234: 2 билета, 33000.50`; `SU5678: 1 билет, 22000.00`; `AB999: 0 билетов, 0` (сработал `LEFT JOIN` + `COALESCE`: рейс без билетов не потерялся). После вставки билета на 25000, но **до** `REFRESH`, запрос по `flight_id = 1` по-прежнему возвращает `2 / 33000.50` — витрина честно показывает устаревшие данные. После `REFRESH … CONCURRENTLY` — `3 / 58000.50`.

*Почему вывод именно такой:* MV — физическая таблица-снимок; вставка в `ticket_flights` её не затрагивает. `CONCURRENTLY` позволяет читать старую версию во время пересчёта, но требует уникального индекса: PostgreSQL сопоставляет старые и новые строки по нему и обновляет только различия. Обычный `REFRESH` (без `CONCURRENTLY`) пересчитывает всё и держит эксклюзивную блокировку на чтение — в отчётных системах это причина планировать обновление в часы минимальной нагрузки (cron / pg_cron).

**Задание на дом (бонус):** проверьте требование уникального индекса экспериментально: выполните `DROP INDEX idx_mv_flight_revenue_pk;` и попробуйте `REFRESH MATERIALIZED VIEW CONCURRENTLY mv_flight_revenue;`. Затем восстановите индекс и повторите. Что произошло в обоих случаях и почему?

**Проверьте себя:** без индекса — ошибка `ERROR: cannot refresh materialized view "public.mv_flight_revenue" concurrently` с подсказкой `HINT: Create a unique index with no WHERE clause on one or more columns of the materialized view.` После пересоздания индекса (`CREATE UNIQUE INDEX idx_mv_flight_revenue_pk ON mv_flight_revenue(flight_id);`) обновление проходит: `REFRESH MATERIALIZED VIEW`. Режиму `CONCURRENTLY` нужен способ однозначно сопоставить строки старой и новой версии витрины — без уникального индекса это невозможно. Не забудьте восстановить индекс до конца занятия, он понадобится в ДЗ.

### 6.3 Необновляемое VIEW + INSTEAD OF TRIGGER
```sql
-- 6. Сложное VIEW (необновляемое, есть GROUP BY) с INSTEAD OF TRIGGER
CREATE OR REPLACE VIEW v_flight_revenue AS
SELECT f.flight_id, f.flight_no, COALESCE(SUM(tf.amount), 0) AS revenue
FROM flights f
LEFT JOIN ticket_flights tf ON f.flight_id = tf.flight_id
GROUP BY f.flight_id, f.flight_no;

CREATE OR REPLACE FUNCTION trg_update_flight_revenue()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'UPDATE' THEN
        UPDATE flights SET flight_no = NEW.flight_no WHERE flight_id = NEW.flight_id;
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        DELETE FROM flights WHERE flight_id = OLD.flight_id;
        RETURN OLD;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_v_flight_revenue
INSTEAD OF UPDATE OR DELETE ON v_flight_revenue
FOR EACH ROW EXECUTE FUNCTION trg_update_flight_revenue();

-- 7. Тест UPDATE через VIEW
UPDATE v_flight_revenue SET flight_no = 'SU1234NEW' WHERE flight_id = 1;

-- Проверка: изменение ушло в базовую таблицу
SELECT flight_id, flight_no FROM flights WHERE flight_id = 1;
```
Обсудите:
- Представление с `GROUP BY` автоматически необновляемо: по агрегированной строке нельзя однозначно вычислить строку базовой таблицы. `INSTEAD OF`-триггер переопределяет поведение и «вручную» отображает операцию на таблицу `flights`.
- Попытка `DELETE FROM v_flight_revenue WHERE flight_id = 1` завершится ошибкой внешнего ключа: в `ticket_flights` есть билеты на этот рейс, а FK объявлен без `ON DELETE CASCADE`. Это демонстрация того, что триггер переносит операцию, но не отменяет ограничения целостности.
- `INSERT` через это представление не определён (нет обработчика `TG_OP = 'INSERT'`) — будет ошибка `ERROR: cannot insert into view "v_flight_revenue"` с подсказкой `HINT: To enable inserting into the view, provide an INSTEAD OF INSERT trigger or an unconditional ON INSERT DO INSTEAD rule.`
