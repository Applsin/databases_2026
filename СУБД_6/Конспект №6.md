онспект лекции 6. От одной базы данных к распределённым системам. Часть I
Блок 1. Зачем выходить за пределы одной машины

Проблема: данных слишком много / запросы слишком медленные для одного сервера.

Два пути:

    Scale-Up (вертикальное): мощнее сервер. Плюсы — простота. Минусы — физический предел, дорого, single point of failure.

    Scale-Out (горизонтальное): много серверов как единая система. Плюсы — почти бесконечное масштабирование, отказоустойчивость. Минусы — сложность архитектуры.

Три стратегии горизонтального роста (внедряются именно в этом порядке):

    Репликация — копии всего набора данных. Схемы: Master–Slave (запись на master, чтения с реплик; минусы — отставание реплик, нужен failover) и Master–Master (конфликты записи, плата по CAP).

    Партиционирование — деление одной таблицы внутри одного сервера. Ускоряет запросы, не масштабирует запись, не переживает отказ.

    Шардирование — деление данных по разным серверам. Масштабирует запись и объём, но требует маршрутизации, перебалансировки, распределённых транзакций.

Параллельное ≠ распределённое (CMU 15-445): параллельные СУБД — узлы рядом, быстрая сеть, коммуникация дёшева; распределённые — узлы удалены, сеть публичная, коммуникация дорога и её нельзя игнорировать. «Databases are hard. Distributed databases are harder» (Э. Павло). Одноузловая транзакция не требует координации, распределённая — требует дорогой координации; цель проектирования — минимизировать многоузловые транзакции. Задача двух генералов (CS 347, Гарсиа-Молина) доказывает невозможность идеальной согласованности при ненадёжной связи.
Блок 2. Партиционирование и кластеризация
Партиционирование (Partitioning)

Логическое деление одной таблицы на физические части; для приложения — одна таблица. Горизонтальное (разные строки, те же колонки) vs вертикальное (деление по колонкам — вынос «холодных» тяжёлых полей; это приём проектирования схемы, а не механизм СУБД).

Зачем: управляемость (удаление старых данных, VACUUM/ANALYZE по частям), partition pruning, параллельная загрузка, меньшие индексы.

Три стратегии:

    Range — по диапазонам (даты, числа) — для временных рядов;

    List — по фиксированному набору значений (регионы, статусы);

    Hash — равномерное распределение без бизнес-смысла (MODULUS n, REMAINDER r).

Партиционирование ≠ шардирование: партиционирование — один экземпляр СУБД, маршрутизация движком, масштабирует скорость/обслуживание, обычный ACID; шардирование — несколько серверов, маршрутизация приложением/прокси, масштабирует запись/объём, нужны распределённые транзакции.
Декларативное партиционирование в PostgreSQL (с v10)

    Partitioned table — логическая, не хранит данные; индексы/CHECK на родителе создаются на партициях (v11); PK обязан включать partition key.

    Tuple routing при INSERT: извлечение ключа → бинарный поиск партиции O(log N) → вставка.

    Partition pruning: static (константы в WHERE, на планировании), executor-stage (параметры, v11), parallel partition processing (v11).

    Ограничения: PK/unique должны включать partition key; FK на partitioned table — с v12; нет SPLIT/MERGE PARTITIONS.

Статическое vs динамическое

    Динамическое pruning — есть (на этапе выполнения).

    Динамическое создание партиций — нет: только явный DDL. Вставка вне границ → ошибка no partition of relation ... found for row. Обходные пути:

        DEFAULT-партиция (v11) — страховка, но деградирует (pruning её не отсекает) и при ATTACH требует полного сканирования под ACCESS EXCLUSIVE (можно избежать CHECK-ограничением).

        Плановое создание заранее (cron/планировщик) — промышленный стандарт.

        pg_partman — расширение с фоновой ротацией.

    Retention: DETACH PARTITION + DROP TABLE (без DELETE/VACUUM); с v14 — DETACH ... CONCURRENTLY.

    В колоночных аналитических СУБД модель иная: части данных создаются движком и склеиваются фоново.

Выбор ключа и когда партиционирование не помогает

    Ключ обязан быть в WHERE большинства тяжёлых запросов (иначе pruning не работает).

    Партиций не должно быть слишком много (сотни — ок, тысячи — деградация планирования).

    Следить за равномерностью (горячая партиция обесценивает выигрыш).

Не помогает, если: запросы не фильтруют по ключу (хуже одной таблицы); таблица мала; узкое место — запись на одном сервере (нужно шардирование); проблема в отсутствии индекса.
Кластеризация (Clustering)

Физическая пересортировка строк по индексу (CLUSTER table USING index). Ускоряет чтение диапазонов. Разовая операция — при вставках/обновлениях порядок нарушается, нужна периодическая повторная кластеризация. С v15 — для партиционированных таблиц.

Архитектуры СУБД (CMU): Shared Memory (почти не используется), Shared Disk (общий диск, своя память у CPU), Shared Nothing (свой CPU/память/диск, связь только по сети — самая сложная для согласованности, но лучшая производительность; основа Greenplum/Cloudberry).
Блок 3. CAP и PACELC
Модели согласованности (спектр)

Линеаризуемость (Spanner, etcd, ZooKeeper) → последовательная → причинная (MongoDB causal sessions) → eventual (Cassandra, DynamoDB, DNS).

Клиентские (сессионные) гарантии (Bayou, Terry et al.): read-your-writes, monotonic reads, monotonic writes, writes-follow-reads. Дешевле линеаризуемости, закрывают большинство пользовательских сценариев.
Доступность и «девятки» SLA

99% — 3,65 дня/год; 99,9% — 8,77 ч; 99,99% — 52,6 мин; 99,999% — 5,26 мин. Конфликт с согласованностью из-за репликации: ждать подтверждения реплик (согласованность) vs ответить с локальной копии (доступность).
CAP-теорема (Брюэр 2000, доказана Гилбертом и Линч 2002)

Невозможно одновременно: C (все узлы видят одно и то же — в доказательстве это линеаризуемость), A (каждый запрос к неотказавшему узлу завершается ответом), P (система переживает разрыв сети).

Доказательство «на пальцах»: сеть разорвана между N1 и N2; запись в N1, чтение в N2 — либо старое значение (нарушена C), либо нет ответа (нарушена A).

Важно: «выберите два из трёх» — упрощение. P не выбирается (сеть рано или поздно разделится). Реальный выбор — только в момент разделения между C и A: CP (жертвуют доступностью), AP (жертвуют согласованностью), CA (только без распределённости).

Сценарий разрыва ДЦ:

    CP (etcd, MongoDB majority, HBase): меньшинство перестаёт принимать записи (stepdown лидера) — жертва A.

    AP (Cassandra, DynamoDB): обе стороны работают, расхождения решаются last-write-wins, hinted handoff, read repair — жертва C.

Критика (Брюэр 2012): CAP — не «CA навсегда», а три режима: норма, разделение (что деградирует), восстановление. Ссылки на CAP как оправдание вечной слабой согласованности некорректны (учебник Postgres Professional, гл. 21).
PACELC (Абади, 2010/2012)

P — при разделении выбор A vs C; E (Else) — в норме выбор L (latency) vs C (consistency).

Механика EL-выбора:

    Синхронная репликация — коммит после кворума → задержка (RTT до ДЦ).

    Асинхронная — коммит локально → минимальная задержка, но окно потери данных (RPO > 0) и устаревшие чтения.

    Кворумы (N, W, R): при R + W > N чтение встречает свежую копию ценой задержки; R = W = 1 — минимальная задержка и максимальный риск.

Четыре класса:
Класс	При P	В норме	Примеры
PA/EL	A	L	DynamoDB, Cassandra, ScyllaDB, Riak
PC/EC	C	C	Spanner, CockroachDB, HBase, Greenplum/Cloudberry
PC/EL	C	L	PNUTS, ZooKeeper (чтение с фолловеров)
PA/EC	A	C	MongoDB (по Абади)
Привязка к системам

    Cassandra/ScyllaDB (PA/EL): leaderless, согласованность на запрос (ONE/QUORUM/ALL), hinted handoff, read repair, LWW.

    DynamoDB (PA/EL): eventual по умолчанию, «сильные» чтения — опция с ценой.

    MongoDB (PA/EC): один primary на replica set, stepdown при меньшинстве; writeConcern: majority и causal sessions приближают к строгой согласованности.

    Spanner (PC/EC): external consistency через Paxos + TrueTime (commit wait).

    etcd/ZooKeeper (CP): консенсус Raft/ZAB, меньшинство молчит.

    PostgreSQL: асинхронная репликация → PC/EL; synchronous_commit = remote_apply → PC/EC.

    Greenplum/Cloudberry (PC/EC): 2PC.

    ClickHouse (PA/EL): асинхронная репликация через Keeper.

Правило: PC/EC — для денег, остатков, блокировок; PA/EL — для лент, счётчиков, телеметрии, сессий.
Блок 4. Распределённые транзакции
Почему одноузловые механизмы не работают

MVCC/WAL/lock manager были централизованы в одном процессе. При партиционировании по серверам: у каждого сегмента свой WAL и lock manager; транзакция через два сегмента требует координации; фиксация на одном при падении другого → неконсистентность.

Две независимые задачи (учебник Postgres Professional, гл. 22.4): (1) глобальная сериализуемость (локальной сериализации проекций недостаточно — проекции могут сериализоваться в разном порядке); (2) атомарность завершения всех подтранзакций (2PC).
2PC (Two-Phase Commit)
text

Координатор → PREPARE → участники (пишут в WAL, держат блокировки)
участники → VOTE YES/NO → координатор
[решение пишется в WAL координатора ДО рассылки]
координатор → COMMIT/ABORT → участники → ACK

Ключевой смысл Prepare: голос YES — безвозвратное обещание (in-doubt до команды координатора).

Проблемы: блокировки в Phase 1 (протокол блокирующий), зависимость от координатора (решение — репликация standby master), latency (два round-trip).

Три сценария отказа:

    Участник упал до PREPARE → таймаут, abort; вернувшийся откатывает по WAL.

    Участник упал после YES → in-doubt; после рестарта опрашивает координатора; долгий простой координатора — вмешательство администратора.

    Координатор упал после записи решения в WAL → восстановленный дорассылает (поэтому решение пишется до рассылки).

Почему не 3PC: при разделении сети две половины могут принять противоположные решения. Альтернатива — консенсус (Paxos/Raft): решение реплицируется кворумом (Spanner: 2PC поверх Paxos-групп).

Миф о медленности: задержки — не от числа сообщений, а от таймаутов неотвечающих участников; в реплицированных системах достаточно кворума.

Где: Greenplum/Cloudberry (master — координатор, сегменты — участники); PostgreSQL — PREPARE TRANSACTION / COMMIT PREPARED для внешних координаторов (XA: Atomikos, Narayana), pg_prepared_xacts. Несовместимо с transaction pooling (pgBouncer).
Глобальный порядок транзакций (GXID)

В одноузловом PostgreSQL xmin/xmax и snapshot — локальны. На разных сегментах «транзакция 42» — разные. Нужны: кто назначает порядок, как выглядит глобальный снимок, где хранится.

Три подхода к GXID:

    TSO (Timestamp Oracle) — централизованный сервис (Percolator, TiDB/PD): start-ts/commit-ts; метки пакетами; цена — сетевой вызов, отказ останавливает запись.

    TrueTime (Spanner) — GPS + атомные часы, интервал неопределённости [earliest, latest]; commit wait до TT.after(s) → external consistency ценой миллисекунд.

    HLC (CockroachDB, YugabyteDB) — (физическое время, логический счётчик); причинность без центра; узел с расхождением > max offset (500 мс) самоустраняется; возможны перезапуски транзакций.

    Часы Лэмпорта — причинный порядок, не «настоящее» время; для уникальности конкатенация с номером сервера.

Распределённый снимок в Greenplum/Cloudberry (DTM): координатор назначает gxid → формирует distributed snapshot активных gxid → рассылает снимок с планом на все сегменты → сегменты применяют к локальным версиям (xmin/xmax хранят gxid). Состояние: shared memory координатора + distributed commit log (dtm log) + локальные WAL/prepare-записи на сегментах.

Вариант без координатора (CockroachDB): transaction record в KV-слое на range первого ключа; состояния pending → committed/aborted; write intents с указателем на запись; читатель «разрешает» intent. Атомарность без 2PC-координатора (решение в одном ключе, реплицируемом Raft); цена — перезапуски на новых HLC-метках.

In-doubt резидуальные транзакции: FTS (Fault Tolerance Service) в Greenplum/Cloudberry сканирует сегменты после восстановления координатора.
Распределённые deadlock'и

Цикла нет ни на одном сегменте по отдельности, но глобально — deadlock (T1 держит X на A, ждёт Y на B; T2 наоборот).

Решение в Greenplum/Cloudberry: Global Deadlock Detector (GDD) — фоновый процесс координатора собирает локальные wait-for graphs, строит глобальный, выбирает жертву (наименьший gxid) и шлёт ROLLBACK. Цена — дополнительные сообщения и latency обнаружения; поэтому в высоконагруженных системах часто предпочитают OCC.
OCC (Kung & Robinson, 1981)

Пессимистичный 2PL платит блокировками даже без конфликтов. OCC: конфликты редки — работаем вперёд, проверяем в конце.

Три фазы:

    Read — чтение и запись в локальный workspace, без блокировок; запоминаются read set и write set.

    Validation — проверка сериализуемости.

    Write — перенос write set атомарно; при провале — abort и restart (дёшево: в общих данных ничего не менялось).

Backward-oriented validation: для каждой уже зафиксированной T_j:

    writeSet(T_j) ∩ readSet(T_i) = ∅ (нет чтения перезаписанного);

    writeSet(T_j) ∩ writeSet(T_i) = ∅ (нет потери обновления).
    Интуиция: T_i ведёт себя так, будто выполнилась после всех зафиксированных T_j.

Пример (перевод A→B на двух шардах + проценты на A): T2 фиксирует A=1100; T1 (читала A=1000, пишет 800) на валидации видит writeSet(T2) ∩ readSet(T1) = {A} → abort → перезапуск с A=1100. Без валидации — потеря обновления. Итог эквивалентен T2 → T1, без единой блокировки; обрыв дёшев (workspace).

Связь с изученным: first-committer-wins (ошибка сериализации при конкурентном UPDATE на REPEATABLE READ/SERIALIZABLE); SSI (PostgreSQL 9.1+, Cahill/Röhm/Fekete 2008) — отслеживание rw-анти-зависимостей и обрыв одной транзакции вместо блокировок.

Где: Silo, FaRM (OCC поверх MVCC — миллионы txn/s на read-mostly); CockroachDB (MVCC + HLC + перезапуски); Spanner (гибрид 2PL + MVCC + TrueTime — при высокой конфликтности возвращаются блокировки); Greenplum (2PL + snapshot, OCC для read-only аналитики).

Когда выигрывает/проигрывает: OCC блестящ при низкой конфликтности и read-mostly; на горячих ключах — лавина перезапусков, 2PL честно упорядочил бы очередь. Выбор — ставка на характер нагрузки, не «какой протокол лучше».
Блок 5. Итоги

    Одной машины недостаточно: scale-up упирается в предел и не даёт отказоустойчивости. Порядок внедрения: репликация → партиционирование → шардирование.

    Партиционирование — логическое деление, кластеризация — физическая пересортировка. В PostgreSQL партиционирование статическое (явный DDL, DEFAULT, pg_partman), но с двухступенчатым pruning. Ключ обязан быть в WHERE тяжёлых запросов.

    CAP — выбор C/A в момент разделения; PACELC — выбор L/C и в норме.

    Распределённые транзакции: 2PC (in-doubt, блокирующий), глобальный порядок (TSO/TrueTime/HLC/distributed snapshot), глобальный deadlock detection. OCC заменяет блокировки валидацией read/write set — выигрывает при редких конфликтах, проигрывает на горячих ключах.
