Конспект лекции: Колоночные СУБД на примере ClickHouse
1. OLTP vs OLAP

OLTP (Online Transaction Processing) — оперативная обработка транзакций: короткие запросы к единичным записям, много INSERT/UPDATE/DELETE малыми порциями. Пример: проверка пароля пользователя.

OLAP (Online Analytical Processing) — аналитическая обработка: сложные запросы с агрегатами и группировками, читающие большие объёмы данных, но лишь небольшое подмножество столбцов; >95% нагрузки — чтение. Термин введён Эдгаром Коддом в 1993 г.

Строковые СУБД ориентированы на запись (write-optimized), аналитические — на чтение (read-optimized). Гибридные HTAP-системы существуют, но крупные компании предпочитают раздельные решения: строковая СУБД для транзакций + колоночная для аналитики, соединённые пайплайном данных.

OLAP применяется в BI и отчётности, clickstream-аналитике, time-series, логах и аудите, ad-hoc аналитике. Общий признак — агрегация множества строк; фраза «в аналитике не пишут SELECT *» отражает архитектурный принцип.

ClickHouse — колоночная OLAP-СУБД, начатая в 2009 г. в Яндексе как внутренний движок для Яндекс.Метрики и открытая в 2016 г. Спроектирована под пять вызовов: огромные данные при высоких темпах вставки; много одновременных запросов с низкой задержкой; интеграция с разнообразными хранилищами; удобный SQL и интроспекция производительности; промышленная надёжность и простое развёртывание (единый бинарник на C++ без JVM). Движок делится на слои: обработка запросов (векторизованный исполнитель), хранение (движки таблиц, главный — MergeTree), интеграция (внешние источники).
2. Колоночное хранение: NSM vs DSM

NSM (N-ary Storage Model) — строковое хранение: все атрибуты строки лежат последовательно на одной странице. Идеально для OLTP: вся строка читается и пишется одной операцией ввода-вывода. При аналитическом сканировании читаются все столбцы, даже если нужны 2 из 50.

DSM (Decomposition Storage Model) — колоночное хранение: каждый атрибут хранится в собственном наборе страниц. Идея восходит к Copeland и Khoshafian (1985), формализована в C-Store (2005). В ClickHouse таблица физически — набор каталогов (parts); внутри part — по одному файлу на колонку (.bin), плюс служебные файлы. Запрос открывает только файлы нужных колонок.

Сборка строки обратно (tuple reconstruction) в ClickHouse использует фиксированные смещения: i-е значение в файле колонки A и i-е в файле колонки B принадлежат одной строке; идентификаторы строк не хранятся.

Преимущества DSM: чтение только нужных колонок; лучшее сжатие (однотипные значения); векторизация (SIMD). Недостаток: запись и изменение одиночных строк дороги — один INSERT превращается в запись десятков файлов. ClickHouse решает это через иммутабельные parts и батчевые вставки.

Количественно: в обзоре Abadi et al. (SIGMOD 2008) колоночные системы показывали ~5–6-кратное превосходство над строковыми на аналитических бенчмарках. Гибридная модель PAX (Ailamaki et al., VLDB 2001) делит таблицу на группы строк, внутри группы данные хранятся поколоночно; так устроены Parquet и ORC.
3. Хранение в ClickHouse: MergeTree, parts, слияния, разреженный индекс

ClickHouse по духу близок к LSM-деревьям, но без memtable и WAL: каждый INSERT сразу формирует готовый part на диске, разложенный по колонкам. Строго говоря, это «MergeTree», а не классический LSM.

Part — самодостаточная «таблица внутри таблицы»:

    строки физически отсортированы по ключу ORDER BY;

    part — каталог с файлом на каждую колонку, файлами marks для навигации по сжатым блокам, разреженным индексом и метаданными (включая кодек сжатия — разные parts могут быть сжаты по-разному);

    part иммутабелен: изменить его нельзя принципиально.

Иммутабельность даёт последовательный I/O вместо случайного, отличное сжатие и полное отсутствие блокировок — запрос заранее знает, что parts не изменятся.

Фоновые слияния (merges). Каждый INSERT порождает part; со временем parts становится много, чтение деградирует (запрос заглядывает в каждый part). Фоновый процесс непрерывно сливает мелкие parts в крупные (целевой размер ~150 ГБ по умолчанию), используя k-way merge sort. В отличие от классических LSM с жёсткой иерархией уровней, в ClickHouse все parts равноправны. После слияния старые parts помечаются неактивными и удаляются, когда их дочитают начавшиеся запросы (reference counting). На время слияния таблица занимает до x2 места. OPTIMIZE TABLE форсирует внеплановое слияние; частый OPTIMIZE ... FINAL в проде — антипаттерн.

Гранулы, блоки и сжатие. Строки part логически делятся на гранулы — по умолчанию по 8192 строки (с адаптивной гранулярностью по байтам). Гранула — минимальная неделимая единица чтения для операторов сканирования и индекса. Физически данные пишутся блоками (~1 МБ несжатых данных) — несколько соседних гранул одной колонки. Блоки сжимаются (по умолчанию LZ4, можно ZSTD и специализированные кодеки). Поверх сжатия хранится отображение: гранула → смещение сжатого блока → смещение внутри распакованного блока. Распаковка — на лету.

Разреженный первичный индекс. В PostgreSQL первичный индекс — B-Tree с записью на каждую строку. В ClickHouse индекс разреженный: одна запись (mark) на гранулу — значение ключа первой строки гранулы. Для таблицы на 8,1 млн строк индекс — ~1000 записей, целиком живёт в оперативной памяти. Запрос с WHERE по ключу сортировки: бинарный поиск по marks → набор гранул-кандидатов → чтение только их. Разреженность — фильтр грубой очистки: на границах диапазона прочитаются лишние строки (до двух гранул), что для аналитики ничтожно.

Отличия от PostgreSQL:

    Первичный ключ не гарантирует уникальность — он лишь задаёт порядок сортировки.

    Вторичных B-Tree индексов нет: быстрый доступ только по ключу сортировки. Для быстрого поиска по другой колонке — data skipping index (minmax, set, bloom_filter, работают на уровне гранул) либо денормализация/вторая таблица с другой сортировкой.

Партиционирование. Таблица режется на партиции по произвольному выражению (PARTITION BY), исторически по месяцам. Для каждой партиции хранятся min/max ключа, что даёт partition pruning. Партиция — единица maintenance: DROP PARTITION удаляет старый месяц почти мгновенно; TTL-правила отрабатывают так же дёшево.

Цена точечных чтений. Точечный запрос WHERE key = X читает минимум одну гранулу (8192 строки) из каждого part каждой партиции, где ключ может находиться, — и так по каждой колонке из SELECT. Плюс файлы marks на каждую колонку. Официальная рекомендация: не использовать ClickHouse как key-value хранилище. Если точечные чтения неизбежны: мало parts (аккуратный батчинг), мало партиций, компактный формат parts для мелких данных, уменьшенная гранулярность, bloom_filter skip-индексы.

Пример схемы time-series:
sql

CREATE TABLE sensor_readings (
    device_id UInt32,
    timestamp DateTime64(3),
    temperature Float32,
    humidity Float32
) ENGINE = MergeTree
ORDER BY (device_id, timestamp)
PARTITION BY toYYYYMMDD(timestamp);

Запрос WHERE device_id = 42 AND timestamp > now() - INTERVAL 1 HOUR: partition pruning отсекает прошлые дни → бинарный поиск по разреженному индексу находит гранулы устройства 42 → с диска читаются только колонки temperature, humidity для этих гранул.
4. Запись и изменение данных

Почему вставлять нужно батчами. Каждый INSERT — новый part: каталог, десятки-сотни файлов, fsync. Измерения на таблице Яндекс.Метрики (105 столбцов): батчами по 1 млн строк — ~500 000 строк/с; по одной строке — 59 строк/с (реплика — 6 строк/с). Разница — четыре порядка. При слишком частых вставках parts образуются быстрее, чем слияния успевают их склеивать: сначала деградируют SELECT'ы, затем при превышении лимита (~300 активных parts на партицию) ClickHouse отклоняет вставку с ошибкой «Too many parts» — это защитный backpressure.

Как организовать частые вставки:

    Батчи 10 000–100 000 строк (или 1–10 МБ) на один INSERT.

    async_insert: сервер буферизует строки от множества мелких INSERT'ов в памяти и сбрасывает их одним part по порогу размера (async_insert_max_data_size, ~100 МиБ), времени (async_insert_busy_timeout_ms, сотни миллисекунд) или числу запросов. Концептуально «memtable наоборот»: данные из буфера недоступны для SELECT, зато parts рождаются редко и крупно.

    Буфер на стороне пайплайна: очередь (Kafka), таблица-движок Buffer, батчер в приложении.

    Следить за составом батча: вставка разбивается по партициям — батч на миллион строк, покрывающий несколько лет, эквивалентен десяткам мелких вставок.

Семейство движков MergeTree: слияние как механизм трансформации. Момент слияния parts — единственная точка, где данные можно «задним числом» модифицировать, пока они снова не стали иммутабельными. На этом построено всё семейство:
Движок	Что делает при слиянии
MergeTree	Ничего: сортирует, перезаписывает, пересобирает индексы
ReplacingMergeTree	Оставляет последнюю версию строки по ключу сортировки
CollapsingMergeTree	Схлопывает пары строк с признаком +1/−1 (sign)
SummingMergeTree	Суммирует числовые колонки строк с одним ключом
AggregatingMergeTree	Хранит и склеивает промежуточные состояния агрегатов (инкрементальная агрегация, основа материализованных представлений)

Правило применимости: специализированные движки оправданы, только если сокращают число строк на порядки (например, «последнее состояние каждого пользователя»). Для полной истории событий ReplacingMergeTree не подойдёт: слияния не гарантируют момент схлопывания (до слияния видны все версии), а полный OPTIMIZE на больших таблицах непрактичен.

Мутации. Настоящих UPDATE/DELETE в стиле PostgreSQL нет — parts иммутабельны. Вместо них:

    Мутации (ALTER TABLE ... UPDATE ... WHERE, ALTER TABLE ... DELETE WHERE [IN PARTITION ...]): фоновая перезапись затронутых parts целиком. Не атомарны (часть parts мутировала, часть — нет), выполняются в хронологическом порядке, не блокируют чтения и друг друга, не затрагивают строки, вставленные после запуска, переживают рестарт сервера. Перезаписываются только файлы затронутых колонок (поколоночное хранение!), но даже изменение одного имени пользователя тянет перезапись колонки во всех parts партиции. Мутации — инструмент разовых операций (GDPR-удаления, исправление ошибок загрузки), а не рутины.

    Lightweight deletes (DELETE FROM ...): строки помечаются маской удаления и физически исчезают при ближайшем слиянии — дешевле полной мутации, но видимость результата зависит от настроек.

    Удаление периодов целиком: DROP PARTITION — мгновенно и бесплатно.

Из отсутствия MVCC и блокировок следует отсутствие многооператорных транзакций: атомарность гарантируется только в рамках одной вставки (одна таблица, одна партиция, до max_insert_block_size ≈ 1 млн строк / 256 МиБ). ClickHouse осознанно жертвует ACID ради скорости аналитики — классический выбор PA/EL-системы.
5. Выполнение запросов: векторизация, JOIN'ы, словари, типизация

Векторизованный движок. Запросы выполняются по модели MonetDB/X100: операторы обрабатывают данные не построчно, а батчами колоночных значений (векторами), что даёт SIMD-инструкции, дружественность к кэшу CPU и возможность JIT-компиляции горячих участков в машинный код. Один запрос по умолчанию использует все ядра сервера (ограничивается max_threads). ClickHouse оптимизирует throughput, а не latency мелких запросов.

JOIN'ы: «ручная коробка передач». Основной алгоритм — hash join: правая таблица целиком загружается в хеш-таблицу в оперативной памяти. Следствия:

    Порядок таблиц имеет значение. Пример: JOIN таблицы на 2 млрд строк (справа) с таблицей на 2 млн (слева) падает с ошибкой памяти — на стадии FillingRightJoinSide потребовалось 64 ГБ. Меняем таблицы местами — хеш-таблица по 2 млн строкам (128 МБ), запрос проходит за секунды. Хеш-таблица весит заметно больше самих данных.

    Cost-based оптимизатора нет: порядок JOIN'ов, фильтрация по ключу соединения, выбор алгоритма — зона ответственности разработчика. Проверяйте через EXPLAIN, что план изменился так, как задумано.

    IN вместо JOIN: подзапрос-фильтр WHERE key IN (SELECT ...) умеет использовать индекс (ключ сортировки) правой таблицы — JOIN этого не делает. Больших списков в IN бояться не нужно — это нормальный паттерн.

    Ключевое слово ANY (LEFT ANY JOIN): к каждой строке присоединяется одна произвольная подходящая строка справа — хеш-таблица хранит по записи на ключ, а не массив, и заметно худеет.

    Альтернативные алгоритмы выбираются настройкой join_algorithm: full_sorting_merge (merge join по ключу сортировки — почти без памяти, если обе таблицы отсортированы по ключу соединения; в примере выше — 88 МБ вместо 64 ГБ), grace_hash (правую таблицу делит на фрагменты по размеру памяти, остальные ждут на диске).

    Неравенства в условии соединения не поддерживаются (кроме специального ASOF JOIN — «ближайшее значение слева по времени»); «больше/меньше» переносите в WHERE.

Словари — замена JOIN для справочников. Если «правая таблица» маленькая (справочник регионов, рекламных кампаний), её не нужно джойнить: движок Dictionary кэширует результат запроса к внутреннему или внешнему источнику (MySQL, PostgreSQL, HTTP-сервис) в памяти, а функция dictGet('dict_name', attr, id) подставляет значения за время поиска по хешу. Словарь с RANGE умеет отдавать значение, актуальное на дату; обновление справочника в источнике «обновляет задним числом» все отчёты. Ограничение: cache-словарь эффективен при hit rate, близком к 100%.

Типизация и схема: дешёвые байты.

    Не храните всё в String. IP-адрес — UInt32/IPv4: uniqExact по IP-числам выполняется со скоростью ~137 млн строк/с против ~37 млн/с для строк, плюс экономия места.

    Enum8/Enum16 для закрытых перечислений; ALTER для Enum почти бесплатен (данные на диске не меняются).

    LowCardinality(String) — словарное кодирование колонки на лету: для колонок с малым числом уникальных значений сокращает объём и время группировок.

    Избегайте Nullable — к каждой колонке добавляется отдельный файл-битмаск, что замедляет чтение; используйте значения-заглушки (0, пустая строка, 1970-01-01).

    Денормализуйте: данные большой кардинальности (URL, поисковые фразы) храните прямо в основной таблице — нормализация потребует JOIN'ов, а они дороги.

    Предвычисляйте колонки. Пример: хранить домен отдельно от URL — запрос по готовому домену быстрее в 2,5 раза (67 мс против 166 мс), а сжатый столбец занимает 5 МБ против 126 МБ. Антипример: хранить версию браузера строкой «12.3.45.6» и делить её в каждом запросе — «преждевременная пессимизация»; правильно — четыре маленьких числовых столбца. Колоночная СУБД не боится широких таблиц: лишние столбцы, не участвующие в запросе, бесплатны.

    Очень длинные строки и массивы (десятки килобайт) в ClickHouse не хранят — в таблицу идёт идентификатор, сами данные — во внешнее хранилище; прагматичный компромисс — сохранять первые N (например, 512) значений.

    Материализованные представления переносят вычисления с query time на insert time: MV на AggregatingMergeTree инкрементально поддерживает агрегаты по мере вставки сырых событий.

6. Масштабирование: шардирование, репликация, ingestion через Kafka

Шардирование и репликация. ClickHouse масштабируется горизонтально в архитектуре shared-nothing:

    Шардирование: таблица делится на шарды по sharding-выражению. Ключ должен распределять данные равномерно (user_id — хорошо; toYYYYMMDD(ts) — плохо: вся свежая запись упирается в один шард, классический skew).

    Distributed table: виртуальная таблица-прокси, дающая глобальное представление всех шардов: запрос рассылается на шарды (scatter), частичные результаты собираются (gather). Писать можно напрямую в шарды или через Distributed.

    Репликация: каждый движок MergeTree имеет реплицированную версию (ReplicatedMergeTree). Реплики шарда равноправны (multi-master): координация — через ClickHouse Keeper (написанная на C++ замена ZooKeeper, протокол Raft), который хранит только лог метаданных операций; сами данные реплики передают друг другу напрямую. Фактор репликации 2–3 обычно достаточен.

    Co-located JOIN'ы: таблицы, шардированные по одному ключу, соединяются локально на каждом шарде без перегона данных.

Ingestion: Kafka как центральная шина. Колоночная СУБД — обычно «аналитический конец» конвейера данных. Apache Kafka играет роль буфера между источниками и ClickHouse: декуплинг скоростей записи и потребления, replay при сбоях (перемотка offset'ов), сглаживание всплесков (backpressure). Три паттерна интеграции:

    Kafka table engine + Materialized View: ClickHouse сам читает из топика, MV перекладывает данные в целевую таблицу. Просто, но требует тюнинга consumer groups.

    Kafka Connect + ClickHouse sink: управляемый батчинг, retry, schema evolution — enterprise-вариант (включать async_insert).

    ClickPipes: managed-вариант в ClickHouse Cloud.

В терминах CQRS ClickHouse обычно играет роль read model: PostgreSQL обслуживает транзакции (write model), изменения текут через CDC в Kafka, ClickHouse материализует агрегаты. Цена — eventual consistency между моделями.

Антипаттерны эксплуатации:

    Микрошардинг: разбить данные на 1000 микрошардов и поднять 200 инстансов ClickHouse на сервере. Один инстанс спроектирован использовать все ресурсы машины на один запрос; 200 инстансов породят десятки тысяч потоков и бессмысленный TCP-трафик между процессами. Один сервер — один инстанс.

    Тысячи ручных таблиц (table_001 … table_999) — стереотип из эпохи MyISAM. Кластерный ключ сортировки и партиции решают ту же задачу внутри одной таблицы; ALTER ADD/DROP COLUMN в ClickHouse бесплатен (меняются только метаданные и файлы колонки).

    Репликация «на ручном приводе» (два независимых пайплайна + rsync раз в месяц) вместо штатной ReplicatedMergeTree + Keeper: данные неизбежно расходятся.

    Избыточная предагрегация: SummingMergeTree с 20 колонками в ключе сортировки уменьшает данные лишь втрое, но необратимо уничтожает аналитическую гибкость, а изменить ключ сортировки существующей таблицы нельзя — только пересоздание. ClickHouse рождён для неагрегированных данных; агрегировать заранее — крайняя мера.

    Запросы в цикле вместо одного запроса с IN: каждый точечный запрос читает гранулы и блоки сжатия — сотни циклов выполняют сотни раз больше работы, чем один проход.

7. Best practices

    Первичный ключ (ORDER BY): колонки самых частых фильтров, от низкой кардинальности к высокой; префикс ключа обслуживает запросы без полного сканирования. Если диапазонных запросов по дате нет и не будет — дату в ключ можно не включать; включите колонку, по которой данные лучше сжимаются (например, user_id).

    Ключ партиционирования: гранула maintenance-операций (обычно месяц/день по времени); партиций не должно быть слишком много.

    Вставки: только батчами или через async_insert.

    Избегайте мутаций как регулярной операции; периодические удаления — через TTL и DROP PARTITION.

    Избегайте OPTIMIZE TABLE ... FINAL в проде.

    Избегайте Nullable-колонок.

    Материализованные представления — для повторяющихся агрегаций.

    Минимизируйте JOIN'ы — денормализация и словари; если JOIN неизбежен — маленькая таблица справа.

    Data skipping indices (minmax, set, bloom_filter) — там, где фильтр не совпадает с ключом сортировки.

    Типы данных — минимально достаточные: UInt32 вместо UInt64, Date вместо DateTime, LowCardinality вместо String.

8. Итоги

    OLAP-нагрузка (сканы миллионов строк по узкому набору колонок) делает строковое хранение расточительным: колоночная модель DSM читает только нужные колонки, лучше сжимает и векторизуется. ClickHouse — эталонная реализация этих принципов.

    Хранение ClickHouse построено на иммутабельных отсортированных parts MergeTree: нет memtable и WAL, вставка сразу формирует part, фоновые слияния поддерживают их число и реализуют логику специализированных движков. Разреженный индекс (mark на гранулу из 8192 строк) целиком живёт в памяти; партиции — единица pruning и maintenance.

    Плата за архитектуру: точечные чтения и обновления дороги, транзакций нет. Поэтому — батчевые вставки, денормализация, словари вместо JOIN'ов, мутации как исключение.

    Масштабирование — shared-nothing: шарды + Distributed, реплики + Keeper (Raft), ingestion через Kafka.
