Q1
SELECT DISTINCT flight_no FROM flights ORDER BY flight_no;

SELECT flight_no FROM flights GROUP BY flight_no ORDER BY flight_no;

1) Итог полностью совпадает — оба выражения убирают дубликаты flight_no, оставляя только уникальные значения.
DISTINCT предназначен непосредственно для дедупликации строк, тогда как GROUP BY обычно применяется для дальнейших агрегаций (COUNT, SUM и т.д.). Посколько агрегатных функций здесь нет, логика их работы одинакова

по `EXPLAIN` планы тоже получаются одинаковые, PostgeSQL видит что группировка идёт по одному столбцу и строит `HashAggregate` или `Sort + Unique` так что в этом случае запросы равнозначны и по данным и по плану

2) ORDER BY без явного указания направления по умолчанию применяет порядок по возрастанию ASC, поэтому ключевое слово ASC можно опустить.
При сортировке по умолчанию PostgreSQL использует collation (например en_US.UTF-8), где регистр учитывается, но порядок определяется правилами локали

Q2
SELECT
    f.flight_id,
    f.flight_no,
    COUNT(DISTINCT t.passenger_id) AS passengers_count,
    COALESCE(SUM(tf.amount), 0) AS revenue
FROM flights f
LEFT JOIN ticket_flights tf ON tf.flight_id = f.flight_id
LEFT JOIN tickets t ON t.ticket_no = tf.ticket_no
GROUP BY f.flight_id, f.flight_no;

1)  один пассажир купил два билета на один рейс
Сумма выручки (SUM(amount)) складывает данные из таблицы ticket_flights, где каждая запись — это отдельный билет. Поскольку пассажир оплачивает каждый билет, обе суммы корректно попадут в общую выручку

Подсчёт пассажиров через COUNT(*) неверно, тк он посчитал бы количество строк (билетов), а не людей. Пассажир с двумя билетами был бы учтён дважды, чтобы не получилось такого, используется COUNT(DISTINCT t.passenger_id)

LEFT JOIN: для рейса, на который не продано ни одного билета, COUNT(*) вернул бы 1 (так как в результате соединения появилась бы одна строка с NULL), а не 0. Это причина, почему пассажиров нужно считать именно через COUNT(DISTINCT t.passenger_id)

2) рейс без проданных билетов
используя LEFT JOIN, такой рейс не исчезнет из отчёта. Вместо этого в полях, относящихся к билетам, появятся значения NULL

Функция COALESCE(SUM(...), 0) нужна для замены NULL на 0: если у рейса нет билетов, то SUM по строкам с NULL вернёт NULL, а COALESCE превратит его в ноль

COUNT(DISTINCT ...) при подсчёте пассажиров игнорирует NULL, поэтому для такого рейса он вернёт 0

INNER JOIN оставляет только совпадающие строки. Если для рейса нет ни одной записи в ticket_flights, при INNER JOIN он полностью выпадет из результата — а нам нужно показать его с нулями

LEFT JOIN сохраняет все строки из левой таблицы (flights), подставляя NULL там, где совпадений нет — это и позволяет получить нулевую выручку через COALESCE

Q3
SELECT a.city
FROM airports a
WHERE NOT EXISTS (
    SELECT 1
    FROM flights f
    WHERE f.departure_airport = a.airport_code
    AND f.status = 'Cancelled'
)
ORDER BY a.city;

Если из аэропорта не вылетало вообще никаких рейсов (ни обычных, ни отменённых), он всё равно должен попасть в результат — ведь отменённых рейсов оттуда нет. Конструкция NOT EXISTS это и обеспечивает: для такого аэропорта подзапрос не находит ни одной строки, условие NOT EXISTS становится истинным, и город проходит в выборку. Вариант с NOT IN в данном случае тоже сработал бы, так как подзапрос не вернул бы ничего для этого кода


Главная ловушка NOT IN — наличие NULL в сравниваемом списке. Любое сравнение с NULL даёт результат UNKNOWN, а AND с UNKNOWN не возвращает TRUE. В итоге условие WHERE отбрасывает UNKNOWN так же, как и FALSE, поэтому строки могут просто исчезнуть, и на практике можно получить пустую выборку.

У NOT EXISTS такой ловушки нет: он ничего не сравнивает со списком, а просто проверяет, существует ли подходящая строка. Наличие NULL в других столбцах на это не влияет. Именно поэтому для подобных задач NOT EXISTS безопаснее — это прямое правило из лекции.

Q4
SELECT t.passenger_id, MIN(t.passenger_name) AS passenger_name
FROM boardings b
JOIN tickets t ON t.ticket_no = b.ticket_no
WHERE b.flight_id = 1 
GROUP BY t.passenger_id;

Два посадочных талона у одного пассажира
Если у одного пассажира есть два посадочных талона, группировка по passenger_id (в отличие от пары passenger_id, passenger_name) соберёт их в одну строку. Это надёжнее, чем DISTINCT по паре (passenger_id, passenger_name): если имя в разных билетах записано по-разному, такой DISTINCT вернул бы две отдельные строки вместо одной.

в принципе разницы нет. И DISTINCT, и GROUP BY обрабатываются одинаково и работают с одинаковой скоростью.

DISTINCT — когда нужно просто убрать дубликаты и получить уникальный список.

GROUP BY — когда помимо удаления дубликатов нужно что-то посчитать или агрегировать (например, количество посадочных талонов или список мест).

Билет сдан, но посадочный талон остался
Аномалия не будет замечена. Запрос соединяет только boardings и tickets по ticket_no, а таблица ticket_flights в нём не участвует. Поэтому пассажир со сданным билетом, но существующим посадочным талоном, всё равно попадёт в результат.

Если добавить INNER JOIN с ticket_flights (например, чтобы посчитать выручку), такой пассажир исчезнет из выборки — для него просто не найдётся пары в таблице ticket_flights.

Q5
1) ALTER TABLE flights ADD COLUMN weather_data JSONB;
Эта команда запрашивает блокировку ACCESS EXCLUSIVE. Она несовместима ни с какой другой блокировкой, включая ACCESS SHARE, которую берёт обычный SELECT.

Если транзакция BEGIN; SELECT COUNT(*) FROM flights; уже выполнила SELECT, но ещё не завершилась (COMMIT/ROLLBACK), то ACCESS SHARE с неё не снимается. В результате ALTER TABLE встаёт в очередь и ждёт завершения этой транзакции.
Пока ALTER стоит в очереди, все новые запросы к таблице (даже простые SELECT) встают за ним. Получается, что одна забытая открытая транзакция может заблокировать всю работу с таблицей.

2) Начиная с PostgreSQL 11, ADD COLUMN ... DEFAULT const не переписывает существующие строки.

Postgres просто записывает в системный каталог, что у таблицы появился столбец с таким значением по умолчанию. Физически в старых строках на диске этого столбца нет — при чтении значение подставляется из каталога «на лету». Новые строки уже хранят значение как обычно. Поэтому команда выполняется мгновенно, независимо от размера таблицы.

Если потом поменять default на true (ALTER TABLE flights ALTER COLUMN is_delayed SET DEFAULT true;) -- это тоже только метаданные. Старые строки остаются со старым значением false, их никто не перезаписывает. Параллельные INSERT, которые в момент смены не указывают is_delayed, получат тот default, который действует на момент их выполнения: до ALTER -- false, после — true. Блокировки записи это не создаст, кроме короткой метаданной блокировки самого ALTER.

3. CREATE INDEX idx_flights_status ON flights(status);

Без CONCURRENTLY эта команда держит ShareLock на таблице всё время построения индекса. ShareLock пропускает SELECT, но несовместим с ROW EXCLUSIVE, который нужен для INSERT/UPDATE/DELETE. Значит, все записи ждут, пока индекс не построится, а на большой таблице это может быть долго.

Чтобы этого избежать, используют CREATE INDEX CONCURRENTLY idx_flights_status ON flights(status);

Минус: строится заметно дольше (два прохода по таблице) и требует ожидания старых транзакций. Нельзя запускать внутри блока транзакции — если прервать, останется «битый» индекс со статусом INVALID, который нужно вручную удалить и создать заново. Также CONCURRENTLY берут не всегда — там, где простой на запись недопустим.

Q6
1) 
SELECT AVG(actual_departure - scheduled_departure) AS avg_delay
FROM flights;
Если actual_departure = NULL (рейс отменён или ещё не вылетел), то и разность будет NULL.

Агрегатные функции (включая AVG, но кроме COUNT()) игнорируют NULL. AVG вычисляется как сумма не-NULL значений, делённая на их количество.
Следовательно, рейсы без фактического времени вылета просто не участвуют в расчёте — они не превращаются в «нулевую задержку» и не искажают среднее ни в одну, ни в другую сторону. В итоге мы получаем среднюю задержку по фактически вылетевшим рейсам, а не по всем.

2) COUNT(aircraft_code) vs COUNT(*)
COUNT(aircraft_code) считает только строки, где значение не NULL. COUNT(*) считает все строки без исключения.

Результаты совпадают, если в столбце нет NULL, и различаются, если есть рейсы с aircraft_code IS NULL (например, самолёт ещё не назначен). Разница равна количеству таких строк.

Связь с ограничением NOT NULL: если на столбец aircraft_code наложено NOT NULL, то NULL в нём в принципе невозможен, и оба COUNT всегда дадут одинаковый результат. Без такого ограничения на уровне схемы совпадение результатов ничем не гарантировано.
