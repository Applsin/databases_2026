# Конспект семинара №6. Индексы в PostgreSQL: статистика, EXPLAIN и частичные индексы

## 1. Цена индекса

Индекс — архитектурный компромисс. Ускоряет чтение, но:

- **Замедляет запись.** Каждый `INSERT/UPDATE/DELETE` требует обновления не только Heap, но и структуры индекса. Для OLTP-профиля здоровое соотношение — 80–90% чтений и 10–20% записей.
- **Занимает дисковое место.** Ориентир: суммарный размер индексов не должен превышать ~50% размера таблицы. Если индексы в разы больше данных — архитектура неверна.
- **Подвержен bloat.** Из-за MVCC при `UPDATE` появляются новые версии строк, а в B-Tree остаются «мёртвые» ссылки. `VACUUM` переиспользует страницы таблицы, но индексные «пустоты» копятся сильнее и требуют периодического `REINDEX` (на нагруженной БД это ювелирная работа DBA).

Правило: **индекс создаётся под конкретный запрос, а не «на всякий случай»**.

## 2. Типы индексов PostgreSQL: теория

### 2.1 B-Tree (по умолчанию)

**Суть.** Сбалансированное дерево поиска: все листья на одной глубине, внутренние узлы хранят разделительные ключи, листья — пары `(ключ, TID)`. Листья связаны двусвязным списком — это даёт быстрый последовательный доступ при range-скане и `ORDER BY`.

**Структура.**
```
       [ разделитель ]
       /              \
  [узел]            [узел]
   /  \              /  \
leaf leaf          leaf leaf
  ↓    ↓            ↓    ↓
 (key, (key,      (key, (key,
  TID)  TID)       TID)  TID) ← листья связаны в список
```

**Что умеет.** `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `IN`, `IS NULL`, `ORDER BY`, `MIN/MAX`, префиксный `LIKE 'abc%'` (при правильной collation/opclass), уникальные и exclusion-ограничения. B-Tree — единственный тип, поддерживающий сортировку и уникальность в чистом виде.

**Когда применять.** По умолчанию почти всегда. PK, FK, уникальные ключи, колонки с высокой кардинальностью в `WHERE`/`ORDER BY`.

---

### 2.2 Hash

**Суть.** Хеш-таблица. Ключ хешируется в bucket, внутри bucket хранятся пары `(hash, TID)`. Порядка нет, диапазоны не поддерживаются — только точное равенство `=`.

**Структура.**
```
key → hash(key) % N → bucket
                       [hash, TID]
                       [hash, TID]
```

С PostgreSQL 10 Hash-индексы WAL-логируются и стали crash-safe, но по-прежнему используются редко: B-Tree почти всегда не хуже, а гибче (умеет диапазоны, сортировку, уникальность).

**Когда применять.** Только для чистого равенства (`=`) по колонке с высокой кардинальностью, когда B-Tree неоправданно велик. На практике — редкость.

---

### 2.3 GIN (Generalized Inverted Index)

**Суть.** Инвертированный индекс: не «строка → значение», а «элемент → список строк». Для неатомарных значений: `tsvector`, `jsonb`, массивы, `hstore`, `pg_trgm`.

**Структура.** Две части:

1. **Entry tree** — B-Tree по элементам. Каждый элемент (лексема, ключ JSONB, элемент массива, триграмма) — отдельный ключ.
2. **Posting list** — упорядоченный набор `TID`, ссылающихся на строки с этим элементом. Если TID много — posting list выносится в отдельные страницы.
3. **Pending list** — буфер для быстрых вставок; периодически разбирается в entry tree.

```
GIN
├── Entry tree (B-Tree по элементам)
│   ├── element_1 → posting list [TID, TID, ...]
│   ├── element_2 → posting list [TID, ...]
│   └── ...
└── Pending list [новые TID до разбора]
```

**Как работает запрос.** Для `@>`, `@@`, `?` планировщик находит нужные элементы в entry tree, пересекает posting list’ы (bitmap AND/OR), получает набор TID, идёт в кучу. Для lossy-opclass (например, `pg_trgm`) обязателен recheck.

**Аналогия.** Алфавитный указатель в конце книги: термин → список страниц.

**Особенности.**
- Элементы **никогда не удаляются** из GIN: набор элементов считается статичным, меняется лишь привязка к строкам.
- Обновление дороже, чем у B-Tree: чистка posting list’ов.
- Хорошо сжимается, если элементов мало, а строк много (обратная ситуация — плохо).

**Когда применять.** Полнотекстовый поиск (`tsvector @@ tsquery`), JSONB containment (`@>`, `?`, `?|`, `?&`), массивы (`@>`, `&&`, `<@`), trigram-поиск (`LIKE '%...%'` через `pg_trgm`). Не для диапазонов и сортировки.

---

### 2.4 GiST (Generalized Search Tree)

**Суть.** Обобщённое поисковое дерево с расширяемыми предикатами. Внутренние узлы хранят не ключи, а **предикаты** (bounding box, объединение диапазонов, пересечение множеств). Поиск спускается только в те ветки, чьи предикаты пересекаются с условием запроса.

**Структура.**
```
Root: предикат, покрывающий всё
      /              \
 предикат A        предикат B
 /    \            /    \
obj   obj         obj   obj
```

**Особенности.**
- Расширяется через opclass: PostGIS, `tsrange`, `int4range`, `ltree` и т.п.
- Может быть **lossy**: узел пропускает больше строк, чем реально подходит, — тогда нужен recheck в куче.
- Не сбалансирован так строго, как B-Tree; глубина зависит от данных.

**Когда применять.** Геометрия (PostGIS), диапазоны дат и чисел (пересечения `&&`), ближайшие соседи (`<->`), exclusion constraints (запрет пересечений). GiST — «швейцарский нож» для нестандартных типов, если нет более специализированного SP-GiST.

---

### 2.5 SP-GiST (Space-Partitioned GiST)

**Суть.** Разновидность GiST, которая рекурсивно делит пространство на **непересекающиеся** области (quadtree, k-d tree, radix tree). Дерево намеренно несбалансированное — это позволяет эффективно обрабатывать точечные данные и префиксные строки.

**Структура.**
```
          root
     /     |     \
  сектор сектор сектор
   /  \    |
 obj  obj obj ...
```

**Особенности.**
- Нет гарантии логарифмической глубины, но для точечных/префиксных данных обычно быстрее и компактнее GiST.
- Поддерживает `point`, `inet`, диапазоны, текстовые префиксы (`text_ops`).

**Когда применять.** Геоточки, IP-адреса (`inet`), диапазоны, префиксный поиск. Часто эффективнее GiST там, где данные плохо ложатся в bbox.

---

### 2.6 BRIN (Block Range Index)

**Суть.** Хранит сводку (обычно `min/max`) по диапазонам страниц кучи. По умолчанию диапазон — 128 страниц. Индекс крошечный: несколько записей на тысячи строк.

**Структура.**
```
Heap: [стр. 1–128]  [стр. 129–256]  [стр. 257–384]
Знач.:   1..100        101..200        201..300
BRIN:  (1,100)       (101,200)       (201,300)

Запрос x=150 → читаем только диапазон 129–256
```

**Особенности.**
- Работает, только если значения **физически коррелированы** с порядком строк (обычно append-only по времени).
- При плохой корреляции min/max становятся широкими, и BRIN почти не отсекает страницы.
- Идеально для огромных таблиц (сотни ГБ–ТБ), где B-Tree неприемлемо велик.

**Когда применять.** Логи, телеметрия, time-series, append-only таблицы с естественной сортировкой по колонке. Диапазонные запросы по времени.

### 2.7 Итоговая таблица

| Тип | Операции | Лучше всего для | Размер | Стоимость обновления |
|---|---|---|---|---|
| B-Tree | `=`, диапазоны, сортировка | OLTP, PK, FK, универсально | средний | низкая |
| Hash | только `=` | точное равенство, высокая кардинальность | средний | низкая |
| GIN | `@@`, `@>`, `&&`, `?` | FTS, JSONB, массивы, trigram | большой | высокая |
| GiST | `&&`, `<->`, `@>` | геометрия, диапазоны, exclusion | средний | средняя |
| SP-GiST | `<@`, `<<`, префиксы | точки, inet, диапазоны, префиксы | средний | средняя |
| BRIN | диапазоны | huge append-only, коррелированные данные | крошечный | очень низкая |

**Главное правило:** B-Tree — универсальный выбор; остальные — под задачу.

## 3. Поиск узких мест

Плохой запрос — не всегда медленный запрос. Опасны быстрые (10 мс) запросы, вызываемые миллионы раз: суммарная нагрузка колоссальна.

- **`pg_stat_statements`** — главный инструмент. Агрегирует по всем запросам: среднее/общее время, число вызовов, I/O, temp-файлы. Позволяет найти топ по `total_time` и `calls`, а не только по `mean_time`.
- **`pgBadger`** — парсер логов. Осторожно: логирование всех запросов «убьёт» диск I/O, а порог «>100 мс» даст искажённую картину, скрыв массовые быстрые проблемы.

Метрики, на которые смотреть: самые частые запросы, самые «времязатратные», генераторы temp-файлов, ошибки, histogram времён.

## 4. Статистика перед созданием индекса: `pg_stats`

Планировщик строит план **не по данным, а по статистике**. Смотрим:

```sql
SELECT attname, n_distinct, null_frac,
       most_common_vals, most_common_freqs, correlation
FROM pg_stats
WHERE tablename = 'flights';
```

- **`n_distinct`** — кардинальность: число уникальных не-NULL значений. Отрицательное значение — доля от размера таблицы (`-1` ≈ все уникальны).
- **`null_frac`** — доля `NULL`. Влияет на выборку и полезно для частичных индексов.
- **`most_common_vals` / `most_common_freqs`** — частые значения и их частоты. Если нужное значение — MCV с высокой частотой, индекс по колонке малоэффективен.
- **`correlation`** — насколько физический порядок строк совпадает с логическим (`-1..1`). Близко к `1` — Index Scan дёшев (последовательное чтение страниц), близко к `0` — дорогой random I/O.

Практический вывод: перед `CREATE INDEX` проверьте, есть ли вообще селективность и корреляция, которые оправдают индекс.

## 5. Практикум 1: Seq Scan vs Index Scan

**Наивный запрос без индекса:**

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM flights
WHERE scheduled_departure >= '2017-08-15'
  AND scheduled_departure <  '2017-08-16';
```

Узел `Seq Scan on flights`, `Buffers: shared hit=832` — читается вся таблица.

**Создаём индекс:**

```sql
CREATE INDEX idx_flights_departure ON flights(scheduled_departure);
```

План меняется на `Bitmap Heap Scan` + `Bitmap Index Scan`. Количество прочитанных буферов резко падает, время сокращается с ~12 мс до ~1 мс.

**Правило.** Тестируйте запрос с **реальными** параметрами production. Планировщик оценивает план по статистике, и значения фильтров критичны.

**Почему Bitmap, а не чистый Index Scan?** Когда строк много, но они разбросаны по страницам, `Bitmap Index Scan` собирает все TID, сортирует их по страницам и затем `Bitmap Heap Scan` читает страницы последовательно — экономит random I/O.

## 6. Sargability

**Правило.** Если к индексированной колонке применена функция в `WHERE`, B-Tree **не используется** — планировщик не может сопоставить функцию со деревом.

```sql
-- плохо: Seq Scan
WHERE EXTRACT(MONTH FROM scheduled_departure) = 8

-- хорошо: диапазон → Index Scan
WHERE scheduled_departure >= '2017-08-01'
  AND scheduled_departure <  '2017-09-01'
```

Такой запрос называется **sargable** (Search ARGument able). Аналогично: `WHERE lower(col) = 'x'` — не sargable, но `WHERE col = 'X'` — да (при правильной collation). Исключение: **функциональные индексы** (`CREATE INDEX ON t (lower(col))`) — тогда функция индексируется, и планировщик её узнаёт.

## 7. Составные индексы

Если запрос фильтрует по нескольким колонкам, можно построить составной индекс.

**Правило порядка:** сначала колонки с `=` (точное совпадение), затем — с диапазоном/сортировкой.

**Причина.** B-Tree упорядочен лексикографически: сначала по первой колонке, внутри — по второй. Поэтому равенство по первой колонке «отсекает» узкий диапазон дерева, внутри которого вторая колонка уже отсортирована и диапазон по ней читается последовательно. Если поставить диапазонную колонку первой, равенство по второй пришлось бы искать во всех значениях первой — индекс почти бесполезен.

```sql
CREATE INDEX idx_flights_airport_date
  ON flights(departure_airport, scheduled_departure);
```

**Когда применять.** Запросы с фиксированным набором колонок в `WHERE`, `JOIN`, `ORDER BY`. Помните про **префиксное правило**: индекс `(a, b, c)` покрывает запросы по `(a)`, `(a, b)`, `(a, b, c)`, но не по `(b)` или `(b, c)`.

## 8. Частичные индексы (Partial Indexes)

**Идея.** Индексируем только строки, удовлетворяющие условию. Если запросы всегда смотрят на подмножество — индексировать остальное бессмысленно.

```sql
CREATE INDEX idx_flights_cancelled
  ON flights(scheduled_departure)
  WHERE status = 'Cancelled';
```

**Преимущества.**
- Компактность: индекс в разы меньше полного.
- Быстрее обновляется при `INSERT/UPDATE` (не все строки попадают в индекс).
- Лучше помещается в `shared_buffers`.

**Ограничение применимости.** Планировщик использует частичный индекс, только если предикат запроса **гарантированно** подпадает под условие индекса. Запрос `WHERE scheduled_departure >= ...` без `status = 'Cancelled'` не сможет его использовать — в индексе нет остальных строк.

**Типичные сценарии.**
- Колонки с большим числом `NULL` (`WHERE col IS NOT NULL`).
- Редкие статусы (`Cancelled`, `Delayed`, `Failed`).
- Активные записи (`WHERE deleted_at IS NULL`).
- Технические флаги (`WHERE is_processed = false`).

## 9. Итоги

1. Индекс — архитектурный компромисс: место на диске и замедление записи в обмен на скорость чтения.
2. Разные типы индексов решают разные задачи: B-Tree — универсально, GIN — неатомарные данные, GiST/SP-GiST — пространственные, BRIN — большие коррелированные таблицы.
3. Перед созданием индекса изучают `pg_stats`: кардинальность, `NULL`-фракцию, корреляцию, MCV.
4. `EXPLAIN (ANALYZE, BUFFERS)` — главный инструмент проверки гипотез. `Seq Scan` vs `Index Scan` vs `Bitmap Heap Scan`.
5. Sargability: не применяйте функции к индексированным колонкам.
6. Составные индексы: сначала `=`, потом диапазон.
7. Частичные индексы — точечная оптимизация OLTP, когда запросы работают с узким подмножеством строк.
