# Конспект лекции №4. Управление памятью и диском в СУБД

## 1. Введение

В **диск-ориентированных СУБД** основное хранилище — энергонезависимая память (HDD или SSD). В **in-memory СУБД** данные хранятся в оперативной памяти.

СУБД должна эффективно перемещать данные между диском и памятью с помощью **Менеджера буферного пула** (Buffer Pool Manager).

Менеджер работает как **write-back кэш**: часто используемые страницы остаются в памяти, неиспользуемые — вытесняются на диск. В отличие от **write-through кэша**, изменения сбрасываются на диск не сразу.

СУБД старается оптимизировать два аспекта:
1. **Spatial Control (Пространственный контроль):** физическое расположение страниц на диске. Часто используемые вместе страницы хранятся как можно ближе друг к другу.
2. **Temporal Control (Временной контроль):** моменты загрузки страниц в память и записи обратно. Минимизирует простои от чтения с диска.

## 2. Буферный пул (Buffer Pool)

Это in-memory кэш страниц — большая область памяти, выделенная СУБД. Организован как массив **фреймов** фиксированного размера. При запросе страницы менеджер проверяет её наличие в памяти; если отсутствует — копирует с диска в свободный фрейм.

Буферный пул используется для:
- хранения кортежей и индексов;
- буферов сортировок и соединений;
- кэшей запросов и словарей;
- буферов обслуживания и логов.

**Page Directory (директория страниц):** структура на диске, сопоставляющая ID страниц с их местоположением в файлах. Все изменения записываются на диск для восстановления при перезапуске. Часто хранится в памяти.

### Метаданные буферного пула

- **Page Table (Таблица страниц):** in-memory хеш-таблица, отслеживающая страницы в памяти. Сопоставляет ID страниц с фреймами. На страницу хранятся: **dirty flag** и **pin/reference counter**.
- **Dirty Flag:** устанавливается потоком при изменении страницы. Указывает, что перед вытеснением страницу нужно записать на диск.
- **Pin / Reference Counter:** считает количество потоков, работающих со страницей. Если счётчик > 0, страница **закреплена (pinned)** и не может быть вытеснена. Если закреплены все страницы, а нужна новая — ошибка нехватки памяти.
- **Access Tracking Information:** отслеживает, какие транзакции обращаются к странице.

### Page Table vs. Page Directory

- **Page Directory:** сопоставление ID страниц с местами в физических файлах. Изменения записываются на диск для восстановления.
- **Page Table:** сопоставление ID страниц с копиями во фреймах пула. In-memory структура, не хранится на диске.

## 3. СУБД против операционной системы

### Locks vs. Latches

- **Locks (Блокировки):** высокоуровневый, логический примитив для защиты *содержимого* БД (кортежей, таблиц) от других транзакций. Видны пользователю. Требуют отката изменений.
- **Latches (Защёлки):** низкоуровневый примитив для защиты критических секций во *внутренних структурах* СУБД (хеш-таблицы, память). Удерживаются только на время операции. Не требуют отката. Реализуются через мьютексы.

### Почему не использовать ОС?

Проблемы `mmap` и страничного кэша ОС:
1. **Безопасность транзакций:** ОС сбрасывает «грязные» страницы в любой момент.
2. **Простои ввода-вывода:** СУБД не знает, какие страницы в памяти. ОС блокирует поток на page fault.
3. **Обработка ошибок:** любой доступ к памяти может вызвать SIGBUS.
4. **Производительность:** конкуренция за структуры ОС, TLB shootdowns.

СУБД управляет памятью лучше, потому что **лучше понимает, что важно для неё**:
1. Сброс «грязных» страниц в правильном порядке.
2. Специализированная предвыборка (prefetching).
3. Лучшие стратегии замещения.
4. Планирование потоков/процессов.

Точечные механизмы ОС, которые СУБД всё же применяют: `madvise` (подсказка о планируемом чтении), `mlock` (запрет выгрузки в своп), `msync` (принудительный сброс на диск).

## 4. Стратегии замещения страниц (Buffer Replacement Policies)

Используются при нехватке фреймов. Критерии: корректность, точность, скорость, минимум метаданных. Закреплённые страницы не вытесняются.

- **Least Recently Used (LRU):** хранит временную метку последнего доступа. Вытесняется страница с самой старой меткой. Поддержание порядка метаданных затратно.
- **CLOCK:** аппроксимация LRU без отдельных меток. Страница имеет **reference-бит** (1 — был доступ). «Стрелка часов» движется по кольцевому буферу: если бит 1 — сбрасывает в 0; если 0 — вытесняет. Положение стрелки сохраняется.

### Проблемы LRU и CLOCK

- **Sequential flooding:** загрязнение пула при последовательном сканировании. Быстрое чтение многих страниц вытесняет потенциально более нужные.
- LRU не учитывает **частоту** доступа. **Least-Frequently Used (LFU)** считает обращения, но игнорирует время и накапливает устаревшие страницы.

### Альтернативы

- **LRU-K:** отслеживает историю K обращений как временные метки, вычисляет интервалы для прогноза. Высокие накладные расходы. Требуется **«ghost cache»** — список недавно вытесненных страниц для предотвращения пробуксовки (thrashing).
- **MySQL-аппроксимация LRU-2:** один связный список с двумя точками входа («молодой» и «старый» списки). Новая страница — в начало «старого»; при повторном доступе — в начало «молодого». Вытеснение из конца «старого».
- **Локализация по запросу:** вытеснение в привязке к запросу/транзакции.
- **Priority hints:** транзакции сообщают пулу о важности страниц.

### ARC: Adaptive Replacement Cache

Разработка IBM Research. Поддерживает LRU и LFU, динамически меняя размеры списков на основе паттернов доступа. Использует «ghost lists» и параметр `p` для баланса recency/частоты:
1. **Recency List T1:** страницы с одним обращением.
2. **Frequency List T2:** страницы с двумя и более обращениями.
3. **Параметр p:** регулирует предпочтение T1 или T2.

### «Грязные» страницы (Dirty Pages)

Страницы с установленным **dirty flag**.
- **Быстрый путь:** страница не «грязная» — просто удаляется.
- **Медленный путь:** страница «грязная» — перед вытеснением записывается на диск.
- **Фоновая запись (Background writing):** периодическая запись «грязных» страниц в фоне с последующим снятием флага или вытеснением.

## 5. Дисковый ввод-вывод и кэш ОС

ОС/оборудование переупорядочивают запросы ввода-вывода, но не знают приоритетов. СУБД ведёт внутренние очереди и определяет приоритеты по:
- последовательный или случайный ввод-вывод;
- задача критического пути или фоновая;
- тип данных: таблица, индекс, лог, эфемерные данные;
- информация о транзакциях;
- пользовательские SLA.

Большинство СУБД используют **Direct I/O** (флаг `O_DIRECT`) в обход файлового кэша ОС для избежания избыточных копий и конфликта стратегий вытеснения. PostgreSQL исторически — исключение, полагающееся на страничный кэш ОС, но PostgreSQL **18** вводит асинхронный I/O как шаг к Direct I/O.

**Fsync-gate (2018):** при ошибке `fsync` ядро Linux помечало «грязные» страницы чистыми, и повторный `fsync` ложно сообщал об успехе — скрытая потеря данных во многих СУБД ~20 лет. Вывод: СУБД не доверяет ОС без проверки.
